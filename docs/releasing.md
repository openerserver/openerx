# 构建与发布

## 版本、标签与发布通道

源码合并和安装包发布是两个独立步骤。`main` 保存已验证的源码；只有从确定提交构建、完成对应验证并上传产物后，才代表该版本可供下载安装。不要把已有 Release 的旧安装包描述为包含新的主分支修复。

- 正式版使用 `vX.Y.Z` 标签，Release 标题使用 `openerx X.Y.Z`；补丁、兼容功能、不兼容变更分别递增 patch、minor、major。
- 测试版使用 `vX.Y.Z-rc.N` 或 `vX.Y.Z-beta.N` 标签，必须勾选 **Pre-release**，不能设为 **Latest**。最新版已验收的稳定版才设为 Latest；没有稳定版时允许没有 Latest。
- 候选版通过验收后，为确认的源码提交创建正式标签及正式 Release，核对正式构建的版本和构建信息；不要只取消 `-rc.N` Release 的 Pre-release 标记来充当正式版。
- 当前产品版本工具接受三段数字版本。应用内部版本保持 `X.Y.Z`；预发布后缀放在 Git 标签、Release 标题和分发文件名中，源码提交与通道写入构建信息，以区分同一内部版本的不同候选构建。使用 `npm run version:bump -- patch` 或 `node scripts/product-version.mjs set X.Y.Z` 同步版本，再运行 `npm run version:check`，不要只改桌面端的单个版本字段。
- 一个完整标签对应一个 Release，同一 Release 汇总该提交的各平台、架构产物，不按 Windows、macOS 单独创建版本标签。未提供的平台应在发布说明中明确列出，不暗示已经支持下载安装。
- 既有 `v2.0.5-macos-preview.1` 保留为历史预览版，不删除、不改标签指向、不替换已有文件；它不代表后续主分支修复已经发布。后续版本采用以上命名规则。

本规则不启用应用自动更新。安装包上传到 GitHub 与客户端自动更新配置、签名清单和升级验证相互独立。

## 本地构建

在仓库根目录执行，先退出正在使用目标输出目录的应用：

```sh
npm ci
npm run check:local
npm run package:v2
npm run make --workspace @openerx/desktop
```

`package:v2` 生成应用包，`make` 生成对应平台的分发产物。输出固定在 `apps/desktop/out/`。开发调试使用 `npm run dev:desktop`；不要为每次调试复制应用包或整个用户配置目录。

## 验证

发布前运行公开文件检查、边界检查、类型检查、相关单元和集成测试，并在目标平台运行桌面端到端测试。应用包还需检查 Electron fuses、产物内容与原生签名：

```sh
npm run test:e2e:v2
npm run verify:package:v2
npm run verify:release-artifacts --workspace @openerx/desktop
npm run verify:native-signature --workspace @openerx/desktop
```

本地通过不自动表示其他操作系统、签名安装、升级回滚或商店分发已经通过。项目目录、权限重连、同步冲突及远程执行也应在发布环境验证。

## 本地签名与上传发布

GitHub 仅托管源码和上传的 Release 文件，不运行检查或构建；自动 CI 和手动发布工作流均已移除，仓库 Actions 已停用。Windows 安装包及端到端测试需要本地 Windows 机器或 Windows 虚拟机；macOS 包在对应架构的 Mac 环境构建并验证。不要将 Mac 的检查结果当作 Windows 验证结果。

证书、签名密码、更新公钥配置及公证凭据由本地发布环境提供，不能写入源码。正式通道先运行 `npm run release:gate:v2`，完成所要求的外部验收与发布批准。签名和公证完成后，在本地验证分发文件、校验值与更新清单，再由维护者上传 GitHub Release。发布说明记录源码提交、平台、架构、签名状态及验证结果；上传文件不会触发云端检查。

## Release 操作清单

1. 确定版本和通道，更新并检查产品版本；将修复和版本变更合入 `main`。在干净的工作区执行本地检查，记录完整源码提交 SHA。发布标签必须指向该提交，不得指向未验证的工作区内容。
2. 为该提交创建带说明的 Git 标签，在 GitHub 创建 **Draft** Release。正式标签如 `v2.0.6`，候选标签如 `v2.0.6-rc.1`；这些仅为格式示例，不表示版本已经发布。每个平台必须检出同一个提交构建。
3. 在目标平台完成构建、桌面 E2E、产物检查及对应签名验证。明确区分源码测试、开发态桌面运行、打包应用和安装/升级验证；跳过、失败或尚未验证的项目必须如实记录。未完成正式验收的构建只能作为明确注明限制的 Pre-release，不能通过改标记冒充稳定版。
4. 上传面向用户的安装包及确有用途的便携包。文件名包含产品、完整发布版本、平台和架构，例如 `openerx-2.0.6-rc.1-windows-x64-unsigned.exe`、`openerx-2.0.6-macos-arm64.dmg`。只修改交付文件名时必须确认不会破坏安装器或更新清单的引用；不要重命名已发布文件。未签名产物应在文件名及说明中显式标注。
5. 上传 `SHA256SUMS` 和 `BUILD-INFO.json`：前者覆盖全部分发文件，使用最终签名后的字节计算；后者记录发布版本、应用内部版本、标签、完整提交 SHA、构建平台/架构、工具链版本、签名/公证状态、执行过的验证及结果，不包含凭据或本机隐私路径。需要更新清单的通道同时上传验证过的签名清单。GitHub 自动附带的 Source code 压缩包不算安装包。
6. 按下方模板完成发布说明，检查资产列表；从 Draft 下载分发文件并比对 SHA-256，在目标系统执行安装、启动及所承诺的升级验证。核对各平台版本、提交和签名状态一致后再发布。只有通过正式发布门禁与外部验收的稳定版可以取消 Pre-release 并设置 Latest。
7. 发布后保留标签和已发布产物，不覆盖同名文件。二进制需要修复时递增补丁号或预发布序号，创建新标签和新 Release；不要移动旧标签。文案错误可以更正，但需保留真实的构建和验证信息。发现严重问题时说明风险、停止推荐该版本并发布修复版，不悄悄替换下载内容。

## 发布说明模板

将以下内容填写在 GitHub Release 中，不另建逐次发布的仓库报告。只有实际提供的下载和实际执行的验证才能列为可用或通过。

```markdown
## openerx <发布版本>

通道：稳定版 / Pre-release
标签：<tag>
源码：<完整 commit SHA 的链接>
应用内部版本：<X.Y.Z>

### 变更

- 新增：<面向用户的变化，没有则省略>
- 修复：<问题及影响，可附 Issue/PR 链接>

### 下载与验证

| 平台 / 架构 | 安装包 | 签名 / 公证 | 验证范围与结果 |
| --- | --- | --- | --- |
| <目标平台> | <资产链接> | <实际状态> | <源码 / 桌面 E2E / 安装 / 升级> |

未提供或未验证的平台：<如实列出>
完整校验值：SHA256SUMS；构建来源：BUILD-INFO.json。

### 升级与兼容性

<升级方法、数据迁移、备份要求和回退限制；没有自动更新时明确说明>

### 已知问题

<未签名、失败或跳过的检查、已知依赖风险等，不适用时写无已知问题>

完整源码变更：<上一标签与当前标签的 compare 链接>
```

## 验证数据

可执行回归、Golden 任务定义与必要的结构化样例位于 `tests/`。`tests/v2/golden/regression-map.json` 指向实际回归入口，不代表这些测试已在某次发布中运行成功。

新生成的报告与截图写入忽略的 `artifacts/`。公开仓库保留源码与必要测试夹具，不保存按任务积累的报告或演示文件。归档构建日志时应脱敏，并记录实际执行的平台和提交。
