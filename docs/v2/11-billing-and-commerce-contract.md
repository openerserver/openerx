# V1 个人额度、计费与账单合同

> 状态：`APPROVED_PRODUCT_SCOPE / IMPLEMENTATION_IN_PROGRESS / OPERATIONAL_CONFIG_PENDING`
>
> 合同类型：个人账户额度、费用、积分、充值、支付、账单与对账边界

## 1. 已确定范围

`已确定`：OpenerX V1 在 Token 使用记录之外，必须提供个人账户的额度、费用、积分、充值和账单能力。这些能力不是 Future Enterprise 功能，也不能用静态演示页或人工改库代替。

V1 必须形成以下闭环：

1. 用户在使用前看见模型或收费工具的计价方式。
2. 系统在执行前校验可用额度，并为本次请求预留最大可扣金额。
3. 执行后依据真实 Token、实际模型和当时生效的价格快照计算费用。
4. 费用按已批准的抵扣顺序从额度、积分和充值余额中结算。
5. 用户可以充值、查看支付状态、余额变化、消费明细和月度账单。
6. 重试、回调重放、同步恢复和服务重启都不能重复扣费或重复入账。
7. 失败、停止、退款和人工调账都有可追溯的冲正记录，不能直接修改已入账流水。

## 2. 用户术语

| 名称 | 用户能理解的含义 | 核心边界 |
| --- | --- | --- |
| Token | 模型实际处理的输入和输出数量 | 是用量，不直接等于金额 |
| 额度 | 平台赠送或套餐包含的可抵扣费用上限 | 不是现金，不可提现，可按规则失效或重置 |
| 积分 | 活动、补偿或奖励获得的抵扣单位 | 不是现金，兑换比例和有效期必须可见 |
| 充值余额 | 用户实际支付后进入账户的可用金额 | 与额度、积分分开显示和记账 |
| 费用 | 一次模型或明确标价工具执行产生的实际应付金额 | 必须关联用量、价格快照和扣减明细 |
| 账单 | 消费、充值、退款、冲正和调账的账户记录 | 账单不等同于税务发票 |

界面不得把额度、积分和充值余额合并成一个无法解释的数字。总可用价值可以汇总显示，但必须能展开查看各组成和有效期。

## 3. 已确认商业规则与运营参数

用户已经同意以下商业方案。积分兑换具体数字、充值档位上下限和支付商户参数属于发布前运营配置，不改变产品范围：

| 决策 | 已确认规则 | 状态 |
| --- | --- | --- |
| 结算币种 | 中国大陆个人用户使用人民币 `CNY`，金额以分为最小存储单位 | 已确认 |
| 额度单位 | 以可抵扣人民币金额表示，不以 Token 数表示 | 已确认 |
| 积分兑换比例 | 使用版本化规则配置，不在代码中写死；Billing Alpha 前配置具体比例 | 机制已确认，数值为运营参数 |
| 扣减顺序 | 优先使用最早到期的额度，再使用最早到期积分，最后使用充值余额 | 已确认 |
| 透支 | 不允许负余额；不足时在执行前提示充值、换模型或降低本次上限 | 已确认 |
| 低余额提醒 | 可用价值低于最近 7 日平均消耗的 2 倍或用户自定阈值时提醒 | 已确认 |
| 充值金额 | 提供固定档位和合规范围内的自定义金额，最小/最大值由支付渠道配置 | 已确认，数值为运营参数 |
| 支付渠道 | V1 同时支持支付宝和微信支付 | 已确认，商户参数为运营配置 |
| 充值退款 | 支付失败自动关闭；重复支付、系统差错和批准退款走原路退回及账本冲正 | 已确认 |
| 积分有效期 | 每笔发放单独声明；没有声明则长期有效，不静默过期 | 已确认 |
| 税务发票 | 账单与税务发票分开；V1 不提供发票申请 | 已确认 |
| 订阅套餐 | V1 只做充值和按量结算，不做订阅/月卡 | 已确认 |

所有费率、兑换比例、有效期和扣减顺序都必须版本化，并记录生效时间；规则变更不得追溯修改已完成账单。

## 4. 价格与费用合同

### 4.1 价格目录

每个可收费项目使用 `PriceCatalogEntry`，至少包含：

- `priceRef`、版本和生效区间。
- 关联模型或平台收费工具。
- 币种、计价单位和整数/高精度单价。
- 输入、缓存输入、输出、推理 Token 的独立价格；不适用项明确为零或不计费。
- 最低费用、免费量、折扣和封顶规则；没有时明确为空。
- 用户可见说明和税费口径。

本地文件操作、Shell、用户自有 MCP 以及其他默认免费能力不得因为“有 UsageRecord”而自动收费。任何收费工具必须先进入价格目录并在执行前明确显示。

### 4.2 报价与价格快照

- 模型选择器显示当前单位价格；“自动”模型显示可能使用的价格范围或最大费率。
- 首次收费前显示收费、退款和余额规则，并记录用户明确接受的条款版本；条款实质变化后重新确认。
- 执行前生成 `PriceQuote`，至少包含预计范围、最大可扣金额、币种、价格版本、收费条款版本和过期时间。
- 手机 Remote 发起、Steer 或 Queue 的收费工作使用与桌面相同的报价、预留、幂等和结算链路；Remote Command/Relay 回执不能作为收费授权或生成第二笔预留。
- 在已接受条款且报价不超过用户单次上限时，用户发送消息表示授权当次可见报价；超过上限必须再次明确确认。
- 执行授权后冻结 `PricingSnapshot`。即使运行期间目录价格变化，本次结算仍使用冻结版本。
- 上游没有返回完整 Token 时，不能凭空估算为最终费用；进入待核算状态并按明确补记规则处理。

### 4.3 实际费用

`ChargeRecord` 至少包含：

- `chargeId`、`accountId`、`usageId`、可选 `messageId/runId/toolCallId`。
- 选择模型、实际模型、价格目录版本和 `pricingSnapshotId`。
- 原始 Token/计量值、计费数量、舍入前结果和最终整数金额。
- 原价、折扣、额度抵扣、积分抵扣、充值余额扣减和最终应付。
- `pending`、`settled`、`reversed`、`refunded` 或 `disputed` 状态。
- 稳定 `dedupeKey`、创建时间、结算时间和冲正引用。

舍入只能在合同规定的最终层级执行；聚合账单必须由逐笔已结算费用求和，不能重新用汇总 Token 计算。

## 5. 额度、积分与余额

### 5.1 额度

`QuotaGrant` 表示平台提供的可抵扣额度，记录来源、面额、剩余值、生效时间、过期时间、适用模型/工具范围和发放原因。周期额度重置时创建新 Grant，不覆盖旧记录。

### 5.2 积分

`PointGrant` 使用整数积分，记录来源、剩余积分、兑换规则版本、适用范围和有效期。积分扣减遵循已批准顺序；过期前提供可见提醒，过期形成独立账本事件。

积分不得宣传为现金，不可直接提现，也不能在没有明确规则时与充值余额混用。

### 5.3 充值余额

`CashBalanceAccount` 按币种隔离。余额只由已确认支付、退款、消费、冲正或有权限的人工调账改变；桌面/手机客户端、Remote Relay、同步队列和 Pi Host 均无权直接写余额。

所有金额使用币种最小单位整数存储，禁止使用二进制浮点数保存货币。

## 6. 费用预留与结算流程

一次收费执行遵循：

```text
quote_created
  -> funds_reserved
  -> execution_started
  -> usage_recorded
  -> charge_settled
  -> unused_reservation_released
```

异常分支：

```text
quote_created -> insufficient_funds
funds_reserved -> execution_cancelled -> reservation_released
execution_started -> failed/stopped -> usage_recorded -> partial_charge_or_release
charge_settled -> reversed/refunded/disputed
```

合同要求：

- 预留金额不得大于报价中用户接受的最大金额。
- Gateway 必须把最大输出和收费工具使用控制在已预留范围内；V1 默认不允许透支。
- 停止或失败只结算实际产生且按规则可收费的用量，未使用预留立即释放。
- 同一个 `usageId` 最多产生一笔有效原始费用；更正通过冲正和新记录完成。
- 商业服务不可用时，不允许在无法验证余额的情况下继续产生新的收费请求；已有本地历史仍可读取。
- 免费模型或完全由额度覆盖的请求仍产生零现金扣款的费用记录，便于解释额度变化。

## 7. 充值与支付

### 7.1 充值订单

`RechargeOrder` 至少包含订单号、账户、金额、币种、支付渠道、状态、幂等键、创建/过期/支付时间和支付服务商引用。

状态机：

```text
created -> pending_payment -> paid -> credited
                         -> failed | expired | closed
paid/credited -> partially_refunded | refunded
```

用户关闭支付页面不代表支付失败；客户端返回页也不代表支付成功。只有经过签名验证并完成服务端查询/回调确认的支付结果可以入账。

### 7.2 支付边界

- Electron 客户端只请求充值订单并打开平台或支付服务商托管的安全收银台。
- 银行卡号、支付密码、短信验证码等支付凭证不得进入 Renderer、客户端日志或 OpenerX 数据库。
- 支付密钥和回调验签只在服务端进行。
- 回调必须验签、校验金额/币种/商户订单、拒绝重放并保持幂等。
- 支付成功后，充值订单、支付流水和余额入账必须在一个可恢复事务或 Saga 中完成。
- 页面轮询、深链接返回和服务端通知可以重复到达，但只能入账一次。

### 7.3 退款与差错

- 退款必须关联原支付和原充值入账，并使用独立退款单。
- 已消费部分不能通过直接删除充值流水处理。
- 系统重复扣费、错误价格或明确失败后的收费必须自动或人工批准后冲正。
- 每笔调账记录操作者/系统原因、关联证据、前后余额和审批引用。

## 8. 不可变账本与账单

### 8.1 账本

服务端使用追加式复式 `LedgerEntry` 记录额度、积分和现金价值变化，每个业务事务必须借贷平衡：

- 已入账记录不能更新金额或物理删除。
- 更正使用反向分录和新分录。
- 每个业务事务所有分录借贷平衡，并有唯一业务幂等键。
- 余额是账本投影，可重建；缓存余额不是最终真值。
- 额度、积分和现金使用不同账户科目，不能靠一个 `balance` 字段混算。

### 8.2 用户账单

账单页至少支持：

- 当前可用额度、积分、充值余额及即将过期项目。
- 按时间、模型、类型和状态筛选消费。
- 查看每笔费用的 Token、实际模型、单价版本、抵扣来源和最终金额。
- 查看充值、支付中、成功、失败、退款、冲正和人工调账。
- 按自然月生成不可变 `BillingStatement`，支持下载 CSV 和 PDF。
- 每条记录提供稳定编号，便于客服查询和争议处理。

月度账单生成后如发生退款或调账，不覆盖旧账单，而是在当前账期列出调整并关联原记录。

## 9. API 与事件

最低云 API：

```text
/api/v2/prices
/api/v2/billing/overview
/api/v2/billing/quotes
/api/v2/billing/charges
/api/v2/billing/ledger
/api/v2/billing/statements
/api/v2/billing/recharge-orders
/api/v2/billing/refunds
```

客户端只能通过业务 API 创建报价和充值订单；不能提交“新余额”或任意账本分录。

最低事件：

- `billing.quote_created`
- `billing.funds_reserved`
- `billing.charge_settled`
- `billing.reservation_released`
- `billing.charge_reversed`
- `billing.quota_granted`
- `billing.points_granted`
- `billing.points_expiring`
- `payment.order_created`
- `payment.succeeded`
- `payment.failed`
- `payment.refunded`
- `billing.statement_ready`

事件和 API 响应不得包含支付凭证；涉及余额的推送只提示客户端重新读取服务端快照。

## 10. 安全、隐私与合规边界

- 价格配置发布、人工调账、退款和积分/额度发放使用独立服务端权限和审计。
- 个人账户只能读取自己的余额、费用、订单和账单。
- 金融记录不得通过普通同步写 API 修改，也不得由本地缓存冲突覆盖。
- 支付页面使用受信任域名白名单；远程支付内容永远不获得 Electron Preload Bridge。
- 日志和诊断包屏蔽支付凭证、完整回调载荷、账户令牌和个人金融信息。
- Webhook 采用签名验证、时间窗、防重放和来源校验；密钥定期轮换。
- 充值、退款、支付渠道、税费、实名和记录保留必须在上线地区完成法律、税务和支付合规审查。
- 账户删除不能非法删除必须保留的交易记录；产品必须解释保留范围，并在允许时去标识化。

该合同不声称产品已经满足任何具体支付牌照、税务或数据法规；正式上线前必须由负责主体和支付服务商完成属地确认。

## 11. 对账与运营

- 每日核对支付服务商成功金额、充值订单、支付流水和现金账本入账。
- 每日核对 UsageRecord、ChargeRecord、预留释放和账本扣减。
- 差异进入隔离队列，不通过自动改余额“抹平”。
- 对账任务可重跑，输出稳定差异 ID、原因、金额和处置状态。
- 运营人员需要最小化的服务端客服工具处理订单查询、退款和调账；它不是面向 V1 普通用户的企业管理员控制台。
- 价格、积分规则和额度发放配置必须经过发布审计和回滚演练。

## 12. 数据保留和导出

- Token 与费用明细、充值订单、退款和账本记录按法律及财务要求保留，不能随对话删除而消失。
- Message 删除后，费用记录保留最小必要业务引用和金额证据，不继续暴露已删除内容正文。
- 用户数据导出包含可读的用量、消费、充值和退款记录，但不包含内部支付密钥、风控信号或其他账户信息。
- 本地只保存只读展示缓存；退出账户或清理缓存可删除本地副本，不影响云端账本。

## 13. V1 发布硬门禁

以下任一失败都阻断发布：

- 同一用量、订单、支付回调或同步重放造成重复扣费/入账。
- 价格变更追溯影响已完成费用，或账单无法还原所用价格快照。
- 余额、额度或积分出现无账本分录的变化。
- 已入账记录可被更新或删除，而不是冲正。
- 费用超过用户接受的最大金额或账户被静默透支。
- 支付成功但未入账、支付失败却入账，且自动对账无法发现。
- 不同账户可以读取或操作彼此的报价、订单、余额、费用或账单。
- Renderer、Pi Host、同步客户端或模型可以直接修改余额/账本。
- 支付凭证、支付密钥或完整敏感回调进入客户端、消息或诊断日志。
- 退款、调账和积分/额度发放没有原因、权限与审计记录。

## 14. V1 非目标

- 组织预算中心、部门成本分摊和管理员代付。
- 企业采购合同、授信账期和线下银行转账自动核销。
- 多币种钱包和跨境结算，除非商业规则阶段明确加入。
- 积分转赠、交易、提现或兑换现金。
- 加密货币支付。
- 税务发票平台和订阅套餐。

这些非目标不削弱个人账户额度、费用、积分、充值和账单的 V1 必做范围。
