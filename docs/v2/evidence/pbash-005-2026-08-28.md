# PBASH-005 Remote、审批与幂等本机证据（2026-08-28）

## 结论

状态为 `LOCAL COMPLETE / REAL REMOTE COMMAND PATH / RELEASE MATRIX PENDING`。

本检查点复用既有 mobile control plane → ciphertext-only Gateway/Relay → outbound Desktop Connector →
App Service → Pi Host / Capability Broker 链路，不创建第二套 Agent Loop。Remote 发起的 Bash 与本地请求
进入同一 Broker、ToolCall、PermissionRequest、Runner 和 WorkspaceChangeSet 状态机。

它不代表 iOS/Android 真机密钥链、生物识别、QR、生产 HTTPS/WSS/APNs/FCM、签名安装包、网络切换或
主机重启故障演练已经完成。

## 执行来源与不可扩权合同

1. Remote prompt payload 显式区分 `attended / unattended`。移动端现有会话“发送”使用 attended，新任务
   使用 unattended；旧客户端省略时按 unattended 处理。
2. App Service 把来源转换为隐藏的 `executionOrigin` 并冻结到 Generation。Pi 模型参数仍只有
   `command + timeout`，不能提交或改写 origin、WorkspaceGrant、profile 或 policy。
3. `remote_unattended + workspace_write` 在严格 schema 中只能使用 `isolated_change_set`；后端不可用时
   fail-closed，不能直接写宿主工作区。
4. Remote execution context 强制 `environment-core-v1 + network-deny-v1`。Remote payload 没有活动
   Workspace、额外根和网络字段，多 Workspace 时仍需 Desktop 可信选择。
5. `executionOrigin` 进入 operation digest、Pi Host 回传匹配、ToolCall input 与公开执行结果；来源变化
   会使旧审批和旧幂等结果失效。

## 精确审批绑定

- attended Remote 的 `workspace_write` Bash 为 L3 per-call；unattended 命令只在 CoW 副本生成 change set，
  后续 apply/undo 仍为 L3 per-call。
- PermissionRequest 绑定原 generation 的 assistant message，并保存原
  `pairingId + controllerDeviceId + hostDeviceId`。其他控制器、重新配对控制器或本地 generation 不能通过
  Remote 命令解除等待。
- Remote response 同时校验 attention ID、permission ID、conversation、payload digest、设备解锁、60 秒内
  重认证；L5 继续要求生物识别且禁止 session approval。
- 审批只恢复同一 Pi ToolCall。任何 command、timeout、grant、origin、profile、network 或 sandbox policy
  字节变化都会产生新 digest。

## 至少一次投递、journal 与恢复

```text
Mobile signed command
  -> Gateway: commandId + pairing idempotencyKey + baseRevision + sequence + TTL
  -> Connector SQLite: accepted/applied/rejected receipt replay
  -> App Service RemoteRepository: command digest + durable result replay
  -> Capability Broker: operation digest + side-effect attempt/result journal
```

1. Gateway 同 command ID 或同 pairing idempotency key 只接受完全相同 envelope；内容替换稳定拒绝。
2. Connector 对 Relay 重投复用 durable receipt。App Service response 丢失时可重投同命令，已完成结果从
   `RemoteRepository` 回放，不创建第二个 Pi 调用或工具副作用。
3. SQLite v15 为 `tool_side_effects` 和 `tool_side_effect_attempts` 增加 `operation_digest`。同 idempotency key
   搭配不同 payload 返回 `SIDE_EFFECT_IDEMPOTENCY_CONFLICT`，不会错误回放旧结果。
4. App Service 进程重启后，未完成 Remote application 从 `applying` 转为 `outcome_unknown`。同命令再次
   到达时返回 `REMOTE_COMMAND_OUTCOME_UNKNOWN`，禁止盲目重跑。
5. Connector 将未知 Remote command 结果投影成端到端加密的 `review.available` reconciliation 事件。
   Tool side effect 与 WorkspaceChangeSet 的待审阅、blocked、apply-failed 和 outcome-unknown 状态使用同一
   受限元数据进入 Remote 收件箱，不包含恢复材料、原始输出或宿主路径。

## 负向验证

| 场景 | 结果 |
| --- | --- |
| unattended Remote 请求直接写 | 合同拒绝；只能 `isolated_change_set` |
| Remote 请求非 deny network policy | 合同拒绝 |
| attended Remote 写 Bash | 进入 L3 per-call，Pi 调用保持等待 |
| 同会话但不同 controller 回应审批 | `REMOTE_PERMISSION_CONTROLLER_MISMATCH`；Permission 仍 pending |
| 正确 controller + 原 payload digest | 恢复原 Pi ToolCall，不新建调用 |
| 完成 idempotency key 下替换 payload | `SIDE_EFFECT_IDEMPOTENCY_CONFLICT`；adapter 只执行一次 |
| Remote application 在完成前崩溃 | 重启标记 `outcome_unknown`；重投不执行 |
| Relay 重投同 Remote command | Connector/App Service 回放结果或 receipt，不重复副作用 |
| 对账事件 | 按 pairing 单独加密；仅含 kind、targetId、status、actionRequired |
