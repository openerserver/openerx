## Security and update proof

The desktop release package validates a strict, signed manifest before configuring the native updater.
The validated fields bind key ID, release channel, version, exact platform/architecture, immutable
artifact facts and deterministic rollout eligibility. Tampering, the wrong key ID, a wrong channel, a
future timestamp, a missing target or an oversized manifest fails closed.

Release configuration is generated inside the packaged ASAR. Only Electron Main reads it. The typed
Bridge returns update state, versions, channel, progress and normalized error codes; the Renderer has no
feed URL, manifest URL or signing-key field. Local packages have updates explicitly disabled.

An ephemeral Ed25519 keypair exercised the CLI against
`docs/v2/release/release-manifest.example.json`:

```text
[m9-release-manifest] SIGNED version=2.0.0 channel=stable targets=3
[m9-release-manifest] VERIFIED version=2.0.0 channel=stable targets=3
```

Cross-packaging proves package shape, ASAR boundaries and Fuses, not native execution or publisher
identity. The native verifier correctly labels these outputs `LOCAL UNSIGNED`. Windows Authenticode,
macOS Developer ID/notarization and install/upgrade/rollback must run on protected native runners.

Expo dynamic configuration was evaluated in both modes. Local mode disables updates. A release-mode
configuration with a valid project ID produced `https://u.expo.dev/<project-id>` and
`runtimeVersion.policy=appVersion`; release mode without a project ID fails closed. iOS and Android
exports also completed. Store credentials, physical-device installation, APNs/FCM and withdrawal remain
external.
