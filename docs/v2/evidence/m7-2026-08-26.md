## Runtime boundary

Pi's native `DefaultResourceLoader` is the only Skill discovery mechanism. Enabled package mounts are
resolved by App Service for each generation. Auto-invocable Skills contribute only name, description and
location to Pi's system prompt; explicit composer selection rewrites only the private Pi frame as
`/skill:name` while the durable user Message remains unchanged. Pi performs its native expansion and
continues the same AgentSession.

References and text assets are read by a custom tool named `read`, but the tool converts an allowed
absolute mounted path to installation ID plus relative path before leaving Pi Host. Scripts use
`openerx_skill_script`. Both operations enter the same Capability Broker and durable WorkItem/Run/Step/
ToolCall projection as M5 tools. L5 script execution remains exact-payload, per-call approval.
Storage migration v9 extends the existing strict ToolCall and policy vocabulary with the `skill` source,
capability and resource type; a repository regression proves those rows can be persisted before E2E.

The package store uses immutable version directories and checksums under the private profile. Directory
copy and ZIP extraction reject path traversal, package symlinks, file/byte limits and undeclared script
paths. Permission expansion clears approval and disables the package. Failed database installation
removes the newly staged version; uninstall uses a recoverable profile trash. Package corruption marks
only that installation damaged and retries Scope resolution, so chat and lower-priority packages remain
available.

## Sync and privacy boundary

Skill installation records share the account sync outbox and conflict boundary. The payload includes
selected version/checksum, source label, declarations and non-sensitive settings. It excludes local
package paths and approved permission digests. A receiving device without local content records the Skill
as missing, disabled and unapproved. Renderer sees typed lifecycle metadata but never receives package
paths, raw IPC, filesystem APIs or credentials.

## Evidence boundary and remaining release gates

This is a deterministic local macOS implementation checkpoint. It does not claim signed publisher/
catalog distribution, native Windows execution, signed macOS x64/arm64 packages or arbitrary
third-party script compatibility. Local installs are deliberately marked unverified; platform catalog
records exist in the contract but catalog download/signature transport remains a release service gate.

JavaScript Skill scripts currently call the host `node` executable. The local gate used Node 24.2.0;
release packages must bundle and sign a compatible runtime or replace this dependency, and must prove
sandbox/network behavior on Windows and both macOS architectures. These release gates do not change the
M7 process, package, Broker, sync or UI boundaries proven here.
