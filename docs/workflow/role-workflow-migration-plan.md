# 角色工作流数据迁移计划

> 适用范围：OpenerX 角色注册表、工作流模板、阶段状态机、角色聚合与开发者修正请求
>
> 目标：定义新增表的两批落地顺序，明确每一批改什么、不改什么，以及如何与现有 `tasks.strategy` JSON 兼容

## 1. 迁移目标

本计划解决两个问题：

1. 不把所有新表一次性压进当前控制平面，降低改造风险。
2. 让主数据、运行态、聚合结果按稳定性分批落地。

## 2. 迁移原则

### 2.1 主数据优先落表

角色和模板属于长期主数据，应先入库。

### 2.2 运行态分批落地

阶段运行、聚合结论和修正请求先允许 BFF 用 `tasks.strategy` JSON 兼容，再逐步迁移到正式表。

### 2.3 保持旧任务可读

没有角色工作流数据的历史任务应继续可读，不强制回填。

## 3. 第一批迁移

第一批建议新增以下表：

1. `role_agents`
2. `role_agent_bindings`
3. `workflow_templates`
4. `workflow_template_stages`

### 3.1 第一批目标

- 让角色注册表和模板摆脱 JSON 配置文件
- 为 BFF 聚合执行器提供稳定主数据源

### 3.2 第一批不做

- 不强制任务工作流运行入表
- 不强制聚合结论入表
- 不强制修正请求入表

### 3.3 第一批兼容策略

- `roleBindingResults`
- `roleAggregateConclusions`
- `developerChangeRequests`

仍可保存在 `tasks.strategy`

## 4. 第二批迁移

第二批建议新增以下表：

1. `task_workflow_runs`
2. `task_stage_runs`
3. `role_aggregate_conclusions`
4. `developer_change_requests`

### 4.1 第二批目标

- 让阶段状态机成为正式运行态对象
- 让角色结论和修正请求可查询、可审计、可统计

### 4.2 第二批兼容策略

- 原始 binding 结果仍可继续暂存在 `tasks.strategy`
- 正式表优先作为前端和管理页读取来源

## 5. 推荐执行顺序

1. 先发第一批 schema 和管理类 routes。
2. 再接 BFF 到数据库主数据源。
3. 然后发第二批 schema 和任务运行态 routes。
4. 最后把前端切到正式读模型。

## 6. 回滚策略

### 6.1 第一批回滚

- 即使角色/模板表已创建，也不影响现有任务主路径
- 可以回退到仅使用现有 JSON 配置

### 6.2 第二批回滚

- 若正式表写入异常，BFF 可继续退回 `tasks.strategy` 兼容模式

## 7. 验收标准

1. 第一批上线后，角色与模板主数据可独立管理。
2. 第二批上线后，任务阶段、角色结论和修正请求具备正式持久化结构。
3. 任一阶段失败时，都可以退回 JSON 兼容读取，不阻断现有任务核心执行。
