# OpenerX 工作流模板灵活化方案

## 1. 文档目的

本文档用于规划 OpenerX 编排策略中“工作流模板”能力的增强方向，目标是让模板从“按分类选一个固定执行模式”演进为“可按规则决策、可解释、可人工覆盖、可灰度发布的执行策略单元”。

本文重点回答四个问题：

- 当前模板机制的主要限制是什么
- 更灵活的模板体系应具备哪些能力
- 应该按什么顺序演进，才能控制实现风险
- 每个阶段的交付结果和验收标准是什么

## 2. 当前机制与问题概述

当前实现中，工作流模板的核心职责是决定任务执行模式与候选 Agent 列表。

现状特征：

- 模板在任务开始执行时参与决策，而不是在配置保存时即时生效
- 模板匹配主要依赖意图分类 category
- 如果存在多个模板，系统只会选中一个模板，不会组合使用多个模板
- 当多个模板同时满足条件时，本质上由模板顺序决定命中结果
- 任务执行开始后，会将选中的模板和执行模式写入任务快照

现有机制能够支撑基础单执行和并行竞争，但存在明显限制：

- 匹配维度过少，只能按分类进行粗粒度选择
- 优先级隐含在数组顺序中，缺乏显式治理能力
- 无法解释“为什么命中这个模板而不是另一个模板”
- 无法对特殊仓库、特殊项目、特殊复杂度任务做更细粒度控制
- 无法支持任务级人工指定模板
- 缺少灰度能力，新增模板容易直接影响线上行为

## 3. 目标

工作流模板灵活化后的目标如下：

- 模板可按多维条件匹配，而不是只按分类匹配
- 模板选择具备显式优先级与可预测的回退机制
- 模板决策结果可解释、可审计、可回放
- 用户或管理员可以在任务级覆盖自动决策结果
- 新模板可以灰度启用，而不是一次性全量生效
- 保持对当前模板数据结构和已有行为的兼容，降低迁移成本

## 4. 总体设计思路

建议将工作流模板从“配置片段”升级为“策略对象”。

每个模板不再只表达“single 或 parallel”，而是同时表达以下信息：

- 该模板适用于什么场景
- 该模板的优先级和生效边界是什么
- 如果命中多个模板，应如何决策
- 如果没有命中模板，应如何回退
- 该模板是否允许人工显式选择
- 该模板是否处于灰度发布范围内

整体上采用三层结构：

1. 模板定义层：描述模板本身的执行能力与适用条件。
2. 模板决策层：负责按上下文计算匹配结果并选出最终模板。
3. 模板观测层：负责记录命中原因、回退原因、版本信息和审计信息。

## 5. 建议的数据模型增强

### 5.1 模板元数据

建议在现有模板结构基础上增加以下字段：

- priority：模板优先级，数字越大优先级越高
- version：模板版本号，用于追踪配置演进
- manualSelectable：是否允许在任务级手工指定
- owner：模板责任人或责任团队
- selectionHint：供前端展示的说明文本

### 5.2 匹配条件

建议新增 match 字段，将模板适用条件统一收敛到一个对象内。

建议支持的条件包括：

- categories：适用的意图分类列表
- complexities：适用的复杂度等级列表
- requiresPlan：是否要求规划阶段
- projectIds：限定项目范围
- repoIds：限定仓库范围
- tags：限定任务标签
- keywords：基于 prompt 关键词命中
- modelFamilies：限定适配的模型族
- requireCredential：是否要求存在身份凭据

### 5.3 匹配模式

建议新增 matchMode 字段：

- all：所有条件都满足才命中
- any：任一条件满足即可命中
- score：每项条件有权重，按得分排序

在第一阶段可先实现 all 和 any，降低复杂度。

### 5.4 回退策略

建议新增 fallbackLevel 字段：

- strict：未精确命中则不使用该模板
- category：允许回退到同分类默认模板
- global：允许回退到全局默认模板

### 5.5 灰度配置

建议新增 rollout 字段：

- enabledProjects：仅对指定项目启用
- enabledUsers：仅对指定用户启用
- percentage：按比例放量
- observeOnly：只记录命中结果但不真正执行

## 6. 模板决策引擎方案

建议将当前的模板解析逻辑从简单线性查找升级为显式决策引擎。

输入上下文建议包括：

- 任务 prompt
- 意图分类结果
- 复杂度与 requiresPlan 判断结果
- 项目和仓库上下文
- 当前用户信息
- 当前策略配置版本
- 是否存在任务级人工指定模板

输出结果建议包括：

- selectedTemplateId：最终选中的模板
- selectedBy：命中来源，例如 manual、matched、fallback
- selectionReason：命中原因说明
- matchedTemplateIds：所有匹配模板列表
- rejectedTemplates：被淘汰模板及原因
- fallbackApplied：是否发生回退
- strategyVersion：决策使用的策略版本

建议决策流程如下：

1. 先处理任务级显式指定模板。
2. 过滤所有未启用模板和不在灰度范围内的模板。
3. 逐个计算模板命中结果。
4. 对命中模板按 priority、score 排序。
5. 选择第一名作为最终模板。
6. 若没有命中模板，则按 fallbackLevel 逐级回退。
7. 输出完整决策说明并写入任务快照。

## 7. 人工覆盖机制

要让模板使用更灵活，必须允许人工覆盖自动决策。

建议增加以下能力：

### 7.1 任务级手工指定模板

在任务创建页或执行前确认页增加“执行模板”可选项：

- 默认值为“自动选择”
- 管理员可显式选择某个 manualSelectable 的模板
- 任务一旦开始执行，模板选择即固化到任务快照中

### 7.2 项目级默认模板

允许某些项目设置默认模板偏好，用于覆盖通用分类决策。

适用场景：

- 核心仓库默认使用并行竞争模板
- 高风险项目默认启用带 pre-execution hook 的模板
- 成本敏感项目默认使用轻量单执行模板

### 7.3 管理员调试模式

为系统管理员提供“模拟命中”能力：

- 输入一段 prompt
- 选择项目、仓库、标签等上下文
- 返回命中的模板列表和最终命中原因

这样可以在不真正执行任务的情况下验证策略配置。

## 8. 可解释性与审计设计

模板机制一旦变复杂，可解释性就必须同步建设。

建议在任务 strategy 快照中新增以下字段：

- selectedTemplateId
- selectedTemplateVersion
- selectionReason
- selectedBy
- matchedTemplateIds
- fallbackApplied
- evaluationSummary

建议在日志或审计记录中保留：

- 模板决策时间
- 输入上下文摘要
- 模板排序结果
- 回退原因
- 是否为人工覆盖

这样后续可以回答以下问题：

- 为什么这个任务没有走并行模板
- 为什么某个模板近期命中率下降
- 某次故障是否由模板调整引起

## 9. 前端配置与交互建议

仅增强后端不够，前端配置体验也需要同步提升。

建议对“编排策略 > 工作流模板”配置区做以下增强：

- 模板列表展示 priority、适用范围摘要、是否允许手工指定
- 模板编辑器增加“适用条件”配置区，而不是只配 categoryDefaults
- 模板编辑器增加灰度配置区
- 模板编辑器增加“命中说明”字段
- 增加“模拟命中”面板，便于配置验证

建议的交互目标：

- 管理员能快速看出多个模板的优先级关系
- 管理员能明确知道模板适用哪些任务
- 管理员能在上线前验证模板是否会误伤现有任务

## 10. 分阶段实施方案

### 阶段一：显式优先级与兼容式扩展

目标：在不重写整套链路的前提下，先解决“顺序即逻辑”的问题。

任务清单：

- 为模板增加 priority 字段
- 保留 categoryDefaults 兼容旧逻辑
- 在模板选择逻辑中按 priority 排序，而不是按数组顺序命中
- 在任务快照中记录 selectedBy、selectionReason
- 补充模板选择单元测试

阶段结果：

- 模板优先级显式可控
- 同分类多个模板的行为更可预测
- 决策结果开始具备解释能力

### 阶段二：多维匹配与回退规则

目标：让模板可以按更多上下文维度命中。

任务清单：

- 引入 match、matchMode、fallbackLevel 字段
- 支持 categories、complexities、requiresPlan、projectIds 等条件
- 新增模板决策摘要对象
- 在任务执行快照中保留所有命中模板列表和回退原因
- 补充策略兼容迁移逻辑

阶段结果：

- 模板不再局限于粗粒度分类匹配
- 复杂任务和特殊项目可以使用不同模板
- 决策链路具备基础可回放能力

### 阶段三：人工覆盖与模拟命中

目标：让模板系统真正可运营，而不仅仅是自动逻辑。

任务清单：

- 支持任务级显式指定模板
- 支持项目级默认模板
- 增加前端“模拟命中”工具
- 增加模板责任人、说明信息
- 增加管理员调试视图

阶段结果：

- 管理员可以主动控制关键任务的模板选择
- 模板上线前可以验证，不再盲配
- 模板配置的维护成本下降

### 阶段四：灰度与实验能力

目标：降低新模板上线风险。

任务清单：

- 支持项目、用户、比例维度的灰度发布
- 支持 observeOnly 观察模式
- 增加模板命中率、执行成功率等基础统计
- 支持快速回滚到全局默认模板

阶段结果：

- 新模板可以渐进式投放
- 模板优化从“拍脑袋调配置”升级为“带观测的实验”

## 12. 风险与控制措施

主要风险包括：

- 模板规则变多后，配置复杂度上升
- 兼容旧配置时容易出现隐式行为变化
- 人工覆盖和自动决策可能出现优先级冲突
- 灰度规则设计不当可能导致行为难以预测

控制措施：

- 第一阶段只引入 priority，不立即引入过多匹配维度
- 所有新字段默认可选，保持旧配置继续可用
- 任何模板决策都输出可解释结果，避免黑盒行为
- 为模板决策增加覆盖性测试和回归测试

## 13. 验收标准

### 13.1 功能验收

- 支持多个模板同时启用且行为可预测
- 支持显式优先级配置
- 支持至少两种以上匹配条件
- 支持任务快照查看模板命中原因

### 13.2 可维护性验收

- 模板选择逻辑独立成清晰函数或模块
- 新旧配置兼容明确且有测试覆盖
- 前端能清楚展示模板适用范围和优先级

### 13.3 运维与治理验收

- 管理员能模拟模板命中结果
- 新模板可以灰度生效
- 模板决策结果可审计、可回放、可排障

## 14. 一页式结论

要让工作流模板使用得更加灵活，关键不是继续堆更多模板，而是把“模板”升级为“可被规则选择、可被人覆盖、可被系统解释、可被灰度治理的策略对象”。

建议的最优推进顺序是：

1. 先解决显式优先级问题。
2. 再引入多维匹配与回退机制。
3. 然后补齐人工覆盖与模拟命中能力。
4. 最后引入灰度与实验观测能力。

按这个顺序推进，可以在保持当前系统可运行和可兼容的前提下，逐步把工作流模板从“基础配置能力”升级为“真正可运营的编排策略能力”。
