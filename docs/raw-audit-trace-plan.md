# 原始审计流与可审核透明性方案

> 适用范围：OpenerX 控制平面、BFF、Web UI、组织化 Agent 治理链路、代码变更审计与审批场景
>
> 目标：在不公开内部推理和策略配方的前提下，向用户公开足够完整的原始事实流，建立可验证、可导出、可追责的审计透明体系

## 1. 文档目标

本文档回答以下问题：

- OpenerX 应该公开哪些“原始数据”来提升用户信任
- 哪些事实应该默认公开，哪些策略和配方不应公开
- 原始审计流的数据对象应该如何定义
- Web UI 上“原始审计流”页面应该如何组织信息
- 如何在信任、可审计性和核心护城河之间取得平衡

本文档是产品与方案设计文档，不是具体代码实现说明。

## 2. 背景与核心判断

当前 OpenerX 的产品方向不是“把模型当聊天工具展示给用户”，而是把系统建设为企业级 AI 研发控制平面。

因此，用户真正需要的不是看到一份润色后的总结，而是能够验证以下事实：

1. 系统实际收到了什么输入。
2. 系统向模型注入了什么上下文。
3. 模型实际返回了什么内容。
4. 系统调用了哪些工具、访问了哪些资源、改动了哪些文件。
5. 为什么会触发审批、阻断、升级或预算限制。
6. 最终结论和中间治理动作是否可回放、可追溯、可导出。

但与此同时，系统也不应默认公开以下内容：

1. 内部推理草稿。
2. 老板 Agent、治理引擎、风险引擎和聚合器的内部策略配方。
3. 提示词资产、加权逻辑、阈值矩阵和防滥用规则。

因此，本方案的核心判断是：

**OpenerX 应公开完整的“行为事实流”，而不是公开完整的“内部推理流”。**

换句话说：

- 用户应该可以审核系统做了什么。
- 用户不必默认看到系统在内部如何做判断。
- 用户应能根据原始事实自行还原过程。
- 平台不应主动暴露高价值的内部决策配方。

## 3. 方案目标

本方案目标如下：

1. 建立统一的原始审计流对象模型。
2. 让任务、审批、仓库、代码变更、治理事件可以统一进入同一条证据链。
3. 让用户和管理员可按权限查看原始事实流，而不是只看二次摘要。
4. 让原始审计流可以导出为审计包，支持争议处理、审计归档和安全复盘。
5. 让前端形成“证据流页面”，而不是继续把审计信息埋在日志和附属面板里。
6. 在透明度提高的同时，明确保护内部 Prompt、策略权重、聚合逻辑等核心资产。

## 4. 设计边界

### 4.1 目标边界

本方案新增的是以下四类能力：

- 原始事实事件采集
- 原始审计流统一建模
- 原始审计流页面展示与导出
- 公开事实 / 隐藏策略的产品边界定义

### 4.2 非目标边界

本方案明确不包括：

- 不公开 chain-of-thought 或内部推理草稿
- 不公开完整内部系统 Prompt 和经营 Prompt 配方
- 不公开风险评分公式、聚合加权公式和阈值矩阵
- 不把审计页做成普通聊天历史页
- 不以“全部公开”替代权限分层和脱敏机制

### 4.3 与现有系统边界的关系

仍遵守当前系统边界：

- 控制平面负责主数据、治理事实、审批、审计、预算与可导出的证据记录
- BFF 负责前端聚合、运行时适配、事实采集和展示模型整理
- Runtime 仍负责实际会话执行、消息处理和工具调用

也就是说：

- 审计流记录“发生了什么”
- 控制平面决定“这些事实如何持久化、如何开放、如何追责”
- 平台不会因为公开事实流而公开内部智能策略资产

## 5. 核心原则

### 5.1 公开行为事实，不公开内部思维

对用户默认开放的是行为证据：

- 输入
- 输出
- 工具调用
- 文件变更
- 治理命中
- 审批与升级动作

默认不开放的是：

- 推理草稿
- 决策配方
- 权重和阈值

### 5.2 公开原始数据，不替外部做高质量策略抽象

系统可以公开原始事件流和原始输出，但不应额外把内部治理逻辑解释成可直接复刻的结构化配方。

### 5.3 摘要视图不能替代证据视图

为了可用性，系统可以生成摘要；但为了信任，系统必须保留原始事实流，并允许用户回看原始证据。

### 5.4 审计流是证据链，不是聊天记录

页面和数据模型都必须围绕“证据链”设计：

- 谁发起
- 何时发生
- 做了什么
- 命中了什么规则
- 结果是什么

### 5.5 权限与脱敏是一等公民

原始审计流必须原生支持：

- `visibility`
- `redaction`
- 导出完整性校验
- 审计员与管理员的差异化查看权限

## 6. 原始审计流对象模型

建议将一次可导出的审计结果定义为 `AuditBundle`。

其核心组成如下：

1. `RunHeader`：一次执行的头信息。
2. `AuditEvent[]`：按时间顺序排列的原始事件流。
3. `ArtifactRef[]`：相关文件、diff、审批单、报告等证据引用。
4. `IntegrityInfo`：完整性校验信息。
5. `RedactionInfo`：脱敏信息。

### 6.1 顶层对象

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://openerx.dev/schema/audit-bundle.v0.1.json",
  "title": "AuditBundle",
  "type": "object",
  "required": ["bundleId", "version", "run", "events"],
  "properties": {
    "bundleId": { "type": "string" },
    "version": { "type": "string", "const": "0.1" },
    "exportedAt": { "type": "string", "format": "date-time" },
    "exportedBy": { "$ref": "#/$defs/ActorRef" },
    "run": { "$ref": "#/$defs/RunHeader" },
    "events": {
      "type": "array",
      "items": { "$ref": "#/$defs/AuditEvent" }
    },
    "artifacts": {
      "type": "array",
      "items": { "$ref": "#/$defs/ArtifactRef" },
      "default": []
    },
    "integrity": { "$ref": "#/$defs/IntegrityInfo" },
    "redaction": { "$ref": "#/$defs/RedactionInfo" }
  }
}
```

### 6.2 RunHeader

`RunHeader` 用于描述一次执行的基础身份信息。

建议字段：

- `runId`
- `taskId`
- `projectId`
- `orgId`
- `sessionId`
- `parentRunId`
- `triggerType`
- `status`
- `initiatedBy`
- `workspaceContext`
- `startedAt`
- `endedAt`

其中：

- `triggerType` 建议支持：`user-start`、`resume`、`retry`、`approval-resume`、`system-replan`
- `status` 建议支持：`running`、`succeeded`、`failed`、`blocked`、`waiting-approval`、`cancelled`

### 6.3 AuditEvent 统一事件模型

所有事件统一采用：

- `eventId`
- `runId`
- `seq`
- `ts`
- `eventType`
- `visibility`
- `actor`
- `payload`
- `tags`
- `relatedIds`

建议 `eventType` 先支持以下枚举：

- `input.received`
- `context.injected`
- `model.invoked`
- `model.output`
- `tool.before`
- `tool.after`
- `tool.error`
- `file.diff`
- `repo.change`
- `policy.hit`
- `budget.hit`
- `approval.requested`
- `approval.resolved`
- `escalation.created`
- `escalation.resolved`
- `role.started`
- `role.output`
- `role.conclusion`
- `role.conflict`
- `boss.decision`
- `run.finalized`

建议 `visibility` 支持：

- `user-visible`
- `admin-only`
- `auditor-only`

### 6.4 事件域拆分建议

建议将 `payload` 拆分为以下事件域：

1. `InputPayload`
2. `ContextPayload`
3. `ModelInvocationPayload`
4. `ModelOutputPayload`
5. `ToolPayload`
6. `FileChangePayload`
7. `GovernancePayload`
8. `RolePayload`
9. `FinalizationPayload`

## 8. 公开事实与隐藏策略的边界表

### 8.1 默认公开的事实

| 类别 | 具体内容 | 默认公开 | 公开范围 | 说明 |
| ------ | ---------- | ---------- | ---------- | ------ |
| 用户输入事实 | 用户原始问题、补充指令、审批备注 | 是 | 用户 / 管理员 | 这是审计起点 |
| 模型输出事实 | 模型原始输出、结构化结果、最终建议 | 是 | 用户 / 管理员 | 用户必须能审核原始结果 |
| 工具行为事实 | 调用了什么工具、何时调用、结果是什么 | 是 | 用户 / 管理员 | 这是“系统做了什么”的核心证据 |
| 文件变更事实 | 改了哪些文件、diff、hash、仓库和分支 | 是 | 项目成员 / 管理员 | 代码类任务必须公开到可审计粒度 |
| 治理命中事实 | 命中了哪条规则、为什么触发审批或阻断 | 是 | 用户 / 管理员 | 防止黑箱阻断 |
| 审批事实 | 谁申请、谁批准、谁拒绝、依据是什么 | 是 | 项目成员 / 管理员 / 审计员 | 属于治理证据 |
| 预算与成本事实 | token、调用次数、估算成本、预算命中结果 | 是 | 管理员，部分对用户可见 | 企业需要成本归因 |
| 角色结论事实 | 安全、测试、架构、老板 Agent 的最终结论 | 是 | 用户 / 管理员 | 组织化协作必须可见 |
| 上下文来源事实 | 用了哪些文档、仓库、模板、历史记录 | 是 | 用户 / 管理员 | 让用户知道证据从哪来 |
| 原始事件时间线 | 所有事件的顺序和时间戳 | 是 | 用户 / 管理员 | 支持回放和争议处理 |

### 8.2 默认不公开的策略与配方

| 类别 | 具体内容 | 默认不公开 | 可开放条件 | 说明 |
| ------ | ---------- | ------------ | ------------ | ------ |
| 内部推理过程 | chain-of-thought、内部草稿和推演过程 | 是 | 不建议开放 | 噪音高、泄露机制、价值低 |
| Prompt 配方 | 完整 system prompt、经营 prompt、裁决 prompt | 是 | 合同约定或源码审阅 | 属于核心知识资产 |
| 策略权重 | 风险打分、阈值、优先级矩阵 | 是 | 仅公开摘要，不给完整公式 | 属于治理引擎核心资产 |
| 聚合算法细节 | 多角色如何投票、如何冲突消解、如何加权 | 是 | 不默认开放 | 应公开结论，不公开配方 |
| 反滥用规则 | 提示注入防御、异常识别、反刷策略 | 是 | 永不默认开放 | 公开后容易被绕过 |
| 敏感工具原始参数 | 密钥、令牌、内网地址、私有路径 | 是 | 仅审计员解封 | 安全要求 |
| 私有知识全文 | 专有 runbook、行业模板、客户制度全文 | 是 | 仅租户内部授权开放 | 可能属于平台或客户资产 |
| 老板经营逻辑 | 为什么选某模板和经营路径的完整内部逻辑 | 是 | 只公开摘要 | 属于产品差异化核心 |
| 风险模型训练资产 | 标注数据、规则来源库、经验模板包 | 是 | 不建议开放 | 属于长期护城河 |
| 异常处置剧本 | 降级逻辑、失败切换矩阵、兜底策略 | 是 | 仅安全 / 运维合同场景 | 会暴露系统弱点 |

### 8.3 一句话边界原则

可以公开的是：

- 行为事实
- 决策证据
- 原始时间线

不应默认公开的是：

- 内部思维
- 决策配方
- 反滥用和防绕过规则

## 9. 基于 Vue Flow 的项目任务总图页面重规划

### 9.1 目标纠偏

如果目标是“把一个项目的所有任务都在一张 Vue Flow 图上展示出来”，那么 Vue Flow 承载的就不应该是单任务审计流，而应该是：

**项目级任务总图。**

也就是说：

- 主画布展示的是项目中的所有任务。
- 每个主要节点代表一个任务，而不是一个审计事件。
- 原始审计流不再作为主画布主体，而是退回为“任务下钻能力”。

这意味着当前文档需要明确区分两个页面：

1. `项目任务总图`
  用 Vue Flow 展示项目内所有任务的全局关系。
2. `任务审计流`
  用于进入某个任务后查看该任务的执行证据。

### 9.2 页面定位

项目任务总图不是日志页，也不是多窗口监控台，而是“项目级任务全景图”。

建议命名：

- 中文：`项目任务总图`
- 英文：`Project Task Graph`

页面核心心智：

- 我不是来看单个任务细节。
- 我是来看这个项目里现在有哪些任务。
- 这些任务分别卡在哪个阶段、谁最重要、谁阻塞了谁、哪些需要我处理。

因此，页面主问题应该变成：

1. 这个项目当前有哪些任务。
2. 哪些任务正在运行、阻塞、失败、待审批或已完成。
3. 哪些任务之间存在真实依赖、阻断或派生关系。
4. 哪些任务属于同一阶段、同一工作流、同一仓库或同一关注域。
5. 从项目视角看，接下来最该关注什么。

### 9.3 与原始审计流的关系

原始审计流仍然重要，但位置变化如下：

1. 项目任务总图是项目级入口。
2. 任务详情页中的审计流是任务级下钻页。
3. 在项目任务总图中点击某个任务后，可以在右栏或跳转动作中进入该任务的审计流。

一句话边界：

**Vue Flow 主画布看任务，审计流看任务内部证据。**

### 9.4 入口设计

建议新增并统一以下入口：

1. 项目详情页中的 `任务总图` Tab。
2. 项目列表页中的 `查看任务总图` 快捷入口。
3. 多任务监控台中的 `切换到项目总图` 入口。
4. 项目编排页中的 `查看任务图谱` 入口。

建议路由形态：

1. `/projects/:projectId/task-graph`
2. 或在项目详情内部作为二级 Tab 挂载

### 9.5 页面总布局

考虑到项目里的任务可能很多、节点也可能较长，页面布局应明确采用“画布优先”原则，而不是传统三栏后台布局。

建议采用“顶部精简摘要 + 全宽 Vue Flow 画布 + 画布内浮层/抽屉”的结构。

1. 顶部：项目摘要、关键计数、布局模式、适配视图。
2. 中间：尽可能占满宽度的 Vue Flow 项目任务总图主画布。
3. 画布内左上：轻量控制浮层。
4. 画布内右侧：点击任务后出现的任务检查抽屉。

其目标是让用户同时完成：

- 全局盘点
- 结构理解
- 任务定位
- 快速处置

布局原则：

1. 默认状态下不常驻左侧大栏和右侧大栏。
2. 所有低频控制项都收进画布内可展开面板。
3. 右侧任务检查器只在选中任务或边时出现。
4. 关闭浮层后，画布应尽量接近全宽。

#### 9.5.1 页面草图

建议先按桌面端 1440 到 1600 宽度设计第一版，草图如下：

```text
+--------------------------------------------------------------------------------------+
| 顶部项目摘要条                                                                       |
| 项目名 | 任务总数 | 运行中 | 阻塞 | 待审批 | 今日失败 | 布局模式 | 适配视图 | 更多 |
+--------------------------------------------------------------------------------------+
| [左上控制浮层]                                                                    [X] |
| 布局 | 筛选 | 图层 | 图例 | 定位                                                   |
|                                                                                      |
|                    Vue Flow 项目任务总图全宽画布                                     |
|                                                                                      |
|   [阶段组] [阶段组] [阶段组] [完成区]                                                |
|      [Task A] -> [Task B] ----> [Task C]                                             |
|           \             \-> [Task D]                                                 |
|      [Task E]   [Task F]   [Task G]                                                  |
|                                                                 [右侧任务抽屉 按需出现] |
|                                                                 [概览][关系][审批]     |
|                                                                 [审计][更多]          |
+--------------------------------------------------------------------------------------+
```

建议宽度规则：

1. 默认画布宽度占可用主体宽度的 100%
2. 左上控制浮层展开时宽度不超过 280px
3. 右侧任务抽屉展开时宽度为 360 到 420px
4. 抽屉关闭后，画布立即回收空间

同时需要明确一条布局原则：

1. 不要为了在首屏塞下更多节点而持续缩小任务卡片。
2. 当任务很多时，优先让用户拖动画布、缩放画布和使用 minimap 定位。
3. 可视区域有限时，应允许节点超出首屏，而不是把节点压到不可读。

#### 9.5.2 顶部摘要条组件拆分

建议拆成四段，但总宽度尽量控制，不要把顶部做成第二条后台工具栏：

1. `项目身份区`
  显示项目名、组织、当前活跃环境或仓库范围。
2. `运行摘要区`
  显示任务总数、运行中、阻塞、待审批、今日失败。
3. `视图控制区`
  显示布局模式、显示层级、适配视图、刷新。
4. `操作区`
  默认只显示 `更多` 下拉，收纳新建任务、导出当前视图、进入监控台等次级动作。

建议精简原则：

1. 顶部只保留项目级关键指标
2. 把低频动作收到 `更多`
3. 不在顶部放长筛选表单
4. 筛选和图层控制回收到画布浮层中

### 9.6 Vue Flow 项目任务图建模

这张图要求“一个项目的所有任务都在一张 Vue Flow 图上”，因此数据建模必须围绕任务对象，而不是事件对象。

建议画布元素分为以下三类：

1. `Task Node`
2. `Task Edge`
3. `Group Node`

#### 9.6.1 主节点类型

建议主节点以任务为中心，首批支持以下类型：

1. `project-root`
  表示当前项目总入口，只出现一个。

2. `task-node`
  表示项目内一个真实任务，是主画布的核心节点。

3. `group-node`
  表示阶段组、状态组、负责人组或仓库组，不代表真实任务。

4. `approval-node`
  可选辅助节点，用于在开启审批图层时显示审批对象。

5. `milestone-node`
  可选辅助节点，用于展示关键阶段门槛，如发布、验证、上线。

首版原则：

- 画布的默认主要节点必须是任务节点。
- 审批、里程碑等辅助节点默认关闭，通过图层开关开启。

#### 9.6.2 边类型

建议只画“真实关系边”，不为了好看伪造连线。

首批边类型建议如下：

1. `depends-on`
  硬依赖边，表示任务 A 依赖任务 B 完成。

2. `blocks`
  阻断边，表示任务 A 当前阻塞了任务 B。

3. `informs`
  软关联边，表示任务 A 对任务 B 有信息输入关系，但不是硬依赖。

4. `spawned-from`
  派生边，表示任务 B 由任务 A 拆出、重试或分叉而来。

5. `approval-required`
  辅助边，表示某任务当前被某审批对象卡住。

如果当前后端拿不到项目级任务关系，则第一阶段应遵守：

- 不强画假关系边。
- 先用分组和布局表达结构。
- 只要有真实依赖数据，再补关系边。

#### 9.6.3 分组节点

为了让“所有任务都在一张图上”但不变成散点堆，建议使用 Group Node 承载结构分区。

建议至少支持以下分组方式：

1. 按状态分组
2. 按阶段分组
3. 按负责人分组
4. 按仓库或工作流分组

默认推荐：

1. 第一默认模式：按阶段分组
2. 第二默认模式：按状态分组
3. 其余模式通过画布左上浮层切换

### 9.7 画布主视图信息架构

中栏主画布的核心不是“事件关系图”，而是“任务全景图”。

#### 9.7.1 默认布局规则

建议默认采用横向阶段泳道布局：

1. 左到右表示任务推进方向或阶段推进方向。
2. 每一列或每一组对应一个阶段，例如 `intake`、`clarify`、`design`、`implement`、`verify`、`release`。
3. 同一阶段内任务按优先级或最近活动时间排列。
4. 已完成任务进入最右侧或底部弱化区。

当某个阶段内任务数量过多时，建议引入“前 N 个展开，其余折叠入组节点”的规则：

1. 单个阶段任务数 `<= 6` 时：全部展开。
2. 单个阶段任务数在 `7 - 12` 时：默认展开前 `6` 个任务，其余收进一个 `+N 更多任务` 组节点。
3. 单个阶段任务数在 `13 - 24` 时：默认展开前 `8` 个任务，其余收进一个或多个组节点。
4. 单个阶段任务数 `> 24` 时：默认只展开前 `10` 个任务，其余按状态或优先级拆成多个组节点。

这里的“前 N 个”建议按以下优先级排序决定：

1. 阻塞任务
2. 待审批任务
3. 运行中任务
4. 最新失败任务
5. 最近活动时间最新的任务
6. 其余普通任务

组节点建议命名示例：

1. `+5 个运行中任务`
2. `+8 个已完成任务`
3. `+12 个低优先级任务`

点击组节点后的行为建议：

1. 第一层点击：在原地展开组内任务
2. 第二层点击：在右侧抽屉显示该组任务列表
3. 提供 `仅看本组` 与 `展开全部` 两个动作

当用户切换布局模式时，支持以下模式：

1. `按阶段`
2. `按状态`
3. `按负责人`
4. `按最近活动`
5. `自由布局`

#### 9.7.2 任务节点卡片展示规则

每个任务节点应直接回答“这个任务值不值得我现在点开”。

建议统一包含，但默认只保留最必要的信息：

1. 任务标题
2. 任务状态 pill
3. 当前阶段
4. 最近活动时间
5. 风险 / 待审批 / 阻塞中的高优先级标签

建议移除或默认隐藏的内容：

1. 负责人或主责角色
2. 仓库或分支摘要
3. 评论数、变更数、审批数、告警数等计数区
4. 长摘要正文

这些信息保留到右侧任务抽屉中，默认节点只负责快速判断，不负责替代任务详情页。

#### 9.7.3 节点外观基础规格

建议所有任务节点遵循统一规格，并以可读性优先：

1. 圆角：14px
2. 默认宽度：300px
3. 最小宽度：280px
4. 默认高度：116px
5. 展开高度：148px
6. 常态边框：1px
7. 选中边框：2px
8. 阴影：仅 hover 或选中时增强

额外约束：

1. 不应提供低于 280px 的任务卡片宽度。
2. 不应因为任务数量增多而自动降到 240px 甚至更小。
3. 当任务很多时，首选方案是增加画布可滚动/可拖动范围，而不是压缩节点。

建议节点内部结构固定为三层，不再默认显示五层信息：

1. `头部`
  标题 + 状态 pill
2. `元信息行`
  阶段 + 最近活动
3. `标签区`
  风险、审批、阻塞、异常中的高优先级标签

展开态才显示：

1. 一句话摘要
2. 负责人
3. 仓库或分支信息

#### 9.7.4 各类节点草图说明

1. `project-root`
  形态：顶部或左上单一入口卡
  内容：项目名、任务总数、活跃任务数、负责人分布摘要

2. `task-node`
  形态：标准主卡片
  内容：任务标题、状态、阶段、最近活动、风险标签

3. `group-node`
  形态：半透明泳道容器或分区底板
  内容：分组标题、数量、说明文案

4. `approval-node`
  形态：小型警示卡或挂件节点
  内容：审批状态、审批级别、等待时长

5. `milestone-node`
  形态：钻石形或强调块
  内容：关键阶段门槛名，例如 `Ready for Release`

#### 9.7.5 节点颜色与语义映射

建议颜色先按任务状态映射，再叠加阶段信息，不要按项目里不同任务随机配色。

状态色建议：

1. `running`
  背景：#EEF6FF
  边框：#69A0FF
2. `blocked`
  背景：#FFF1EC
  边框：#F08A63
3. `waiting-approval`
  背景：#FFF7E8
  边框：#E8B04B
4. `failed`
  背景：#FFF0F0
  边框：#DE6B6B
5. `paused`
  背景：#F6F3FF
  边框：#A58AE6
6. `completed`
  背景：#F1F6F3
  边框：#6EAF86

阶段信息建议不要再改整张卡底色，而是放到：

1. 顶部阶段条
2. 阶段标签
3. 分组底板标题

#### 9.7.6 边的视觉语义与着色

边必须直接表达任务关系，而不是只是排版辅助线。

建议规则：

1. `depends-on`
  颜色：深蓝灰
  线型：实线
  箭头：实心
2. `blocks`
  颜色：橙红
  线型：较粗实线
  箭头：实心
3. `informs`
  颜色：中性灰蓝
  线型：虚线
  箭头：空心
4. `spawned-from`
  颜色：紫蓝
  线型：点划线
  箭头：实心但较小
5. `approval-required`
  颜色：琥珀色
  线型：虚线
  箭头：菱形或空心箭头

边的交互规则建议：

1. hover 边时，高亮起点与终点任务
2. 选中边时，右栏显示该关系说明
3. 在“只看主链路”模式下，隐藏 `informs` 与低权重辅助边

#### 9.7.7 选中、悬停与邻居高亮

建议定义明确反馈：

1. 悬停任务节点
  边框加深，阴影增强，对应关联边高亮
2. 选中任务节点
  节点抬升一层，右栏切换到该任务检查器
3. 聚焦当前任务
  非邻居任务降到 40% 不透明度
4. 查看上下游
  仅保留当前任务的一度或二度邻居

#### 9.7.8 画布控制器布局

建议固定如下：

1. 左上：轻量控制浮层入口
  默认只显示 4 到 5 个按钮：`布局`、`筛选`、`图层`、`图例`、`定位`
2. 左上浮层展开后：以 popover 或 drawer-in-canvas 方式出现，不挤压页面外层布局
3. 右上：`适配视图`、`只看主链路`、`显示全部任务`、`重置布局`
4. 右下：Vue Flow Controls
5. 左下：Minimap 或项目缩略图开关

建议明确：

1. 左侧控制区可以直接放进 Vue Flow 画布里
2. 它默认不展开，只在点击时出现
3. 展开后也应是轻量面板，而不是整列常驻侧栏

同时需要补充导航规则：

1. 画布默认允许拖动平移
2. 鼠标滚轮或触控板支持缩放
3. minimap 默认可见或一键开启
4. `适配视图` 只负责快速回到全局视角，不负责把所有节点压缩到过小
5. 当节点超出首屏时，预期交互就是用户自己拖动画布去查看

### 9.8 左栏控制区信息架构

为了尽量增大画布面积，原“左栏控制区”不建议做成页面常驻侧栏，而建议改成“画布内左上控制浮层”。

建议模块仍然保留，但表现形式改为分组弹出层：

1. `项目概览卡`
2. `布局模式卡`
3. `任务筛选卡`
4. `图层开关卡`
5. `图例卡`
6. `快速定位卡`

默认状态下：

1. 只显示五个入口按钮
2. 不显示完整卡片内容
3. 点击对应入口后，在画布内弹出相应面板

建议优先级：

1. 高频：布局模式、筛选、快速定位
2. 中频：图层开关
3. 低频：项目概览、图例

#### 9.8.1 项目概览卡

建议展示：

- 项目名
- 项目任务总数
- 运行中数量
- 阻塞数量
- 待审批数量
- 已完成数量
- 今日失败数量

#### 9.8.2 布局模式卡

建议支持：

- 按阶段
- 按状态
- 按负责人
- 按最近活动
- 自由布局

#### 9.8.3 任务筛选卡

建议支持以下筛选项：

- 任务标题搜索
- 状态
- 当前阶段
- 负责人
- 是否只看高风险
- 是否只看待审批
- 是否只看运行中
- 是否只看有关系边的任务

#### 9.8.4 图层开关卡

建议支持：

- 任务主节点
- 审批辅助节点
- 里程碑节点
- 关系边
- 软关联边
- 分组底板

#### 9.8.5 图例卡

图例必须明确说明：

- 各状态颜色含义
- 各边颜色含义
- 辅助节点代表什么
- 分组底板代表什么

#### 9.8.6 快速定位卡

建议提供以下快捷定位：

- 跳到运行中任务区
- 跳到阻塞任务区
- 跳到待审批任务区
- 跳到最新活跃任务
- 跳到失败任务

### 9.9 右栏任务检查器信息架构

为了尽量保留画布面积，右栏不建议做成常驻侧栏，而建议改成“画布内右侧任务抽屉”。

建议顶部固定任务头部，下面使用精简后的五个一级 Tab：

1. `概览`
2. `关系`
3. `审批/风险`
4. `审计`
5. `更多`

说明：

1. `执行` 信息并入 `概览`
2. `跳转` 动作并入 `更多`
3. 这样可以压缩 tab 数量，降低右侧密度

右栏草图如下：

```text
+--------------------------------------+
| 任务头部                              |
| 任务标题  状态  阶段  风险  最近活动   |
| 任务 ID | 仓库/分支 | 负责人          |
+--------------------------------------+
| Tab: 概览 | 关系 | 审批/风险 | 审计 | 更多 |
+--------------------------------------+
| 当前 tab 内容区                       |
+--------------------------------------+
```

#### 9.9.1 `概览` Tab

展示：

- 任务一句话摘要
- 当前状态
- 当前阶段
- 最近活动
- 最近执行进展
- 当前 session 或分支摘要
- 最近失败或暂停原因
- 负责人
- 变更摘要
- 当前关注原因

#### 9.9.2 `关系` Tab

展示：

- 上游依赖任务
- 下游依赖任务
- 阻断它的对象
- 被它阻断的对象
- 派生来源任务
- 相关软关联任务

#### 9.9.3 `审批/风险` Tab

展示：

- 待审批事项
- 当前风险标签
- 是否阻断
- 规则命中摘要
- 高优先级待处理项

#### 9.9.4 `审计` Tab

这个 tab 不在右栏直接展开完整审计图，而是作为下钻入口。

展示：

- 最近审计事件摘要
- 最近工具调用摘要
- 最近文件变更摘要
- `打开该任务审计流` 按钮

这样就把项目总图和任务审计流的职责分开了。

#### 9.9.5 `更多` Tab

展示：

- 打开任务详情页
- 打开任务工作台
- 打开审计流
- 在监控台聚焦该任务
- 打开审批单

建议明确交互：

1. 右侧任务抽屉默认隐藏
2. 点击任务节点或边时，以覆盖式抽屉从画布右侧滑出
3. 抽屉关闭后，画布恢复全宽
4. 在较窄屏幕下，抽屉应改为底部上滑面板或全屏详情层

### 9.10 页面模式

建议页面支持以下三种模式：

1. `运营视角`
2. `编排视角`
3. `处置视角`

#### 9.10.1 运营视角

目标：快速盘点当前项目运行态势。

重点展示：

- 按状态或按阶段布局
- 运行中、阻塞、待审批数量
- 最新活跃任务

#### 9.10.2 编排视角

目标：看任务之间的依赖和推进结构。

重点展示：

- 真实关系边
- 阶段推进路径
- 派生任务与阻断关系

#### 9.10.3 处置视角

目标：优先处理需要立即动作的任务。

重点展示：

- 阻塞任务
- 待审批任务
- 高风险任务
- 最新失败任务

### 9.11 权限分层

建议至少分三层：

1. 普通成员视图
2. 项目管理员视图
3. 审计或平台管理员视图

#### 9.11.1 普通成员视图

可见：

- 所有可见任务节点
- 基础状态和阶段
- 可见依赖关系
- 自己有权限查看的任务摘要

#### 9.11.2 项目管理员视图

可见：

- 全部任务节点
- 更完整的审批和风险信息
- 更完整的负责人和关系视图
- 更完整的图层开关

#### 9.11.3 审计或平台管理员视图

可见：

- 项目管理员全部能力
- 更深的任务治理信息
- 从任务右栏进入审计流时的更高权限能力

### 9.12 Vue Flow 落地约束

#### 9.12.1 性能边界

建议规则：

1. 首屏默认只展开当前筛选命中的任务节点。
2. 审批节点和软关联边默认关闭。
3. 项目任务过多时，先按组折叠，而不是一次性平铺。
4. 右栏详情按需加载，不在首屏把所有任务详情都拉下来。
5. 不通过缩小节点尺寸来换取更多首屏展示量。
6. 单个阶段、单个状态组或单个负责人组内超过阈值时，必须自动收敛为 `前 N 个节点 + 组节点`。

建议的默认阈值如下：

1. 阶段组阈值：6
2. 状态组阈值：8
3. 负责人组阈值：10

建议的组节点规则如下：

1. 每个组节点最多聚合 12 个任务。
2. 若超出 12 个，则继续拆分为多个组节点，而不是做成超长列表。
3. 已完成任务优先进入折叠组，不抢首屏。
4. 阻塞、待审批、失败任务默认尽量不进入折叠组，除非数量本身已经过高。

#### 9.12.2 可用性边界

建议规则：

1. 不在节点内堆正文日志。
2. 不默认显示常驻左右栏，避免压缩画布。
3. 所有低频信息都通过点击后出现的浮层或抽屉承载。
4. 默认第一屏只显示任务最关键的信息：标题、状态、阶段、最近活动、高优先级标签。
5. 不为没有真实语义的任务画边。
6. 默认优先展示“现在该看什么”，不是“所有历史都堆出来”。
7. 画布主目标是项目调度和定位，不是替代任务详情页。
8. 节点尺寸优先保证可读性，不因任务数量增多而自动压缩到难以点击。
9. 任务很多时，正确交互是拖动画布、缩放和定位，而不是把整张图硬塞进首屏。

同时建议删除或降级以下默认显示内容：

1. 常驻项目概览卡
2. 常驻图例卡
3. 常驻负责人信息
4. 常驻仓库/分支摘要
5. 常驻计数区

这些内容都不是第一屏必须内容。

#### 9.12.3 复用现有前端能力

当前仓库已经具备 Vue Flow 与任务画布基础，因此建议直接复用：

1. 复用 MultiTaskMonitor 的画布交互、拖拽和布局模式经验。
2. 复用 TaskGraph 的 Vue Flow、Dagre 与样式引入链路。
3. 沿用现有 Vue Flow 测试 stub 机制。
4. 优先在现有任务与项目接口基础上聚合新的项目级读模型。

## 10. 实施建议

### 10.1 第一阶段：项目级任务读模型

目标：先把“项目下所有任务”的可视化输入准备好。

任务建议：

1. 定义 `ProjectTaskGraphViewModel`。
2. 聚合项目下所有任务的基础字段：状态、阶段、最近活动、负责人、仓库、风险摘要。
3. 如果存在真实任务关系数据，则输出 `depends-on / blocks / informs / spawned-from` 边。
4. 若暂时缺少真实关系数据，至少输出可用于分组布局的结构字段。

### 10.2 第二阶段：项目任务总图 MVP

目标：先把“项目下所有任务在一张图上”跑通。

任务建议：

1. 新增项目级 `任务总图` 页面或 Tab。
2. 落地顶部摘要、左栏控制区、中间 Vue Flow、右栏任务检查器四区结构。
3. 首版先支持任务节点、分组底板和基础布局模式。
4. 首版先支持按阶段和按状态两种布局。

### 10.3 第三阶段：真实关系边与任务处置能力

目标：让这张图从“任务盘点图”升级为“任务关系图”。

任务建议：

1. 补齐真实依赖边、阻断边、派生边。
2. 在右栏加入审批/风险和跳转能力。
3. 支持聚焦当前任务上下游。
4. 支持只看阻塞链、只看待审批链。

### 10.4 第四阶段：与监控台和审计流联动

目标：让项目任务总图成为项目级总入口。

任务建议：

1. 从多任务监控台跳到项目任务总图。
2. 从项目任务总图跳到单任务工作台。
3. 从右栏 `审计` Tab 跳到该任务的审计流。
4. 支持按项目范围的实时订阅和局部刷新。

## 11. 最终建议

如果用户真正的目标是“把一个项目的所有任务都在一张 Vue Flow 图上展示出来”，那么前端策略应该是：

1. Vue Flow 主画布承载项目级任务总图，而不是单任务审计流。
2. 主节点以任务为中心，任务关系边只表达真实语义。
3. 审计流作为任务级下钻能力存在，不再抢占项目级主画布。
4. 左栏负责布局与筛选，右栏负责任务检查与跳转。
5. 页面首先服务项目管理、任务定位和任务处置，其次才是任务证据下钻。

一句话总结：

**如果你要的是“一张图看完一个项目的所有任务”，那这张 Vue Flow 图就应该是项目任务总图，不是任务审计图。**
