# OpenerX 组织架构化 Agent 研发协作方案

> 适用范围：OpenerX 控制平面、BFF、Web UI、运行时与治理能力的后续产品演进
>
> 目标：将现有生命周期 Hook、工作流模板、多角色执行与聚合能力，重构为符合 IT 公司研发团队组织方式的 AI 协作体系

## 1. 文档目标

本文档回答以下问题：

- OpenerX 应该被用户理解成什么
- 哪些职责由平台管理员承担，哪些职责应交给老板 Agent 自动完成

- 工作流、Hook、角色聚合如何映射为真实研发团队的协作方式
- 如何在不推翻现有架构的前提下，把系统演进为“AI 研发组织系统”

本文档是产品与管理设计文档，不是代码实现细节说明。

## 2. 背景

当前 OpenerX 已经具备以下基础能力：

- 生命周期 Hook
- 工作流模板与阶段模型
- 多角色 Agent 执行
- 并行候选与聚合评判
- 审批、阻断、修正请求与任务收口

这些能力在技术上已经形成了较强的调度基础，但在产品认知层仍然存在三个问题：

1. 系统对用户展示的仍然更像“任务编排引擎”，而不是“一个可理解的研发团队”。
2. 管理职责和模型职责尚未完全分层，用户不容易判断哪些是管理员手动配置，哪些是模型自动判断。
3. 现有角色体系偏“执行与治理能力集合”，还不够像现实 IT 公司中的岗位协作关系。

因此，本方案提出将 OpenerX 从“技术编排系统”提升为“组织架构化的 AI 研发协作系统”。

## 3. 一句话定义

OpenerX 是一个由老板 Agent 带领虚拟研发团队完成任务的 AI 组织协作系统。

在这个定义下：

- 平台管理员负责制度
- 老板 Agent 负责项目经营
- 各岗位 Agent 负责专业工作
- 人类只在制度调整、重大越权和高风险例外中介入

## 4. 设计目标

本方案目标如下：

1. 让系统对用户展示的是团队协作关系，而不是底层模型编排关系。
2. 让管理员只负责平台制度，不再深度参与每个项目的日常推进。
3. 让老板 Agent 成为项目管理员的模型替身，在授权边界内自动完成项目管理工作。
4. 让每个 Agent 都对应稳定岗位成员，形成贴近真实 IT 公司开发组的组织结构。
5. 让管理员可以灵活选择“组织化协作模式”或“单兵模式”，而不是强制所有项目都按完整团队运作。
6. 让所有自动判断都具备清晰的授权边界、升级规则和审计能力。

## 5. 核心原则

### 5.1 制度与经营分离

系统中的“管理”必须拆成两层：

- 制度管理：由平台管理员负责
- 项目经营：由老板 Agent 负责

平台管理员决定什么可以做，老板 Agent 决定当前项目怎么做。

### 5.2 Agent 是岗位成员，不是抽象工具

系统中的每个 Agent 都应当被用户理解为团队中的岗位成员，而不是某个底层模型、脚本或插件。

用户看到的应该是：

- 谁负责需求澄清
- 谁负责方案把关
- 谁负责代码实现
- 谁负责安全与测试
- 谁负责发布与运行

而不是：

- 哪个 prompt 被调用了
- 哪个 execution plan 被触发了
- 哪个 runtime candidate 获胜了

### 5.3 工作流是团队作业流程，不是脚本流水线

工作流模板表达的是团队标准作业流程。

它定义的是：

- 一个项目应经过哪些阶段
- 每个阶段由哪个岗位主责
- 哪些岗位必须参与
- 哪些结论会阻断推进
- 哪些节点需要审批

而不是简单的一串技术执行步骤。

### 5.4 自动化优先发生在项目经营层

本方案不追求让模型自动修改平台制度。

自动化的重点应该放在：

- 项目受理
- 模板选择
- 团队编组
- 阶段推进
- 角色调度
- 风险汇总
- 阻断、修正与审批建议

也就是由老板 Agent 自动经营项目，而不是由平台模型自动修改制度。

### 5.5 所有越权动作都必须升级

如果自动系统要做的事超出了既有制度边界，就必须升级给人类。

例如：

- 变更平台安全红线
- 扩大工具权限
- 越过审批规则
- 执行高风险生产操作但未被授权
- 修改模板治理规则

### 5.6 组织模式必须可切换

组织化协作方案应是平台提供的一种能力，而不是唯一工作方式。

平台管理员或项目管理员应能按项目、按模板、按任务选择不同模式：

- 单兵模式：由一个主执行 Agent 基本独立完成任务，其他角色默认不介入或只在异常时介入
- 组织化协作模式：由老板 Agent 组织多个岗位 Agent 分阶段协作
- 混合模式：平时按单兵模式执行，但在高风险阶段自动切入组织化协作

这意味着：

- 系统必须允许从完整团队模式退回到一个人完成任务
- 系统也必须允许从单兵模式升级到组织化协作
- 模式选择应成为可配置项，而不是硬编码策略

## 6. 组织架构模型

### 6.1 平台管理员

平台管理员是制度设计者，不是项目执行者。

主要职责包括：

- 维护角色体系
- 维护模板库
- 维护审批标准
- 维护安全与合规边界
- 维护模型白名单、工具白名单与预算上限
- 维护自动托管开关和升级规则

平台管理员的目标是“搭制度”，不是“盯项目”。

### 6.2 老板 Agent

老板 Agent 是本方案中的核心新增角色，是项目级管理员的模型替身。

老板 Agent 对应现实中的：

- 项目负责人
- 研发经理
- 技术负责人
- 交付负责人

它不是平台根管理员，而是项目经营者。

主要职责包括：

- 接收任务并判断是否立项
- 选择适合当前任务的工作流模板
- 决定当前项目需要哪些岗位成员参与
- 组织阶段推进
- 汇总岗位结论并做项目级判断
- 决定继续、回退、暂停、审批或升级给人类

老板 Agent 不直接承担平台制度维护职责，也不能越过平台规则。

### 6.3 项目组成员 Agent

建议首批建立以下岗位角色：

- 产品 Agent
- 架构 Agent
- 开发 Agent
- 测试 Agent
- 安全 Agent
- 运维 Agent
- 设计 Agent
- 发布 Agent

其中：

- 开发 Agent 是默认主执行岗位，负责主代码与主交付物落地
- 其他岗位主要负责建议、评审、检查、阻断、审批建议和修正请求
- 同一岗位允许绑定多个底层 Agent，以形成同岗位多视角评审能力

### 6.4 人类监督者

人类默认不需要深度参与每个任务。

人类应当只在以下场景介入：

- 平台制度调整
- 高风险审批
- 越权请求确认
- 老板 Agent 请求升级
- 系统置信度不足且无法自动裁决

## 7. 人工与自动边界

### 7.1 平台制度层

以下事项默认由平台管理员负责：

- 角色与权限边界
- 模板库与模板上限
- 审批规则与安全红线
- 模型和工具边界
- 自动托管授权策略
- 预算与成本约束

这层属于“公司制度”，不应完全交给模型自主修改。

### 7.2 项目经营层

以下事项默认交给老板 Agent 自动负责：

- 任务类型和复杂度判断
- 模板选择与切换建议
- 团队编组
- 阶段推进与节奏控制
- 角色结论的综合裁决
- 是否发起审批、回退、暂停、继续或升级

这层是本方案自动化的核心。

在单兵模式下，这一层并不消失，而是被弱化为：

- 选择是否仍由老板 Agent 做轻量调度建议
- 或直接跳过老板 Agent，由主执行 Agent 独立完成任务

也就是说，老板 Agent 应当是可配置参与，而不是强制存在。

### 7.3 专业执行层

以下事项由岗位 Agent 自动负责：

- 产品 Agent：需求澄清、范围说明、验收标准
- 架构 Agent：方案评审、边界判断、技术风险
- 开发 Agent：实现代码、配置、文档和修复动作
- 测试 Agent：测试策略、回归、验证结果
- 安全 Agent：漏洞、权限、敏感数据、合规检查
- 运维 Agent：部署、回滚、环境与运行观察
- 设计 Agent：视觉、交互、文案一致性
- 发布 Agent：发布准备、窗口建议、上线检查

### 7.4 必须升级给人类的场景

以下情况必须触发升级：

- 命中平台安全红线
- 需要扩大角色权限或工具权限
- 需要修改制度与模板治理规则
- 需要执行未授权的高风险生产动作
- 多岗位结论冲突且老板 Agent 无法高置信裁决
- 预算、成本、合规或审计约束被触发

## 8. 岗位职责模型

### 8.1 产品 Agent

职责：

- 澄清需求目标与范围
- 输出验收标准
- 标记非功能性约束
- 识别需求缺口与歧义

输出物：

- 需求摘要
- 范围说明
- 验收标准清单

### 8.2 架构 Agent

职责：

- 审查模块边界、接口与依赖
- 判断方案合理性和扩展性
- 给出技术风险与替代方案

输出物：

- 架构结论
- 方案建议
- 风险清单

### 8.3 开发 Agent

职责：

- 负责主代码改动与交付物实现
- 承接其他角色提出的修正请求
- 输出实现结果和测试证据

输出物：

- 代码变更
- 变更说明
- 本地验证结果

### 8.4 测试 Agent

职责：

- 制定验证策略
- 给出通过、失败和回归风险结论
- 将问题转为开发修正请求

输出物：

- 测试报告
- 回归风险说明
- 缺陷清单

### 8.5 安全 Agent

职责：

- 检查权限、安全与合规风险
- 判断是否需要阻断或审批
- 为高风险变更提供证据性结论

输出物：

- 安全评审结果
- 风险等级
- 审批建议

### 8.6 运维 Agent

职责：

- 判断环境、部署与回滚风险
- 检查日志、监控、健康状态和运行假设
- 对发布后异常提供观察结论

输出物：

- 运行准备结论
- 上线风险说明
- 发布后观察摘要

### 8.7 设计 Agent

职责：

- 审查视觉风格、一致性和交互质量
- 给出可执行的设计修正建议

输出物：

- 设计检查结果
- 视觉与交互修正建议

### 8.8 发布 Agent

职责：

- 汇总发布前条件
- 判断是否满足上线准备
- 给出上线窗口与发布策略建议

输出物：

- 发布准备清单
- 发布建议与回滚建议

## 9. 团队协作流程

本方案建议用真实 IT 公司开发组的协作节奏来表达任务推进。

### 9.1 接单与立项

老板 Agent 接收任务，并判断：

- 是否立项
- 风险等级
- 复杂度
- 是否需要完整团队
- 适合使用哪套模板

如果不满足推进条件，老板 Agent 应要求补充信息，而不是直接进入开发。

### 9.2 需求澄清会

产品 Agent 主导输出：

- 任务目标
- 范围
- 验收标准
- 约束条件

老板 Agent 根据澄清结果决定是否进入方案阶段。

### 9.3 方案评审会

架构 Agent 主导，安全 Agent 和开发 Agent 参与。

这一阶段输出：

- 方案结论
- 风险清单
- 边界判断
- 回退路径

老板 Agent 决定：

- 通过
- 补充方案
- 阻断
- 升级审批

### 9.4 开发排期与任务拆解

老板 Agent 负责组织拆解任务与阶段目标。

开发 Agent 承接主执行工作，测试、安全、运维准备对应检查项。

### 9.5 实施开发

开发 Agent 负责代码、配置、脚本和文档落地。

其他岗位不应同时抢占主代码改动，而是在约定节点：

- 提交专业结论
- 发起修正请求
- 触发 Gate
- 提供审批建议

### 9.6 联调与验收

测试、安全、运维分别给出专业结论。

老板 Agent 汇总这些结论，并判断是否进入发布阶段。

### 9.7 发布决策

老板 Agent 根据角色结论做最终项目级判断：

- 直接发布
- 审批后发布
- 延期发布
- 回退修正
- 请求人工接管

### 9.8 发布后观察与复盘

运维 Agent 负责发布后观察。

老板 Agent 负责项目收口、复盘、经验沉淀和模板反馈。

## 10. 与现有系统能力的映射

### 10.1 生命周期 Hook

在组织化模型中，生命周期 Hook 应被解释为：

- 阶段入口治理动作
- 阶段出口会签动作
- 异常响应动作
- 恢复前治理动作

Hook 不再只对技术人员解释为底层回调，而应被产品层表达为团队治理动作。

### 10.2 工作流模板

工作流模板在本方案中等价于团队标准作业流程。

模板决定：

- 阶段顺序
- 主责岗位
- 参与岗位
- Gate 规则
- 审批要求
- 回退策略

### 10.3 多角色与并行评审

同岗位多 Agent 不应直接作为技术细节向用户暴露。

产品层应将其解释为：

- 同岗位多视角评审
- 组内会签
- 组内候选比选

### 10.4 Judge

Judge 更适合作为老板 Agent 的内部裁决辅助能力，而不是一项独立面向普通用户的概念。

### 10.5 修正请求与阻断

现有的 developer change request、阻断、审批建议等能力，产品层应当表达为：

- 组员给开发的修改单
- 阶段 Gate 阻断
- 项目经理升级审批

## 11. 产品呈现建议

### 11.1 任务详情页

任务详情页应优先展示：

- 当前老板判断
- 当前阶段
- 当前主责岗位
- 各岗位结论
- 阻塞项与修正项
- 审批状态

底层 Agent 执行细节保留为展开视图，而不是主叙事。

### 11.2 项目编排页

项目编排页应优先展示：

- 当前模板
- 当前老板 Agent
- 项目小组构成
- 各阶段主责与参与岗位
- Gate 与审批要求
- 当前自动托管级别

### 11.3 设置与治理页

设置页主要服务平台管理员，配置项应围绕：

- 角色库
- 模板库
- 老板策略
- 自动托管策略
- 协作模式策略
- 审批与升级策略
- 安全与预算边界

其中，协作模式策略至少应支持以下配置：

- 默认使用单兵模式
- 默认使用组织化协作模式
- 仅在高风险任务启用组织化协作
- 仅在特定模板中启用老板 Agent
- 允许项目管理员手动切换模式

## 12. 自动托管等级建议

为了让用户逐步接受“老板 Agent 接管项目管理”，建议引入自动托管等级：

自动托管等级与协作模式并不是同一个概念：

- 协作模式决定“是一个人做，还是按团队做”
- 自动托管等级决定“老板 Agent 在该模式下能自动做多少决定”

例如：

- 单兵模式 + L0：一个主执行 Agent 工作，人类做关键确认
- 单兵模式 + L1：一个主执行 Agent 工作，系统只在异常时插入老板建议
- 组织化协作模式 + L1：老板 Agent 自动推进常规阶段，但关键动作仍需人工确认
- 组织化协作模式 + L2：老板 Agent 在授权边界内经营整个项目

### 12.0 协作模式建议

建议在自动托管等级之外，再定义协作模式。

#### 单兵模式

- 由一个主执行 Agent 完成绝大多数工作
- 适合小任务、低风险任务、探索型任务和快速交付场景
- 只有在命中高风险规则或明确配置时，才插入安全、测试、运维等辅助角色

#### 组织化协作模式

- 由老板 Agent 组织多个岗位 Agent 分阶段协作
- 适合中高复杂度任务、跨层改造任务、需要审计与审批的任务

#### 混合模式

- 默认按单兵模式运行
- 当命中高风险、发布、生产、跨系统改造等条件时，自动切换为组织化协作
- 适合希望保持效率，但又不愿完全放弃治理能力的团队

### 12.4 协作模式 × 自动托管等级对照表

为了避免“协作模式”和“自动托管等级”被混为一谈，建议统一按下表理解：

| 协作模式 \ 自动托管等级 | L0 手动监督 | L1 半自动经营 | L2 全自动托管 |
| --- | --- | --- | --- |
| 单兵模式 | 一个主执行 Agent 完成任务，人类确认关键动作 | 一个主执行 Agent 完成任务，系统在异常或高风险时插入老板建议 | 一个主执行 Agent 高度自主执行，只有越权、重大异常和低置信度决策才升级 |
| 组织化协作模式 | 老板 Agent 和多个岗位 Agent 提供完整团队协作建议，但关键阶段和关键决策仍由人类确认 | 老板 Agent 自动推进常规阶段，多岗位按模板协作，关键审批和高风险动作仍需人工确认 | 老板 Agent 在授权边界内经营整个项目，多岗位协作和阶段推进均自动完成，仅例外情况升级 |
| 混合模式 | 默认按单兵模式运行，系统建议何时切换到组织化协作，切换与关键动作由人类确认 | 默认按单兵模式运行，命中高风险或关键条件时自动切换到组织化协作，关键审批仍人工确认 | 默认按单兵模式运行，系统可自动切换到组织化协作并由老板 Agent 接管经营，只有越权和重大例外升级 |

建议理解方式如下：

- 协作模式决定“任务是按一个人做，还是按一个团队做”
- 自动托管等级决定“在该模式下，系统可以替人做多少项目管理决策”

这张表应作为 [docs/organization-oriented-agent-operating-model.md](docs/organization-oriented-agent-operating-model.md)、[docs/development-role-agents-plan.md](docs/development-role-agents-plan.md) 和 [docs/boss-agent-design.md](docs/boss-agent-design.md) 的统一参照。

### 12.5 推荐使用场景表

为了让管理员和项目负责人能够直接按任务场景选用组合，建议优先参考下表：

| 任务场景 | 推荐协作模式 | 推荐自动托管等级 | 原因 | 备注 |
| --- | --- | --- | --- | --- |
| 小任务 | 单兵模式 | L1 | 小任务通常范围清晰、改动面有限，优先保证效率；保留老板 Agent 的异常建议能力即可 | 若涉及敏感权限、核心链路或生产配置，可临时升级为混合模式 |
| 跨系统改造 | 组织化协作模式 | L1 | 跨 Web UI、BFF、控制平面、Runtime 或多仓库改造通常需要架构、开发、测试和运维共同参与 | 若组织规则成熟、审计充分，可逐步升级到 L2 |
| 生产发布 | 混合模式 | L0 或 L1 | 发布前后的主要目标是效率与风险平衡，平时可按单兵推进，进入发布阶段后自动切入组织化协作 | 对生产高风险项目，优先使用 L0；对成熟低风险项目可使用 L1 |
| 安全修复 | 组织化协作模式 | L0 或 L1 | 安全修复通常需要安全、架构、开发、测试甚至运维共同参与，不适合完全按单兵模式处理 | 高危修复优先 L0；中低风险修复可使用 L1 |

进一步建议如下：

- 小任务：默认走单兵模式，不要为追求形式完整而强行拉起完整团队。
- 跨系统改造：默认走组织化协作模式，因为跨边界任务的失败通常不是编码问题，而是边界、兼容和发布问题。
- 生产发布：最适合混合模式，因为前期实现可以保持轻量，发布节点再切入更强治理。
- 安全修复：默认按组织化协作处理，除非确认只是低风险、局部、可快速验证的小修补。

如果团队尚未建立稳定的自动托管信心，建议优先采用以下保守默认值：

- 小任务：单兵模式 + L1
- 跨系统改造：组织化协作模式 + L1
- 生产发布：混合模式 + L0
- 安全修复：组织化协作模式 + L0

### 12.1 手动监督模式

- 老板 Agent 只给建议
- 人类确认模板与关键决策
- 适合敏感项目和初期试点

### 12.2 半自动经营模式

- 老板 Agent 自动推进常规阶段
- 关键审批与高风险动作仍需人工确认
- 适合大多数项目

### 12.3 全自动托管模式

- 老板 Agent 在授权边界内自动完成项目经营
- 仅在越权和重大异常时升级给人类
- 适合成熟、低风险、规则稳定的项目

## 13. 成功标准

本方案成功的标志包括：

1. 用户能把系统理解为虚拟研发团队，而不是任务调度器。
2. 管理员不需要深度参与每个项目的推进。
3. 老板 Agent 能在授权边界内独立推进大多数项目。
4. 每个岗位 Agent 的职责、结论、阻塞和产物都能清晰展示。
5. 所有关键自动决策都具备解释、审计和升级能力。

## 14. 版本化落地建议

### 14.1 第一阶段

目标：先让系统像一个团队。

建议交付：

- 老板 Agent 概念与页面呈现
- 项目团队与阶段视图
- 模板选择与老板建议
- 人工与自动边界说明

### 14.2 第二阶段

目标：让团队中的岗位真实参与项目推进。

建议交付：

- 多岗位阶段参与
- 同岗位多 Agent 聚合
- 阻断、修正和审批闭环

### 14.3 第三阶段

目标：让老板 Agent 成为真正的项目经营者。

建议交付：

- 自动托管等级
- 老板阶段裁决能力
- 自动升级与人工接管闭环
- 模板和组织策略的持续优化建议

## 15. 与已有方案的差异和替代关系

本方案与 [docs/development-role-agents-plan.md](docs/development-role-agents-plan.md) 不是互相冲突的两套设计，而是处于不同抽象层级的两份文档。

### 15.1 继承关系

[docs/development-role-agents-plan.md](docs/development-role-agents-plan.md) 已经完成了以下关键定义：

- 首批角色 Agent 清单
- 研发阶段拆分方式
- 模板驱动原则
- 角色产物与阶段产物要求
- 同角色多 Agent 聚合评审方向
- 与 Hook、审批、控制平面的衔接思路

这些内容在本方案中继续成立，本方案不否定这些基础设计。

换句话说：

- 旧文档回答“系统里应该有哪些角色、哪些阶段、怎样接入研发流程”
- 新文档回答“这些角色和阶段应当如何被重新解释为一个真实公司的组织结构”

因此，本方案是对旧文档的产品叙事升级与管理层补全，而不是对其底层阶段模型和角色清单的推翻。

### 15.2 主要差异

两份文档的重点差异如下：

1. 旧文档以“角色接入”为中心。
重点在于把产品、架构、开发、安全、测试、运维等角色接入研发阶段，并定义输出物、阶段和模板。

2. 新文档以“组织经营”为中心。
重点在于补齐平台管理员、老板 Agent、项目组成员、人类升级之间的职责分层，让系统更贴近真实 IT 公司开发组的组织结构。

3. 旧文档默认管理员维护模板，项目成员按模板执行。
新文档进一步提出：在平台制度不变的前提下，老板 Agent 应成为项目管理员的模型替身，自动完成模板选择、团队编组、阶段推进与项目级裁决。

4. 旧文档主要解释“角色如何进入流程”。
新文档进一步解释“谁来经营流程、谁来承担管理责任、哪些判断应自动化、哪些必须升级给人类”。

### 15.3 替代边界

本方案建议将 [docs/development-role-agents-plan.md](docs/development-role-agents-plan.md) 视为“角色与阶段接入设计文档”，将本方案视为其上层的“产品定位与组织模型文档”。

因此，建议采用以下边界：

- 当需要说明角色、阶段、模板、产物与流程接入时，以 [docs/development-role-agents-plan.md](docs/development-role-agents-plan.md) 为准。
- 当需要说明管理员职责、老板 Agent 定位、人工与自动边界、组织架构叙事和产品认知时，以本方案为准。

这意味着本方案不直接替代旧文档中的所有细节章节，但会在产品定位层面覆盖旧文档对系统整体形态的描述。

### 15.4 建议的文档角色分工

为了避免未来继续出现文档重叠，建议将两份文档的角色明确划分为：

- [docs/development-role-agents-plan.md](docs/development-role-agents-plan.md)：角色与阶段接入蓝图
- [docs/organization-oriented-agent-operating-model.md](docs/organization-oriented-agent-operating-model.md)：组织架构化产品总方案

进一步说：

- 旧文档更接近“系统里应该有哪些岗位和流程”
- 新文档更接近“系统为什么要按公司组织方式来设计，以及谁负责经营这些流程”

### 15.5 后续替代建议

在后续文档体系整理中，建议采取以下策略：

1. 不删除 [docs/development-role-agents-plan.md](docs/development-role-agents-plan.md)，保留其作为角色与阶段设计基础文档。
2. 在需要写产品概述、项目介绍、对外说明、管理视角方案时，优先引用本方案。
3. 后续如产生“老板 Agent 设计文档”或“项目经营自动化设计文档”，应继续归属于本方案这一条产品叙事主线。
4. 当旧文档中出现“管理员直接维护并主导项目流程”的表述时，后续应逐步修订为“平台管理员维护制度，老板 Agent 负责项目经营”。

## 16. 总结

这套方案的核心，不是让系统“调度更多 Agent”，而是让系统更像一个真实的研发组织。

平台管理员定义制度。
老板 Agent 负责经营项目。
各岗位 Agent 作为组员协同完成任务。

当用户理解系统时，不再需要理解复杂的编排技术细节，只需要理解团队是如何协同工作的。

这将使 OpenerX 从一个“具备多 Agent 能力的系统”，演进为一个“具备组织智能的 AI 研发团队操作系统”。
