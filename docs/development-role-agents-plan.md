# 开发过程多角色 Agent 接入方案

> 适用范围：OpenerX 控制平面、BFF、Web UI、运行时与治理能力的后续研发流程设计
>
> 目标：为项目建立一组面向开发过程的角色化 Agent，并将这些 Agent 以模板化、可审计、可插拔的方式接入需求、设计、开发、测试、发布和运维各阶段

## 1. 文档目标

本文档回答以下问题：

- 需要建立哪些开发过程 Agent
- 每类 Agent 在研发流程中承担什么职责

- 如何和现有多 Agent、生命周期 Hook、审批治理体系对齐
- 应该按什么阶段落地，避免先做出一套难以执行的“角色剧场”

本文档是流程与系统接入方案，不是最终实现细节说明。

## 2. 背景与问题

当前 OpenerX 已经具备多 Agent 执行、生命周期 Hook、审批治理、运行时适配等基础能力，但现有设计更偏向“执行型 Agent 编排”，还没有形成一套清晰的“研发过程角色体系”。

当前缺口主要有：

- 任务进入系统后，谁负责需求澄清、方案把关、界面定义、安全检查、发布准备，没有稳定的角色分工
- 多 Agent 能力更多服务于执行和治理，还没有固化成研发流程模板
- 部分角色天然不是“写代码的人”，例如产品、美术、安全、运维，但系统中缺少这些角色的入口与输出物模型
- 不同任务类型需要的角色组合不同，例如 UI 重构、后端能力建设、部署改造、安全修复，其流程不应相同
- 缺少“阶段性准入”机制，导致任务容易直接进入实现，而跳过需求、设计和风险评估

因此，需要把多 Agent 体系从“执行器集合”提升为“研发生命周期协作体系”。

## 3. 设计目标

本方案的目标如下：

1. 建立一组稳定的角色化 Agent，覆盖产品、架构、开发者、部署、运维、美术、安全、测试等主要研发职责。
2. 将 Agent 嵌入研发阶段，而不是让所有 Agent 在单一任务里同时竞争输出。
3. 每个阶段必须有明确输入、输出、准入条件和退出条件。
4. 角色 Agent 的输出必须可沉淀为任务附件、结构化记录、审计事实或审批依据。
5. 与现有生命周期 Hook 方案兼容，优先复用模板、Hook、审批标准，不另起一套平行系统。

## 4. 设计原则

### 4.1 角色化，不人格化

这里定义的是“职责角色 Agent”，不是人格陪伴型 Agent。

重点是职责边界、输入输出和交付责任，而不是风格化对话人设。

### 4.2 阶段触发，不全量常驻

不是每个任务都需要所有角色全程参与。

正确做法是：

- 先按任务类型选择工作流模板
- 再由模板决定阶段与阶段中的主责 Agent
- 只有在命中条件时，才插入补充角色，例如安全、运维、部署或美术

### 4.3 产物优先，不以聊天记录代替交付

每个角色 Agent 的价值必须体现在可消费产物上，例如：

- PRD 摘要
- 架构方案
- API 契约
- UI 线框与视觉说明
- 发布计划
- 运维 Runbook
- 风险清单
- 测试报告

如果只有聊天，没有产物，就无法进入后续阶段。

### 4.4 治理内嵌，而不是事后补救

安全、审批、发布和运维检查要作为生命周期的一部分，而不是开发完成后才想起补一道门。

### 4.5 模板驱动，而不是人工拼流程

系统应预置若干工作流模板，由管理员维护。项目成员发起任务时选择模板，系统自动插入对应角色 Agent 与阶段 Hook。

### 4.6 主代码写权限单点收敛

项目主代码的编写权限只授予开发者 Agent。

其他角色 Agent 的职责是：

- 发现问题
- 形成结构化分析与建议
- 触发 Gate、审批或阻断
- 通知开发者 Agent 执行实际代码修改

这条规则的目的不是削弱其他角色，而是避免多角色同时写主代码，导致职责混乱、变更来源不清和治理失效。

### 4.7 同角色多 Agent 视角机制

一个角色不必只绑定一个 Agent。

对于安全、架构、测试、运维这类辅助性角色，建议允许一个角色下配置多个 Agent 实例，例如：

- 安全 A
- 安全 B
- 架构 A
- 架构 B

这样做的目的不是让它们都去改代码，而是从多个视角发现问题、提出不同建议、相互校验盲区，再统一通知开发者 Agent 执行修正。

建议原则：

- 开发者角色可以保留单主执行 Agent 或主执行 Agent + 备份 Agent 模式
- 辅助角色优先采用多 Agent 评审池模式
- 多 Agent 的输出应被聚合为同一角色视图，而不是直接把底层运行时细节暴露给普通用户

## 5. 角色 Agent 清单

建议首批建立以下 8 类角色 Agent。

### 5.1 产品 Agent

职责：

- 澄清需求背景、用户目标、范围边界与验收口径
- 识别需求中的歧义、冲突与遗漏
- 输出用户故事、验收标准、非目标边界

典型输入：

- 用户请求
- 现有页面与流程
- 历史需求文档

典型输出：

- 需求摘要
- 验收标准
- 范围声明

### 5.2 架构师 Agent

职责：

- 判断改动应落在哪一层：Web UI、BFF、控制平面、Runtime、治理系统
- 设计模块边界、接口边界、数据模型演进与兼容策略
- 识别对现有架构的冲击面与技术风险

典型输出：

- 方案说明
- 模块拆分建议
- 风险与权衡记录

### 5.3 开发者 Agent

职责：

- 负责项目主代码实现，包括控制平面服务、BFF、Web UI、数据库、接口、事件流与运行时适配改造
- 承接其他角色提出的问题、建议、缺陷和阻断项，并执行实际代码修改
- 输出实现方案、代码变更、自测结论与交付说明

典型输出：

- 实施拆解
- API 契约
- 数据模型改造清单
- 代码变更说明

### 5.4 美术 Agent

职责：

- 负责视觉风格、组件层级、信息密度、图标/配色/可读性建议
- 为复杂控制台、治理页、监控页提供视觉与可解释性优化意见

典型输出：

- 页面视觉规范
- 关键区块示意
- 文案与视觉协同建议

说明：

- 美术 Agent 不负责主代码实现。它负责提出视觉表达与信息呈现建议，并将修改要求交给开发者 Agent 落地。

### 5.5 安全 Agent

职责：

- 识别权限绕过、越权访问、密钥暴露、命令执行风险、供应链与发布风险
- 对高风险改动提出审批、阻断或加固建议

典型输出：

- 风险评估
- 加固建议
- 审批触发建议

### 5.6 部署 Agent

职责：

- 负责构建、环境变量、部署步骤、依赖检查、回滚预案和环境差异识别
- 将功能交付从“代码完成”推进到“可发布”

典型输出：

- 发布计划
- 部署步骤
- 环境准备清单

### 5.7 运维 Agent

职责：

- 负责运行监控、告警、容量、日志、诊断路径和故障处置 Runbook
- 在故障修复、发布观察和回滚阶段承担主责

典型输出：

- 监控点建议
- 告警规则建议
- Runbook

### 5.8 测试 / QA Agent

职责：

- 负责测试矩阵、回归范围、边界条件、验收执行和缺陷复查
- 为“能否进入发布”提供可验证依据

典型输出：

- 测试清单
- 回归方案
- 验证结论

## 6. 研发阶段接入方案

建议将开发流程拆为 8 个阶段，并在每个阶段插入对应角色 Agent。

### 6.1 阶段 A：需求进入与澄清

触发时机：

- 新需求、新问题、新改造任务进入系统时

主责 Agent：

- 产品 Agent

协作 Agent：

- 架构师 Agent
- 安全 Agent（仅高风险需求）

本阶段目标：

- 把用户原始请求整理为明确任务
- 写清楚目标、范围、非目标、验收标准
- 识别是否涉及权限、安全、生产、发布风险

准出产物：

- 需求摘要
- 验收标准
- 任务类型标签
- 风险标记

### 6.2 阶段 B：方案设计

触发时机：

- 需求澄清完成，准备进入实现前

主责 Agent：

- 架构师 Agent

协作 Agent：

- 开发者 Agent
- 美术 Agent（涉及 UI）
- 安全 Agent（涉及鉴权、密钥、外部调用、执行权限）
- 部署 Agent（涉及环境和发布变更）

本阶段目标：

- 明确模块归属与接口边界
- 明确需要改哪些层、哪些表、哪些 API、哪些页面
- 输出最小可行实施路径

准出产物：

- 方案文档
- 模块改造清单
- 风险与兼容性说明

### 6.3 阶段 C：任务拆解与排程

触发时机：

- 方案通过后

主责 Agent：

- 产品 Agent
- 架构师 Agent

协作 Agent：

- 开发者 Agent
- 部署 Agent
- QA Agent

本阶段目标：

- 把方案拆成可执行任务包
- 为每个任务包指定主责角色与前置依赖
- 标记哪些任务需要审批或人工确认

准出产物：

- 任务 DAG
- 执行顺序
- 阶段性验收点

### 6.4 阶段 D：实现开发

触发时机：

- 任务进入编码或配置实现

主责 Agent：

- 开发者 Agent

协作 Agent：

- 美术 Agent（UI 实现前或关键页面评审时插入）
- 安全 Agent（高风险代码路径执行前后插入）

本阶段目标：

- 由开发者 Agent 完成代码、配置、脚本与文档实现
- 保持与既有架构一致，不破坏边界
- 其他角色负责指出问题、给出建议并通知开发者 Agent 修正
- 对高风险改动执行安全检查或审批挂钩

准出产物：

- 实现代码
- 自测记录
- 变更说明

### 6.5 阶段 E：集成验证

触发时机：

- 开发完成，进入联调与验收验证

主责 Agent：

- QA Agent

协作 Agent：

- 开发者 Agent
- 部署 Agent
- 运维 Agent
- 安全 Agent

本阶段目标：

- 检查接口、页面、实时链路、权限链路、部署链路是否闭环
- 识别性能、监控、日志和故障恢复缺口

准出产物：

- 测试报告
- 缺陷清单
- 发布阻塞项

### 6.6 阶段 F：发布准备

触发时机：

- 测试通过，准备上线

主责 Agent：

- 部署 Agent

协作 Agent：

- 运维 Agent
- 安全 Agent
- 产品 Agent

本阶段目标：

- 准备部署步骤、环境变量、变更窗口、回滚路径
- 判断是否需要审批单、发布白名单或人工确认

准出产物：

- 发布计划
- 回滚预案
- 发布检查表

### 6.7 阶段 G：发布执行与运行观察

触发时机：

- 版本开始部署和上线观察

主责 Agent：

- 运维 Agent

协作 Agent：

- 部署 Agent
- 开发者 Agent
- 安全 Agent

本阶段目标：

- 执行发布、观察指标、核对日志、定位异常
- 发生问题时快速触发降级、回滚或临时止血策略

准出产物：

- 发布结果
- 观测结论
- 故障记录

### 6.8 阶段 H：复盘与资产沉淀

触发时机：

- 任务关闭或发布稳定后

主责 Agent：

- 产品 Agent
- 架构师 Agent

协作 Agent：

- 运维 Agent
- QA Agent
- 安全 Agent

本阶段目标：

- 复盘目标达成度、缺陷、风险与流程问题
- 将经验回写为模板、规则、Runbook 或治理标准

准出产物：

- 复盘记录
- 模板更新建议
- 规则沉淀建议

## 7. 推荐工作流模板

为了避免每次都从零拼角色组合，建议系统预置以下模板。

### 7.1 功能开发模板

推荐链路：

产品 → 架构师 → 开发者 → QA → 部署 → 运维

适用场景：

- 常规功能新增
- 页面和接口联动改造

### 7.2 UI 重设计模板

推荐链路：

产品 → 架构师 → 美术 → 开发者 → QA → 产品确认

适用场景：

- 仪表盘重构
- 控制台布局调整
- 设置页信息架构重排

### 7.3 平台能力建设模板

推荐链路：

产品/架构师 → 开发者 → 安全 → QA → 部署 → 运维

适用场景：

- BFF / 控制平面 / Runtime 接口扩展
- 数据模型新增
- 治理能力建设

### 7.4 发布修复模板

推荐链路：

运维 → 开发者 → QA → 部署 → 运维观察

适用场景：

- 线上问题修复
- 热补丁
- 紧急回滚后恢复发布

### 7.5 安全修复模板

推荐链路：

安全 → 架构师 → 开发者/部署 → QA → 安全复核 → 发布

适用场景：

- 鉴权问题
- 凭证泄露风险
- 高风险执行链路加固

## 8. 与 OpenerX 现有体系的衔接方式

### 8.1 与多 Agent 生命周期 Hook 对齐

本方案不新建独立编排引擎，而是建立在现有 [docs/multi-agent-hook-architecture.md](docs/multi-agent-hook-architecture.md) 的模板与 Hook 演进方向上。

建议做法：

- 用工作流模板表达“阶段 + 角色 Agent + 准入条件”
- 用生命周期 Hook 表达阶段切入点，例如 `pre-design`、`pre-implementation`、`pre-release`、`post-release-review`
- 用 Hook 执行记录保存角色 Agent 在每个阶段的输出摘要和决策结果
- 对辅助角色支持“同角色多 Agent 聚合评审”，例如同一安全角色下由多个安全 Agent 并行给出意见，再汇总为统一风险结论

### 8.2 与审批治理对齐

安全 Agent、部署 Agent、运维 Agent 的输出可直接连接审批治理链路。

建议规则：

- 高风险代码改动由安全 Agent 提交 `request_approval` 决策
- 生产环境发布由部署 Agent 或运维 Agent 触发发布审批
- 命中高风险环境、命令等级、外部 API 或敏感文件时，沿用 [docs/approval-standards-management-plan.md](docs/approval-standards-management-plan.md) 中的标准模型

### 8.3 与控制平面职责对齐

控制平面服务负责：

- 角色 Agent 注册信息
- 工作流模板定义
- 阶段执行记录
- 审批单、审计事件与任务状态

BFF 负责：

- 将任务请求映射为模板执行
- 在阶段切换时调度角色 Agent
- 聚合阶段输出给前端展示

Web UI 负责：

- 展示当前任务处于哪个阶段
- 展示每个角色 Agent 的输出和阻塞项
- 允许管理员选择模板、查看审批与人工接管点

Runtime 负责：

- 真正执行编码、分析、检查和辅助性任务
- 回传事件、结果、失败原因和中间产物

## 9. 建议的数据与页面模型

本轮先做方案，不要求立即实现，但建议后续围绕以下对象落地。

### 9.1 建议新增逻辑对象

- `role_agents`：角色 Agent 注册表
- `workflow_templates`：按任务类型组织的流程模板
- `workflow_stage_runs`：阶段执行记录
- `workflow_artifacts`：角色产物记录
- `workflow_gate_decisions`：准入、阻断、审批决策

### 9.2 页面建议

- 在任务详情页新增“流程”或“阶段”视图
- 展示当前阶段、已完成阶段、阻塞阶段
- 展示每个角色 Agent 的输出摘要与完整产物入口
- 管理页中新增“工作流模板”配置入口，仅管理员可编辑

## 10. 落地阶段建议

建议按三期推进。

### 10.1 Phase 1：角色注册与模板落地

目标：

- 建立角色 Agent 注册表
- 提供静态模板选择
- 在任务级别展示阶段清单

不做：

- 不做复杂自动裁决
- 不做全量并行赛马

### 10.2 Phase 2：阶段 Hook 与产物沉淀

目标：

- 阶段切换自动触发对应角色 Agent
- 角色输出自动沉淀为结构化产物
- 高风险阶段可触发审批与阻断

### 10.3 Phase 3：多角色协同与聚合评判

目标：

- 前后端并行实现
- 安全、QA、部署、运维并行评估
- 由 Judge 类 Agent 对阶段结果进行汇总裁决

## 11. 首批验收标准

首批上线后，至少应满足以下标准：

1. 系统中可以配置多种工作流模板，并将模板绑定到任务类型。
2. 每个任务至少能看到需求、设计、实现、验证、发布几个基本阶段。
3. 每个阶段至少有一个主责角色 Agent，且能生成可查看的阶段产物。
4. 安全和发布阶段可以触发审批或阻断，而不是只做信息展示。
5. UI 能展示阶段状态、角色输出、阻塞原因和人工接管点。
6. 只有开发者 Agent 具备项目主代码写权限，其他角色只能输出建议、阻断或通知开发者修正。
7. 安全、架构、测试、运维等辅助角色可以在同一角色下挂多个 Agent，从多个视角发现问题并形成聚合建议。
