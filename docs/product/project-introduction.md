## 1. 一句话介绍

OpenerX 是面向企业研发组织的 AI Dev/Ops 管理与治理平台，用来把 AI Agent（智能体）纳入可治理、可审计、可追责的研发流程。

它不是：

- 个人 AI IDE
- 企业版聊天助手
- 低价开发者插件
- 纯多 Agent 编排引擎
- 新的底层运行时平台

它是：

- 连接任务、项目、成员、Agent、审批、预算、审计、代码变更与运行时执行的统一管理平台
- 让 AI 在组织边界内运行、全程留痕、可以回查、能够规模化落地的系统

## 2. 目标用户

OpenerX 主要服务以下六类用户和团队：

1. **平台工程与 DevOps 团队**
   需要统一管理组织内的 Agent 基础设施、运行入口与扩展能力，不希望每个团队各自拼装 AI 工具链。

2. **研发管理者与技术负责人**
   需要让跨团队的 AI 使用可控、可见、可追踪，能回答“哪些任务正在跑、谁在跑、做了什么、结果是什么”。

3. **安全、合规与治理负责人**
   需要审批流、审计事件、策略约束、阻断能力和证据导出，把 AI 的使用纳入现有的合规体系。

4. **成本与运营相关角色**
   需要预算上限、周期控制、告警规则、用量账本（Usage Ledger）和费用可解释性，避免 AI 使用变成一笔不可控的开支。

5. **内部产品与交付团队**
   需要回答“这批需求能不能按期交付、AI 参与之后质量会不会失控、交付过程对业务方和客户如何解释”，希望把 AI 参与的工作纳入正式的产品和交付流程，而不是停留在开发者个人的聊天窗口。

6. **老板 / 高层管理者**
   不直接关心某一次对话或某一段提示词，而是关心组织在 AI 上的投入产出、风险等级、对外可交代性，以及是否需要继续扩大投入。

次一级匹配用户包括中型技术团队，以及需要多角色复核的交付团队；不匹配的用户包括个人开发者、缺少流程约束的小团队，以及只想采购低价提效工具的用户。

## 3. 组织为什么需要这样一个系统

AI 工具的“能不能生成内容”已经不是企业的核心问题。企业真正卡住的通常是以下几个场景：

1. AI 开始触碰真实研发工作，但没人能清楚说出**谁可以发起高风险动作**。
2. 跨仓库、跨系统的改动做完了，却无法解释**到底改了什么、由谁发起、为什么放行**。
3. 某些操作应当经过审批、阻断或升级，但现有工具里没有地方设置“事前卡点”。
4. 出现争议或事故时，**无法提供原始行为证据**，只能看到一份摘要或结论。
5. 各团队各自使用模型，**成本散落、没有预算、无法规模化**。

OpenerX 的定位就是解决这组“组织如何把 AI 纳入正式研发流程”的问题，而不是再做一个能生成更多内容的聊天入口。

## 4. 核心能力

OpenerX 提供五组核心能力，按目标用户最关心的问题来组织：

### 4.1 组织化的智能体协作

- 组织（Organization）、项目（Project）、成员（Member）、智能体（Agent）、技能（Skill）构成统一的协作视图
- Task 是用户能看到的业务工作项，Session 是 Task 下面的一次具体执行
- Role 主要用于系统内部的职责与权限控制
- 多角色 Agent 可以在同一条任务上协作，而不是被塞进一个抽象助手里

### 4.2 把治理放到执行前

- 策略、审批、门控和钩子可以在执行前就介入，而不是等到事后再补救
- 审批、阻断、升级、策略命中都可以配置成系统能力
- 适合安全、合规、治理负责人把现有制度映射到 AI 的使用流程里

### 4.3 可回查的执行证据链

- 对外展示的执行追踪，主要读取已经持久化的任务视图，而不是直接依赖运行时原始消息
- 审计事件、会话操作记录、消息与代码变更共同组成一条可回查的事实链
- 面向安全、合规、交付和管理层，提供可验证、可导出的证据材料

### 4.4 成本与预算可控

- 用量账本以只追加、不回写的方式记录调用和成本事实
- 预算可以按组织或项目设置上限、周期与告警
- 成本与 Task / Session 绑定，让费用可以追到具体业务工作项

### 4.5 并行比较与顺序执行

- 同一个 Task 或阶段可以选择单次执行、并行比较、顺序执行等不同方式，而不是只能一次发起、一次等待结果
- 并行比较适合方案评估、代码生成对比、评审复核等场景：系统可以同时运行两个或多个候选执行，再由人或规则选择结果
- 顺序执行适合复杂任务拆解：可以按“分析 → 设计 → 实现 → 验证”这样的顺序逐步推进，前一步的产出可以直接作为后一步的输入
- 对安全、架构、QA、运维等辅助角色，也可以并行给出复核意见，再统一收敛为一个可追踪的结论
- 无论采用哪种执行方式，过程都仍然落在同一个 Task、Session、审计和预算体系里，方便管理、回放和追责

## 5. 用户视角下的典型使用链路

以下四条链路覆盖最常直接操作系统的角色在真实场景中的主要使用方式，帮助快速判断 OpenerX 是否解决你当前关心的问题。老板 / 高层管理者通常更多查看汇总视图和治理结果，而不是日常直接操作 Task，因此不单列一条日常操作链路。

### 5.1 研发管理者：统一掌控跨团队 AI 使用

1. 通过 Organization 和 Project 建立治理边界。
2. 在 Project 下发起 Task，由真实成员或 Agent 组成的团队执行。
3. 在 Task 详情页查看 Session 执行、并行比较结果、顺序步骤状态、消息流、变更与决策点。
4. 对异常任务进行人工介入、暂停或升级。

### 5.2 安全与合规负责人：把制度嵌入执行路径

1. 在策略和审批规则中配置高风险动作清单与审批规则。
2. 对满足条件的会话操作触发门控或钩子。
3. 审批通过后，运行时继续执行，审批过程会被记录为审计事件。
4. 事后通过执行追踪导出证据链。

### 5.3 平台工程与成本 / 运营负责人：规模化与预算化

1. 在组织级别配置预算上限、周期与告警规则。
2. 通过用量账本回看各项目、各 Task 的调用与费用分布。
3. 在运行时接入层统一接入默认的 pi-mono，减少各团队自己对接运行时的复杂度。
4. 通过 BFF 提供的事件通道获取实时状态，用于内部平台集成。

### 5.4 内部产品与交付团队：把 AI 纳入正式交付

1. 将需求、工单或迭代映射成 Project 下的 Task，使 AI 参与的工作进入产品视角。
2. 对复杂需求可以选择让多个候选方案并行比较，或按“分析 → 实现 → 验证”的顺序逐步执行，避免把整件事一次性压给单次生成。
3. 在 Task 上配置门控、钩子和审批规则，把测试通过、评审通过、风险提示等条件放到交付前面。
4. 让产品、开发、测试、运维作为 Member 或 Agent 在同一条 Task 上协作，保留讨论与决策轨迹。
5. 交付或对外同步时，基于 Task 状态、审计事件与执行追踪给出可解释的交付说明与证据。

## 6. 与常见替代方案的差别

面向目标用户，OpenerX 与以下几类方案有明确的定位差别：

1. **和个人 AI IDE / 代码助手相比**
   OpenerX 不是让单个工程师更快完成一段代码，而是让组织把 AI 的使用纳入可治理流程。

2. **和通用多 Agent 编排引擎相比**
   OpenerX 不满足于“把多个 Agent 连起来”，而是把编排放在治理、审批、预算、审计的上下文中。

3. **和新的底层运行时 / 模型平台相比**
   OpenerX 不是新做一个运行时，而是在已有运行时之上提供组织级的管理与治理层。

4. **和纯 Chat 助手相比**
   在 OpenerX 里，最核心的不是对话窗口，而是 Task、Session、Member、Agent、Approval 这些可管理、可追踪的对象。

## 7. 面向不同目标用户的切入点

每一类用户通常都有一组具体的日常问题。为便于阅读，下面按“他们关心什么 → OpenerX 能给什么”的方式，只保留最常被问到的重点入口。

- **研发管理者**
  - 关心：
    - AI 有没有真的让团队多出产能，而不是让人忙在对着模型调提示词上；
    - AI 参与的那些需求，现在到底进展到哪一步、卡在谁手上、要不要加人；
    - 不同小组用 AI 的方式是不是一致，有没有人绕过评审和测试直接合入；
    - 出现生产事故或质量回退时，能不能快速定位到是哪个任务、哪次执行、由谁触发；
    - 是否能把 AI 参与的工作和业务需求、迭代目标对上号，而不是只看到一堆对话记录。
  - 能给：Project 与 Task 的统一视图、Session 执行记录、审计留痕，以及把测试、评审、审批等质量条件放到执行前的能力和异常任务的人工介入入口。
- **安全与合规负责人**
  - 关心：
    - AI 是否访问了不应访问的代码库、数据或环境；
    - 高风险动作（例如改生产配置、调用外部接口、拉取敏感数据）在执行前有没有有效的卡点；
    - 谁在什么时间、因为什么理由批准了某个动作，是否可追责；
    - 合规审计或安全事件复盘时，能不能一次性拉出完整证据链，而不是事后拼日志；
    - 策略更新后，旧任务能否按新规则继续受控。
  - 能给：策略与审批规则配置、门控与钩子的执行前拦截、审计留痕，以及可导出的执行追踪证据。
- **平台工程与 DevOps 团队**
  - 关心：
    - 各团队各自拼 AI 工具链带来的碎片化和重复投入；
    - 模型或运行时升级 / 切换时，会不会把跑在上面的任务打断、能否回滚；
    - 系统出现故障时，能否降级、排障和逐步恢复；
    - 与公司现有的 SSO、审计系统、工单系统、发布系统的集成成本；
    - 多项目、多环境下的可观测性、容量与扩展。
  - 能给：组织化的 Agent 与 Session 模型、统一的对外接口、对不同运行时的适配层，以及事件通道和用于接入内部平台的集成点。
- **成本与运营相关角色**
  - 关心：
    - 每个团队、项目和具体 Task 的 AI 消耗是多少，异常消耗能否及时发现；
    - 预算到了上限能不能自动阻断，而不是月底收账单时再追责；
    - 费用能否准确归属到部门、产品线、项目，便于内部分摊和对外计价；
    - 成本和收益如何关联，哪些任务值得更多预算、哪些在浪费；
    - 历史用量能否用作下一个季度的预算依据。
  - 能给：以只追加方式记录的用量账本、按组织 / 项目维度设置的预算上限与告警、成本与 Task / Session 的绑定，以及面向汇总与回放的费用事实。
- **内部产品与交付团队**
  - 关心：这批需求能不能按期交付、AI 参与之后质量会不会失控、对外怎么解释。
  - 能给：
    - **需求到执行的映射**：把产品/交付口径的需求、工单、迭代挂到 Project 和 Task 上，让“正在做什么”在产品视角是可见的，而不只是开发者个人的对话记录。
    - **交付状态可见**：通过 Task 生命周期状态（draft / active / done / archived）和 Session 执行视图，随时回答“做到哪一步、卡在哪、是否需要人工介入”。
    - **质量与验收把关**：利用门控、钩子和审批，把测试通过、评审通过、风险提示等作为交付前必须满足的条件，而不是靠会议口头确认。
    - **跨角色协作**：产品、开发、测试、运维可以作为 Member 或 Agent 同时参与一个 Task，保留完整的讨论与决策轨迹，方便交付回顾和对外同步。
    - **对外可解释**：当业务方、客户或合作方问“AI 改了什么、为什么这么改”时，可以基于审计事件和执行追踪导出一份可解释的证据，而不必临时翻日志。
    - **与现有交付工具集成**：通过平台对外提供的稳定接口，把 OpenerX 中的 Task、审批、变更状态同步到公司既有的需求管理、发布管理或项目管理系统，而不要求团队换一套工具。
- **老板 / 高层管理者**
  - 关心：
    - 公司在 AI 上的投入有没有带来真实的业务回报，还是在买一堆工具堆概念；
    - 对外（客户、监管、董事会）被问到“你们怎么用 AI、有没有风险”时，能不能给出有据可查的回答；
    - 是否存在因为 AI 出事而放大的声誉、合规或法律风险，公司处于什么风险等级；
    - 不同部门用的 AI 系统能不能收敛成一套组织级平台，减少重复投入和管理盲区；
    - 下一阶段要不要继续加大 AI 预算、扩到哪些业务线，决策依据是什么。
  - 能给：按组织与项目汇总的用量账本、预算执行情况与成本分布、Task 状态与审批记录等治理事实、可对外呈现的审计事件与执行追踪证据，以及统一平台带来的组织级收敛视图。

## 8. 角色未来可能的合并与重整

上述六类角色是按目前大多数企业既有的组织分工来写的。随着 AI 真正进入正式研发流程，这些角色的边界会发生明显重整。下面给出几条可预期的合并/重塑方向，作为组织设计的参考，不是对现状的否定。

### 8.1 研发管理者 ←→ 内部产品与交付团队

- **趋势**：两边关心的问题会逐渐融合。研发管理者越来越需要回答交付状态和对外解释，内部产品与交付团队也必须看懂 AI 的执行过程，而不是只看最终工单。
- **可能的新角色**：**AI 交付负责人**，同时对"AI 参与下的需求能否按期按质交付"和"AI 参与过程对业务方可解释"负责。
- **对 OpenerX 的要求**：Task 既要承载工程视角（Session、执行记录、质量门槛），也要承载产品视角（需求映射、交付状态、对外说明）。

### 8.2 安全、合规 ←→ 平台工程

- **趋势**：AI 带来的风险大多数不是新类型，而是落在已有的访问控制、审计、事件响应体系里。为了降低摩擦，治理策略会越来越多地被平台工程直接编码到运行入口上，而不是事后审查。
- **可能的新角色**：**AI 平台治理工程师**，兼顾策略编写、门控 / 钩子实现、可观测性与应急响应。
- **对 OpenerX 的要求**：策略、审批、门控和钩子必须是平台工程可以配置和编排的对象，而不是合规团队独立维护的一份文档。

### 8.3 成本与运营 ←→ 老板 / 高层管理者

- **趋势**：AI 成本迅速从"工具杂项"变成"战略性资源投入"。老板关心的投资回报和成本与运营角色关心的明细费用，会在同一份视图里被质问，粗汇总已经不够。
- **可能的新角色**：**AI 成本治理负责人**，同时服务于季度预算决策与日常成本控制，把用量事实转译成投入产出语言。
- **对 OpenerX 的要求**：用量账本和预算不仅要支持明细分摊，还要支持跨项目汇总、趋势比较与按业务线呈现，便于给高层做决策。

### 8.4 产品 / 开发 / 测试 / 运维（在单个 Task 内部）

- **趋势**：当 Agent 具备跨角色能力后，"把一件事交给谁做"的决策会从"按部门分发"变成"按 Task 内的成员组合"。一个 Task 里可能同时有人类产品经理、人类开发者、测试 Agent、运维 Agent。
- **可能的新角色**：**任务协作者**，不再强调部门标签，而强调在某个 Task 中承担的职责和产出。
- **对 OpenerX 的要求**：成员（Member）模型必须统一覆盖人类与 Agent，角色（Role）主要作为内部权限与职责抽象，而不强行暴露给业务视图。

### 8.5 观察总结

- 角色合并的驱动力不是"裁掉某个岗位"，而是 AI 把原来需要跨部门串起来的信息链条收拢到了同一个统一平台里；
- 合并后的角色共同点是：同时要理解业务目标、执行过程和治理约束，这三件事过去经常由不同人分别负责；
- OpenerX 的目标是让这种角色重整变得可以在系统里落地，而不是只停留在组织架构图上。

## 9. 一段话总结

OpenerX 是一个让企业可以放心使用 AI Agent 的管理与治理平台：对用户可见的一侧围绕 Project、Task、Member、Agent 组织协作，后台通过“治理层与执行层分离”的方式，把并行比较、顺序执行、审批、预算、审计和追踪统一起来。它的目标用户不是个人开发者，而是需要把 AI 纳入正式研发流程的组织和团队。

## 附录 A：用到的概念速查

本附录只给出正文直接使用、或理解正文时必须对齐的业务、治理与协作名词的一句话含义，帮助目标用户快速对齐语境；系统组件和内部读链细节不在这里展开。完整、权威的定义与交叉引用见 [architecture/core-concepts-glossary.md](../architecture/core-concepts-glossary.md)。

### A.1 组织与协作

- **Organization（组织）**：系统中的最高治理单元，承载成员、项目、角色和治理策略。
- **Project（项目）**：工作边界、资源归属和任务承载的上层业务容器，Task 挂在 Project 下。
- **Member（成员）**：任务的参与主体，既包括人类成员，也包括 Agent 成员。
- **Agent（智能体）**：可被调度、可执行任务、受治理约束的自动化成员，是 Member 的一类。
- **Role（角色）**：系统内部用来表达职责与权限的概念，回答"谁能做什么"，对最终用户不强制暴露。
- **Skill（技能）**：成员或 Agent 的能力说明，用于描述擅长什么、适合做什么。

### A.2 执行与编排

- **Task（任务）**：用户可见的业务工作项，是运行时的主体对象。
- **Session（会话）**：某个 Task 下的一次具体执行分支，Task 可以有多个 Session。
- **Runtime（运行时）**：真正负责推进 Session 执行、读取消息并完成动作调用的执行层。
- **Session Operation（会话操作）**：Session 中一次具体动作的记录，例如 executor、judge、hook、resume 调用。
- **Workflow（工作流）**：定义模板、阶段规则、触发条件与治理约束的静态规则域，不是任务本身。
- **Workflow Stage（工作流阶段）**：工作流里的一个明确阶段，用来定义 Gate、Hook、审批与触发条件。
- **Execution Mode（执行模式）**：Task 或阶段采用的执行方式，如单次执行、并行比较、顺序执行。
- **Gate（门控）**：进入下一阶段前必须满足的条件，例如"所有审批通过"或"成本未超限"。
- **Hook（钩子）**：在关键事件发生时自动触发的动作，用来回答"此时系统要做什么"，可以返回 allow / deny / rewrite-prompt / switch-model 等决策。
- **Lifecycle Status（生命周期状态）**：Task 在业务层的稳定状态，如 draft / active / done / archived。

### A.3 治理与审计

- **Control Plane（控制平面）**：负责治理、审批、预算、审计和任务状态管理的组织级管理层。
- **Policy（策略）**：预定义的治理规则集合，用于权限、预算、审批与执行约束。
- **Approval（审批）**：对高风险动作或关键任务的人工审核与授权机制。
- **Audit Event（审计事件）**：可被记录、追溯与导出的行为事实，是对外解释与合规的基础。
- **Execution Trace（执行追踪）**：面向 Task 或 Project 的公开执行事实链，对外主要读取已经持久化的任务视图，而不是直接依赖 Runtime 的原始消息。

### A.4 成本与预算

- **Usage Ledger（使用账本）**：以只追加、不回写的方式记录模型调用与成本事实的账本，用于费用追溯与回放。
- **Cost（成本）**：模型调用、运行时权限使用或任务执行带来的费用消耗，和 Task / Session 绑定。
- **Budget（预算）**：对组织或项目的成本上限、周期与告警规则的治理约束。
