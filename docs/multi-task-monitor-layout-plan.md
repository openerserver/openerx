# 多任务监控台开发任务单

## 1. 文档目的

本文档将“多任务监控台布局方案”展开为一版可执行的开发任务单，用于前端实现、测试补齐和联调排期。

本文档覆盖：

- 本次改造的目标与边界
- 现有实现与代码落点
- 分阶段开发任务拆分
- 每项任务的交付物、验收标准、测试要求
- 推荐实施顺序与风险说明

本文档面向 Web UI、测试、产品评审，不作为最终 PR 描述。

## 2. 背景

当前多任务监控台已经具备以下能力：

- 自由拖拽任务窗口
- 自动导入运行中任务
- 显示任务概览与实时回复
- 自动编排避免明显重叠

但当前页面仍有两个核心问题：

1. 画布上的窗口虽然能排开，但任务之间的结构关系不清楚。
2. 现有“自动编排”只解决别遮挡，没有解决为什么这样排、用户该先看哪里。

因此，本次改造的核心不是继续优化纯几何排版，而是把监控台升级为“结构化监控画布”。

## 3. 目标

多任务监控台需要同时满足两类需求：

1. 观测：用户能快速识别哪些任务在运行、卡住、失败、完成。
2. 理解：用户能看清任务之间的分组、阶段差异、时间优先级和关注顺序。

本次开发目标是让用户在 3 到 5 秒内回答以下问题：

- 现在最该关注哪几个任务
- 哪些任务属于同一类状态或同一阶段
- 哪些任务最近仍在持续输出
- 哪些任务疑似停滞或已结束

## 4. 非目标

本次不做以下内容：

- 不做真正的依赖图建模
- 不做默认满屏关系连线
- 不做主任务 + 关联任务的中心辐射布局
- 不修改 BFF 或 Service 的数据模型
- 不重做整个多任务监控台视觉风格

结论：首批落地范围限定为 Web UI 侧的布局模式、结构提示层、活跃提示和相关测试补齐。

## 5. 现有实现与代码落点

当前主要实现集中在以下位置：

- `control-plane/web-ui/src/pages/MultiTaskMonitor.vue`
- `control-plane/web-ui/src/stores/task-monitor.ts`
- `tests/web-ui/MultiTaskMonitor.test.ts`
- `control-plane/web-ui/src/router/index.ts`

当前代码现状：

1. 页面顶部工具区已有“添加任务到监控台 / 筛选已投放任务 / 状态筛选 / 导入运行中 / 自动编排”。
2. 当前“自动编排”由 `MultiTaskMonitor.vue` 内部 `autoArrangeNodes()` 实现，本质是按列瀑布流重新摆放卡片。
3. 布局状态尚未抽象为 `layoutMode`，也没有结构提示层的独立数据模型。
4. `task-monitor` store 当前只维护节点位置、尺寸、层级、折叠状态，不维护布局模式或分组元数据。
5. 页面数据已经足够支撑第一批模式：任务状态、pipeline 阶段、最近活动时间、消息流状态都已能从现有接口与实时事件中推导。
6. 现有单测已覆盖页面加载、导入运行中、实时回复稳定性、避免重叠等基础能力，但未覆盖布局模式切换与结构提示。

结论：第一阶段不需要后端改造，可以直接在 Web UI 内完成。

## 6. 本次推荐方案

### 6.1 总体策略

将单一“自动编排”升级为“布局模式切换器”，保留自由拖拽能力，但新增结构化模式。

### 6.2 首批落地模式

首批实现以下 4 个模式：

1. 自由布局
2. 按状态编排
3. 按阶段编排
4. 按时间编排

其中：

- 自由布局：保留用户手动拖拽结果，不主动打乱已有位置。
- 按状态编排：按运行中、暂停中、异常或已完成分区。
- 按阶段编排：按当前 pipeline 阶段分区，未识别阶段归入“其他”。
- 按时间编排：按最近活动时间排序，最新者靠前。

### 6.3 首批结构表达

首批不做关系线，只做以下轻量结构表达：

- 分组背景
- 区域标题
- 区域内数量统计
- 活跃中或疑似停滞标签

## 7. 交付范围

本次任务单按 MVP 范围定义如下：

### 7.1 页面交互范围

- 顶部“自动编排”改为“布局模式切换”
- 增加“重置布局”动作
- 结构化模式下显示分区背景和标题
- 卡片头部固定显示状态、阶段、最近活动信息
- 增加“活跃中 / 疑似停滞”提示

### 7.2 布局逻辑范围

- 抽离布局模式计算逻辑
- 将自由布局与结构化布局分开处理
- 结构化布局切换时保留当前打开任务集合与折叠状态
- 再次应用同一模式时允许重新编排

### 7.3 测试范围

- 增加布局模式切换单测
- 增加按状态编排单测
- 增加按时间编排单测
- 增加结构提示层渲染单测
- 增加自由布局不被覆盖的单测

## 8. 产品规则

### 8.1 自由布局规则

- 不主动改变用户已拖拽位置
- 新任务加入时只寻找最近空位
- 点击“重置布局”后才回到系统建议位置

### 8.2 按状态编排规则

- 分区建议顺序：运行中、暂停中、异常或已完成
- 每个分区内部按最近活动时间倒序排列
- 若任务状态无法识别，归入“其他”

补充说明：当前实现虽然已经有状态分区，但存在两个实际问题：

- 同一屏内卡片宽度不一致，导致视觉节奏不稳定，也让分区背景与卡片边界难对齐。
- `按状态` 模式仍沿用接近“多列平铺”的思路，异常、已完成这类低优先级分区在窄画布下会变成很小的背景块，卡片与背景关系不明确。

因此，状态模式需要单独采用一版新的布局方案，而不是继续沿用当前通用 section 逻辑。

### 8.2.1 状态布局 V2 方案

状态模式改为“纵向泳道 + 等宽卡片 + 分区整行占位”，不再把所有状态当成并列的窄列来处理。

核心原则：

- 所有任务卡片在所有模式下保持统一宽度，禁止同屏内出现 320 / 336 / 360 等混杂宽度。
- 状态模式下，分区背景必须先于卡片排布确定，卡片只是填充到分区内部，不允许出现“卡片落在分区外缘”或“分区很窄但卡片很宽”的关系错位。
- 窄画布优先保证分区语义正确，其次才追求横向并列数量。

建议的状态泳道顺序：

1. 运行中
2. 已暂停
3. 异常
4. 已完成

建议的状态泳道形态：

- `运行中`：主泳道，默认放在最上方，整行展示；若数量多，可在泳道内部做 2 列等宽卡片瀑布。
- `已暂停`：次级泳道，放在运行中之后；数量少时保持单行，数量多时允许内部换列。
- `异常`：高警示泳道，不再缩成右侧小块；即使只有 1 个任务，也应独占一整行或与暂停共享同级整行区域。
- `已完成`：归档泳道，固定放在最下方；背景块横向铺满，卡片可以仍为等宽，但整体视觉弱化。

### 8.2.2 卡片尺寸规则

新的统一规则如下：

- 默认卡片宽度固定为一个常量，例如 350px。
- 自由布局、按状态、按阶段、按时间 4 种模式全部复用同一个卡片宽度常量。
- 允许高度因内容变化而自适应，但宽度不得因模式不同而变化。
- 状态模式内部若需要 2 列，列宽仍然等于统一卡片宽度，不允许为了塞进更多列而临时压窄卡片。

### 8.2.3 状态背景层规则

状态模式的背景层改为“整行分组板块”，每块板块包含：

- 状态标题
- 数量统计
- 说明文案
- 内部卡片容器区域

背景层不再仅仅作为绝对定位的描边框，而应与卡片容器共享同一套宽度和行高计算。

推荐做法：

- 每个状态分区先计算自己的行高，再决定下一个状态分区的起始 `y`。
- 分区背景高度必须由“标题区高度 + 卡片区实际占用高度 + 底部留白”共同决定。
- `异常` 与 `已完成` 的背景不能因为任务数少就压缩成一个窄列；它们至少应与当前画布主列宽保持一致。

### 8.2.4 窄画布回退规则

当画布可用宽度不足以容纳多状态并列时，状态模式必须回退为单列纵向泳道：

- 每个状态分区独占一整行。
- 每行内部卡片按统一宽度纵向堆叠。
- 分区之间保留固定垂直间距，例如 24px 到 32px。

结论：在当前类似 637px 可用宽度的画布下，`按状态` 不应尝试把 `异常` 与 `已完成` 做成左右并排板块，而应纵向堆叠。

### 8.2.5 新的状态模式视觉层级

为避免“异常 / 已完成”分区在同屏时层级混乱，建议统一为以下优先级：

- 运行中：最强背景与标题对比
- 已暂停：中性偏提醒
- 异常：高对比警示边框与标题，但仍占整行
- 已完成：最低对比度，弱化背景填充和标题说明

这里的重点不是把 `异常` 缩小，而是通过视觉语义强调它，同时通过整行占位保持结构稳定。

### 8.2.6 实施建议

状态布局从当前“通用 section 网格”中独立出来，单独实现 `applyStatusLaneLayout` 或等价函数。

建议拆成两层：

1. 先根据状态生成泳道模型：标题、说明、卡片集合、泳道高度、优先级。
2. 再基于真实画布宽度为每个泳道计算：起始 `x/y`、泳道宽度、泳道内部列数、卡片位置。

这样状态模式就不再被阶段模式、时间模式的通用列分区逻辑牵着走。

### 8.2.7 验收标准补充

新的状态布局方案需要额外满足：

- 同一屏内所有任务卡片宽度一致。
- 切换到 `按状态` 后，所有卡片都位于各自状态背景块内部。
- `异常`、`已完成` 在窄画布下不再显示为压缩的并排窄块。
- 分区背景高度与内部卡片总高度一致，不出现卡片压到相邻分区背景上的情况。
- 浏览器侧需要新增一组 `按状态` 专项截图/边界框回归。

### 8.3 按阶段编排规则

- 优先读取 `pipeline.summary.currentStageId`
- 若可解析到对应 stage label，则按 label 分组
- 若没有 pipeline 或阶段未知，归入“其他”

### 8.4 按时间编排规则

- 根据最近活动时间排序
- 最新活动任务排在首个可视区域
- 长时间无更新但仍为运行中的任务应显示停滞提示

### 8.5 活跃提示规则

- 最近 30 秒内有实时回复增量或任务事件更新：显示“活跃中”
- 最近 2 分钟无更新但状态仍为运行中：显示“疑似停滞”
- 已完成、失败、暂停任务不显示“疑似停滞”

## 9. 开发任务拆分

## 9.1 Epic A：布局模式状态抽象

### A1. 新增布局模式状态

目标：让监控台具备可持久化的 `layoutMode` 状态，而不是只有一个临时的自动编排按钮。

建议改动：

- 在 `task-monitor` store 新增布局模式状态
- 定义布局模式枚举：`free | status | stage | time`
- 提供 `setLayoutMode`、`resetLayout` 或等价 action
- 明确哪些状态进入持久化，哪些仅驻留页面内

交付物：

- store 层新增布局模式状态与操作方法
- 页面层可以读取和切换当前模式

验收标准：

- 页面刷新后能恢复最近一次布局模式
- 现有拖拽与折叠能力不受影响

### A2. 抽离布局计算入口

目标：将当前 `autoArrangeNodes()` 从单一瀑布流函数升级为统一编排入口。

建议改动：

- 将布局计算拆分为 `applyFreeLayout`、`applyStatusLayout`、`applyStageLayout`、`applyTimeLayout` 或同级函数
- 页面中只保留统一的布局切换和触发逻辑
- 估算卡片高度的逻辑保留在统一入口，避免四处重复

交付物：

- 页面内编排逻辑可按模式调用
- 后续新增模式时不需要改写主流程

验收标准：

- 切换布局模式时，当前节点集合能正确重排
- 原有“导入运行中”后自动排列能力仍正常

## 9.2 Epic B：顶部工具区改造

### B1. 将“自动编排”改为“布局模式切换器”

目标：让用户能显式理解当前画布是按什么规则在展示。

建议改动：

- 将顶部单个按钮改为模式选择器
- 选项至少包含：自由布局、按状态、按阶段、按时间
- 保留现有“导入运行中”和状态筛选

交付物：

- 顶部工具区新增布局模式选择控件
- 当前模式有明确文案反馈

验收标准：

- 用户切换后可立即看到布局变化
- 当前模式在页面可见，不需要靠猜测判断

### B2. 增加“重置布局”动作

目标：为自由拖拽与结构化重排之间提供明确恢复手段。

建议改动：

- 在顶部工具区增加“重置布局”按钮
- 自由布局下重置为系统推荐自由位置
- 结构化模式下重置为当前模式的标准排布

验收标准：

- 拖拽打乱后可一键恢复
- 重置不会关闭窗口、清空任务、重置折叠状态

## 9.3 Epic C：结构提示层实现

### C1. 为结构化模式增加分区背景与标题

目标：让用户不用逐个读卡片，也能先理解画布整体结构。

建议改动：

- 在画布层增加结构提示层
- 状态模式显示泳道背景、标题和数量
- 阶段模式显示阶段分区、标题和数量
- 时间模式显示时间方向提示或轻量刻度

说明：

- 结构提示层应当独立于卡片节点存在
- 它的优先级高于“把卡片再排整齐一点”

交付物：

- 结构化模式下可见的背景层或区块层
- 每个分区显示标题和任务数

验收标准：

- 用户不打开任何卡片也能分辨当前布局规则
- 分区标题与卡片分组结果一致

### C2. 定义分区元数据模型

目标：避免分区标题、边界、计数直接散落在模板计算中。

建议改动：

- 定义画布分区数据结构，如 `id`、`title`、`count`、`x`、`y`、`width`、`height`
- 每次应用结构化布局时同步生成分区元数据
- 模板根据该元数据渲染结构层

验收标准：

- 页面模板中不出现大量硬编码分区判断
- 后续新增模式时可复用同一结构层渲染方式

## 9.4 Epic D：三种结构化布局落地

### D1. 按状态编排

目标：优先支持最符合监控直觉的布局模式。

建议改动：

- 将任务分入运行中、暂停中、异常或已完成、其他
- 每组内按最近活动时间排序
- 组内保持紧凑网格或列式排布

优先级：P0

验收标准：

- 运行中任务稳定出现在首个高关注区域
- 异常任务不会和运行中任务混排
- 已完成任务不会挤占首屏高优先级区域

### D2. 按阶段编排

目标：让用户判断任务集中卡在哪个 pipeline 阶段。

建议改动：

- 从 pipeline 摘要中提取当前阶段标签
- 相同阶段归并到同一分区
- 未识别阶段统一进入“其他”

优先级：P1

验收标准：

- 同阶段任务可稳定归并
- 无 pipeline 数据时页面不报错
- 阶段标签缺失时能优雅降级

### D3. 按时间编排

目标：让值守场景快速看最近变化。

建议改动：

- 以最近活动时间为主排序键
- 时间最新者进入左上或首区域
- 可配合活跃或停滞标签强化优先级判断

优先级：P0

验收标准：

- 最近刚更新的任务排在最前面
- 长时间未更新任务明显靠后
- 相同时间粒度下顺序稳定，不频繁跳动

## 9.5 Epic E：卡片头部信息强化

### E1. 固定展示关键判断字段

目标：减少用户必须展开概览后才能判断任务状态的成本。

建议改动：

- 卡片头部固定展示任务标题、状态、阶段、最近更新时间
- 若空间不足，优先保留状态、阶段、最近更新时间
- 避免把弱信息塞进头部

验收标准：

- 默认视图下即可判断任务大致状态
- 展开概览不再是理解任务的前置动作

### E2. 增加活跃中或疑似停滞提示

目标：解决“任务虽然还在运行，但到底还活不活跃”的判断问题。

建议改动：

- 基于实时事件和最近更新时间推导活跃提示
- 在卡片头部或流区标题位置增加轻标签
- 仅使用轻量强调，不做强动画轰炸

验收标准：

- 实时增量到来时可看到活跃提示
- 运行中且长时间无更新时出现停滞提示
- 已结束任务不误报为停滞

## 9.6 Epic F：交互与行为一致性

### F1. 布局切换保留页面上下文

目标：切换模式只改变展示结构，不破坏用户当前工作状态。

建议改动：

- 保留已打开任务集合
- 保留卡片折叠状态和概览展开状态
- 不重置搜索词和状态筛选

验收标准：

- 切换布局模式后任务集合不丢失
- 用户展开的卡片不会被莫名重新折叠

### F2. 手动拖拽与结构化模式共存

目标：让自由调整与结构化规则共存，而不是互斥。

建议改动：

- 自由布局下拖拽结果视为用户主导位置
- 结构化模式下允许微调，但再次应用该模式时按规则重排
- 明确文案或交互反馈，避免用户误以为拖拽结果会永久绑定模式

验收标准：

- 自由布局下拖拽不被自动覆盖
- 结构化模式下再次应用时位置可恢复到规则布局

## 9.7 Epic G：测试与回归补齐

### G1. 补齐页面单元测试

建议新增用例：

- 切换到按状态模式后，节点按状态分区显示
- 切换到按时间模式后，最新活动任务排在前面
- 切换布局模式后，折叠状态仍保留
- 自由布局下拖拽后切回自由模式，不自动洗掉位置
- 结构提示层会显示标题和数量
- 活跃中与疑似停滞标签能按规则显示

建议修改文件：

- `tests/web-ui/MultiTaskMonitor.test.ts`

### G2. 补齐交互回归检查

最低回归范围：

- 页面初始化自动导入运行中任务
- 导入运行中任务后仍能正常布局
- 实时消息流渲染不回退
- 现有路由入口不受影响

建议执行命令：

- `bun run test:ui:file tests/web-ui/MultiTaskMonitor.test.ts`
- `bun run test:ui:file tests/web-ui/router.test.ts`

## 10. 实施顺序建议

推荐按以下顺序开发：

1. A1 + A2：先把布局模式状态和统一编排入口抽出来
2. B1 + B2：完成顶部模式切换器与重置动作
3. D1：先落地按状态编排
4. C1 + C2：补结构提示层和分区元数据
5. D3：补按时间编排
6. E1 + E2：补卡片关键信息与活跃提示
7. D2：补按阶段编排
8. F1 + F2：校正布局切换与拖拽共存规则
9. G1 + G2：补齐测试与回归

原因：

- 按状态和按时间的用户价值最高，且对现有数据依赖最小
- 阶段编排依赖 pipeline 标签质量，适合放到第二批
- 结构提示层应在首个结构化模式之后尽快补齐，否则用户仍难理解布局意图

## 12. 风险与注意事项

### 12.1 阶段标签稳定性风险

问题：`pipeline.summary.currentStageId` 可用，但阶段 label 是否稳定取决于实际 pipeline 数据。

建议：

- 阶段编排实现时必须带“其他”兜底
- 不要在第一版写死过多阶段名称映射

### 12.2 节点高度估算风险

问题：当前自动编排依赖卡片高度估算，结构化布局继续复用时可能出现轻微错位。

建议：

- 第一版允许近似排布
- 不要为像素级完美排版引入过重复杂度

### 12.3 实时事件频繁导致重排风险

问题：若实时事件一来就触发重排，页面会跳动，影响监控体验。

建议：

- 结构化模式切换时触发重排
- 普通实时更新只更新内容与活跃标签，不自动整体洗牌

### 12.4 自由布局与持久化冲突风险

问题：持久化节点位置后，模式切换与恢复策略容易混乱。

建议：

- 明确区分“用户自由位置”和“当前模式计算位置”
- 必要时为自由布局保存单独位置快照

## 13. 最终验收标准

本任务完成后，应满足以下结果：

1. 监控台顶部不再只有“自动编排”按钮，而是明确的布局模式切换。
2. 页面至少支持自由布局、按状态、按阶段、按时间 4 种模式。
3. 按状态和按时间模式具备清晰可见的结构提示层。
4. 卡片默认状态下即可快速判断状态、阶段和最近活动情况。
5. 用户可以识别活跃任务与疑似停滞任务。
6. 布局切换不会破坏当前任务集合与主要页面上下文。
7. 关键单测覆盖布局模式切换、结构提示层和活跃提示逻辑。

## 14. 结论

多任务监控台本次开发不应继续围绕“自动编排更聪明一点”展开，而应明确升级为“带结构提示的多模式监控画布”。

首批最值得投入的能力不是关系线，也不是更复杂的自由画布，而是：

- 布局模式切换
- 按状态编排
- 按时间编排
- 结构提示层
- 活跃或停滞提示

这条路径实现成本可控、与现有代码贴合度高，也最容易在第一版就显著提升多任务监控的可读性。
