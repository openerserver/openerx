# Boss Agent 专项设计文档

> 历史状态：本文件保留为历史讨论记录。
>
> 当前结论：OpenerX 不再单独存在“老板层”，原先归于“老板 Agent”的经营与治理职责已并回管理员成员体系。后续产品与系统设计不应再把老板 Agent 当作正式一等对象继续扩展。
>
> 命名映射：本文中的 `Boss Agent`、`BossParticipationMode`、`BossDecisionRecord`、`bossDecisions` 等术语，在当前方案中统一应理解为“管理介入 / 管理决策”的历史命名；新增设计应优先采用 `ManagementIntervention`、`ManagementParticipationMode`、`ManagementDecisionRecord`、`managementDecisions` 等命名。
>
> 阅读方式：本文件可用于追溯“管理介入能力”早期为何被抽象成 `boss-agent`，但不应再被视为当前主方案的命名规范来源。涉及现行产品语义、前后台边界和对象定义时，应以 [docs/organization-oriented-agent-operating-model.md](docs/organization-oriented-agent-operating-model.md)、[docs/organization-oriented-agent-frontend-information-architecture.md](docs/organization-oriented-agent-frontend-information-architecture.md) 与 [docs/organization-oriented-agent-technical-checklist.md](docs/organization-oriented-agent-technical-checklist.md) 为准。

> 适用范围：OpenerX 项目经营自动化、组织化研发协作、模板调度与阶段裁决能力演进
>
> 历史目标：定义老板 Agent 的职责边界、输入输出、升级规则和自动托管等级，使其成为项目级管理员的模型替身

## 1. 文档目标

本文档回答以下问题：

- 老板 Agent 在 OpenerX 中是什么
- 老板 Agent 和平台管理员、普通岗位 Agent 的边界是什么
- 老板 Agent 应该基于哪些输入做判断
- 老板 Agent 应该输出哪些可审计的项目级决策
- 哪些情况必须升级给人类
- 自动托管等级如何设计，如何逐步放权给老板 Agent

本文档聚焦老板 Agent 本身，不重复展开岗位角色清单和阶段状态机的全部细节。

## 2. 定义

老板 Agent 是项目级经营管理者，是项目管理员的模型替身。

但它不是所有任务的强制参与者。

在 OpenerX 中，老板 Agent 应当是可配置启用的项目经营角色：

- 在组织化协作模式中，老板 Agent 是核心中枢
- 在单兵模式中，老板 Agent 可以被降级为轻量建议者
- 在最简单的单人执行场景中，老板 Agent 甚至可以完全不参与

它不等于平台管理员，也不等于开发 Agent。

它对应现实 IT 公司中的以下复合角色：

- 项目负责人
- 研发经理
- 技术负责人
- 交付负责人

它的核心价值不是直接写代码，而是：

- 接项目
- 组团队
- 定流程
- 推进阶段
- 汇总结论
- 做项目级决策
- 在必要时升级给人类

## 3. 角色边界

### 3.1 与平台管理员的边界

平台管理员负责制度，老板 Agent 负责经营。

平台管理员负责：

- 角色与权限边界
- 模板库与模板治理规则
- 安全红线与审批标准
- 可用模型、工具和预算边界
- 自动托管授权范围

老板 Agent 不允许直接修改这些平台制度。

### 3.2 与普通岗位 Agent 的边界

普通岗位 Agent 负责专业结论，老板 Agent 负责项目级裁决。

例如：

- 产品 Agent 提供范围与验收标准
- 架构 Agent 提供方案与风险判断
- 开发 Agent 提供代码实现与自测结论
- 测试 Agent 提供验证与缺陷结论
- 安全 Agent 提供安全风险与审批建议
- 运维 Agent 提供发布与运行风险结论

老板 Agent 不替代他们的专业判断，而是消费这些判断并决定项目怎么走。

### 3.3 与人类的边界

老板 Agent 不是最终免责主体。

它在授权边界内自动推进项目，但在以下情况必须升级给人类：

- 越权
- 高风险
- 制度冲突
- 多方结论无法裁决
- 预算或合规边界被触发

## 4. 核心职责

老板 Agent 的职责建议划分为六类。

### 4.1 任务经营

负责判断：

- 任务是否立项
- 任务值不值得投入完整流程
- 复杂度和风险等级如何
- 当前任务是轻量协作还是完整团队协作

其中最后一项尤其关键：

老板 Agent 不只是在团队模式里调度组员，它还应判断当前任务是否根本不需要团队模式，而应直接退回到单兵模式。

### 4.2 模板调度

负责判断：

- 当前任务适合哪套工作流模板
- 是否从默认模板切换到更严格或更轻量的模板
- 是否需要增加安全、运维、设计等辅助岗位

### 4.3 团队编组

负责决定：

- 当前项目应启用哪些岗位角色
- 哪些岗位作为主责角色
- 哪些岗位作为参与角色
- 哪些岗位只在命中条件时插入

### 4.4 阶段推进

负责组织以下项目节奏：

- 需求澄清
- 方案评审
- 开发拆解
- 实施开发
- 集成验证
- 发布决策
- 发布后观察
- 复盘沉淀

### 4.5 项目级裁决

负责综合岗位结论，并输出项目级决策，例如：

- allow
- revise-and-continue
- needs-approval
- block
- pause
- escalate-human

### 4.6 异常升级

负责判断何时请求人类介入，而不是无限自动推进。

## 5. 输入模型

老板 Agent 不应只看任务原文，它应消费一组结构化项目上下文。

### 5.1 任务基础输入

- 任务标题
- 任务描述
- 任务来源
- 项目和仓库信息
- 任务优先级

### 5.2 分类与路由输入

- 任务分类结果
- 复杂度判断
- 风险等级初判
- 推荐模板列表
- 推荐角色编组

### 5.3 模板与阶段输入

- 当前项目绑定模板
- 候选模板及其约束
- 当前阶段
- 阶段进入条件与退出条件
- Gate 与审批要求

### 5.4 岗位结论输入

- 产品结论
- 架构结论
- 开发进度与实现结果
- 测试结论
- 安全结论
- 运维结论
- 发布结论

### 5.5 运行态输入

- Hook 执行记录
- 角色聚合结论
- Developer Change Requests
- 审批单状态
- 阻断原因
- 当前自动托管等级

## 6. 输出模型

老板 Agent 的输出必须是结构化、可审计、可被 UI 和后端消费的。

### 6.1 决策输出

建议老板 Agent 输出统一的项目级决策对象，至少包含：

- 决策类型
- 决策原因
- 置信度
- 触发依据
- 关联阶段
- 是否需要审批
- 是否需要升级给人类

### 6.2 调度输出

老板 Agent 还应输出：

- 选定模板
- 当前阶段目标
- 需要启用的岗位列表
- 当前主责岗位
- 需要补充触发的辅助岗位

### 6.3 治理输出

老板 Agent 应能产出：

- 审批建议
- 暂停建议
- 回退建议
- 修正建议
- 人类升级请求

### 6.4 审计输出

每次老板决策都应沉淀为审计事实，例如：

- 决策时间
- 输入摘要
- 输出摘要
- 决策证据
- 关联角色结论
- 是否被人工覆盖

## 7. 决策类型建议

建议老板 Agent 首批支持以下决策类型：

- `accept-task`：接受任务并进入项目流程
- `request-clarification`：要求补充信息
- `select-template`：选择或切换模板
- `form-team`：建立项目小组
- `advance-stage`：推进到下一阶段
- `hold-stage`：暂不推进，等待补充结论
- `request-revision`：要求开发或其他岗位修正
- `request-approval`：发起审批
- `pause-project`：项目暂停
- `rollback-stage`：回退到前一阶段
- `complete-project`：项目完成
- `escalate-human`：升级给人类

## 8. 升级规则

升级规则是老板 Agent 的核心安全边界。

### 8.1 必须升级的场景

以下场景必须升级给人类：

1. 平台制度变更
例如修改模板治理规则、角色权限规则、审批标准、安全红线。

2. 未授权高风险动作
例如高风险生产操作、破坏性命令、超预算调用、越权访问。

3. 结论冲突且无法裁决
例如安全 Agent 要求阻断，测试 Agent 给出通过，开发 Agent 声称已修复，但证据不足。

4. 低置信度关键决策
例如发布放行、跨系统大改、合规敏感任务等关键动作，但老板 Agent 置信度不足。

5. 明确要求人工确认的项目或阶段
当项目被设置为手动监督模式或特定阶段被标记为人工确认时，老板 Agent 只能提出建议。

### 8.2 可自动决策但需要留痕的场景

以下场景可以由老板 Agent 自动执行，但必须保留决策记录：

- 模板选择
- 阶段推进
- 常规修正请求
- 补充岗位插入
- 常规阻断与恢复建议

## 9. 协作模式与老板参与方式

老板 Agent 的设计必须支持不同协作模式下的不同参与强度。

### 9.1 单兵模式

特点：

- 默认由一个主执行 Agent 完成任务
- 不要求老板 Agent 常驻参与
- 其他岗位默认不介入，除非命中高风险规则或显式配置

在该模式下，老板 Agent 有三种可选参与方式：

- 不参与：系统直接由主执行 Agent 独立完成
- 旁路建议：老板 Agent 只在任务开始时给出模板或风险建议
- 异常介入：仅在阻断、审批、失败或高风险时介入

### 9.2 组织化协作模式

特点：

- 老板 Agent 是项目经营中枢
- 多个岗位 Agent 按阶段参与
- 老板 Agent 负责团队编组、阶段推进和项目级裁决

### 9.3 混合模式

特点：

- 平时按单兵模式运行
- 命中高风险、发布、生产、跨系统改造、合规或大范围变更时，自动切换到组织化协作
- 老板 Agent 在切换发生时接管项目经营工作

### 9.4 配置原则

平台必须允许管理员灵活配置：

- 某个项目是否默认启用老板 Agent
- 某个模板是否强制需要老板 Agent
- 某个任务类型是否允许跳过老板 Agent
- 哪些条件下必须从单兵模式升级到老板接管模式

这意味着老板 Agent 不是全局强制开关，而是一个可按项目、模板、任务类型和风险等级动态启用的管理角色。

## 10. 自动托管等级

自动托管等级定义老板 Agent 的放权范围。

自动托管等级建立在协作模式之上，而不是替代协作模式：

- 协作模式决定老板 Agent 是否参与，以及参与强度
- 自动托管等级决定老板 Agent 一旦参与后，可以自动做多少决定

### 10.1 L0 手动监督模式

特点：

- 老板 Agent 只做建议，不做最终确认
- 模板选择、关键阶段推进、发布决策都需要人类确认
- 适合试点项目、敏感项目和高风险场景

老板 Agent 的定位：

- 智能项目助理

### 10.2 L1 半自动经营模式

特点：

- 老板 Agent 自动完成常规任务受理、模板建议、团队编组和常规阶段推进
- 高风险审批、关键发布和制度冲突仍交给人类
- 适合大多数日常研发项目

老板 Agent 的定位：

- 受监管的项目经理

### 10.3 L2 全自动托管模式

特点：

- 老板 Agent 在授权边界内自动完成项目经营
- 只在越权、重大异常和低置信度关键决策时升级给人类
- 适合规则稳定、风险受控、可充分审计的项目

老板 Agent 的定位：

- 自动化项目负责人

## 11. 典型工作链路

### 11.1 接单与立项

老板 Agent 接收任务后：

1. 判断任务类型和复杂度
2. 判断是否需要完整团队
3. 选择模板候选
4. 输出是否立项和初始项目编组建议

### 11.2 方案阶段

老板 Agent 收到产品和架构结论后：

1. 判断是否进入实现阶段
2. 判断是否需要安全前置介入
3. 判断是否需要补充澄清或回退

### 11.3 开发阶段

老板 Agent 在开发阶段主要负责：

1. 跟踪主责开发岗位进度
2. 判断是否插入测试、安全或设计复核
3. 汇总修正请求并决定是否继续推进

### 11.4 发布阶段

老板 Agent 在发布阶段主要负责：

1. 汇总测试、安全、运维和发布岗位结论
2. 判断是否满足发布条件
3. 决定直接发布、审批后发布、延期或回退

## 12. 与现有系统能力的衔接

### 12.1 与工作流模板的关系

老板 Agent 不替代模板，而是消费模板、选择模板、切换模板并驱动模板运行。

模板定义制度化流程，老板 Agent 负责根据项目情况在允许范围内调度这些流程。

### 12.2 与 Hook 的关系

Hook 是阶段治理动作，老板 Agent 是项目级决策者。

Hook 的输出可以成为老板 Agent 的输入，但老板 Agent 不等于 Hook 本身。

### 12.3 与角色聚合器的关系

角色聚合器负责把同岗位多个底层 Agent 的结论合成一个岗位结论。

老板 Agent 不直接裁决多个底层实例，而是消费聚合后的岗位结论。

### 12.4 与审批系统的关系

老板 Agent 可以发起审批建议，但是否最终通过，取决于平台授权和审批规则。

## 13. 页面与产品呈现建议

### 13.1 任务详情页

建议增加“老板判断”视图区块，展示：

- 当前老板结论
- 当前阶段
- 当前主责岗位
- 最近一次决策原因
- 是否触发升级或审批

### 13.2 项目编排页

建议展示：

- 当前项目老板 Agent
- 当前自动托管等级
- 老板最近一次模板选择与切换原因
- 当前团队编组

### 13.3 管理设置页

建议增加老板治理配置：

- 默认老板 Agent
- 自动托管等级
- 协作模式默认值
- 老板可切换模板的范围
- 老板可自动推进的阶段范围
- 必须人工确认的动作列表

## 14. 首批实施建议

### 14.1 第一阶段

先交付老板 Agent 的“可见性”，包括：

- 页面上明确有老板角色
- 任务中可以看到老板判断
- 模板推荐和阶段推进由老板输出建议

### 14.2 第二阶段

交付老板 Agent 的“项目经营能力”，包括：

- 自动模板选择
- 自动团队编组
- 自动阶段推进建议
- 自动修正请求收口

### 14.3 第三阶段

交付老板 Agent 的“托管能力”，包括：

- 自动托管等级
- 自动审批建议
- 自动升级规则
- 更完整的项目级裁决记录

## 15. 成功标准

老板 Agent 设计成功的标志包括：

1. 用户能明确理解“老板是谁、老板负责什么”。
2. 用户能根据项目情况选择单兵模式、组织化协作模式或混合模式。
3. 老板 Agent 与平台管理员、开发 Agent、辅助岗位 Agent 的边界清晰。
4. 老板 Agent 的关键决策都有结构化输入和结构化输出。
5. 升级规则明确，系统不会在越权场景中静默自动决策。
6. 自动托管等级和协作模式都可配置，团队可按风险逐步放权。

## 16. 总结

老板 Agent 不是一个更强的开发模型，而是一个项目级经营角色。

它的价值不在于替代所有岗位，而在于把模板、阶段、岗位、审批和升级整合成一套可经营、可审计、可逐步放权的项目管理能力。

在 OpenerX 的组织化方向中，老板 Agent 是连接“平台制度”和“团队执行”的关键中枢。
