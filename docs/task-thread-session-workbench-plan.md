# Task Thread / Session Workbench 设计方案

> 目标：把 OpenerX 从“任务执行页”升级为“任务线程工作台”。
>
> 主力用户路径不再是“新建很多任务”，而是“启动一个任务后，在该任务下持续续跑、分叉、对比、收敛”。

## 1. 背景与问题

当前任务详情页的主要问题：

1. `续跑` 已存在，但只是一个附属弹窗动作，不是页面核心交互。
2. 页面最大面积给了任务图、编排决策、表格信息，而不是模型回复正文。
3. `Session` 只是历史列表，没有升级为用户真正操作的上下文对象。
4. 缺少 `fork` 能力，无法从某个上下文分叉出新方案。
5. 缺少面向“同时盯多个任务”的工作台形态，用户只能单页来回切。

当前代码现状：

1. 任务详情页为单路由页面，只有一个 `router-view` 容器，暂无内建多窗能力。
2. 任务详情页已有 `会话历史 + 续跑` 基础，但续跑仅支持给某个 session 追加 prompt。
3. BFF 已支持列出任务相关 sessions、读取 session messages、继续当前 session。
4. OpenCode Runtime 文档中有 `fork` 能力，但 OpenerX 还未接入。

## 2. 产品定位

重新定义三个对象：

1. `Task`：一件长期要完成的事情，是容器。
2. `Session`：这件事情的一条执行线程，是上下文本体。
3. `Branch`：基于某个 session 或某条消息分叉出的替代执行路径。

用户心智应改为：

1. 我进入的是一个“任务线程工作台”。
2. 我当前正在一个分支里和模型持续协作。
3. 如果我想尝试另一种思路，就从这里分叉。
4. 如果我同时处理多个任务，就把多个任务开成多个工作窗。

## 3. 核心设计原则

1. 回复优先：页面最大面积必须给模型回复与会话内容，而不是外围元数据。
2. 续跑优先：默认动作是继续当前分支，而不是重新创建新任务。
3. 分支显式：fork 后形成清晰的 session 分支树。
4. 多任务并行：支持同屏查看多个任务工作窗。
5. 深链路可恢复：每个任务窗、session、branch 都能通过 URL 恢复。

## 4. 目标交互模型

### 4.1 单任务模式

单任务详情页升级为三栏工作台：

1. 左栏：`分支 / Session 树`
2. 中栏：`模型回复主视图`
3. 右栏：`上下文 / 任务图 / 变更 / 治理信息`

其中中栏为最大区域，占桌面宽度的 50% 到 65%。

### 4.2 多任务模式

在应用顶层新增 `Task Workbench` 概念，支持多个任务子窗口并行：

1. `标签页模式`：多个任务作为顶部 tabs
2. `分屏模式`：左右或四宫格显示多个任务窗
3. `弹出模式`：使用新浏览器窗口打开某个任务，作为轻量降级方案

建议顺序：

1. 先做应用内 tabs
2. 再做双栏分屏
3. 最后做自由拖拽子窗口

## 5. 单任务页信息架构

### 5.1 左栏：Session / Branch Tree

展示内容：

1. `Main` 主分支
2. 由 fork 产生的各子分支
3. 每个分支的状态：`running / paused / completed / failed`
4. 是否当前活跃分支
5. 最近更新时间
6. 简短摘要：最近一次用户指令或最近一次模型答复摘要

每个分支节点操作：

1. `继续此分支`
2. `从此分叉`
3. `设为当前主分支`
4. `查看改动`
5. `归档分支`（后续阶段）

### 5.2 中栏：模型回复主视图

这是新版页面的核心。

展示对象：当前选中 session 的消息流与步骤流。

优先级：

1. 模型文本回复
2. 用户输入内容
3. 工具调用摘要
4. 执行事件时间线

设计要求：

1. assistant 回复使用接近聊天界面的长文阅读布局。
2. 支持 markdown 渲染、代码块高亮、折叠长输出。
3. 工具调用默认折叠，仅显示摘要，如 `读取 3 个文件`、`执行 bun test`。
4. 每条 assistant/user 消息旁提供操作：
   1. `从这里分叉`
   2. `复制为续跑提示`
   3. `引用到输入框`
5. 页面底部固定 `续跑输入框`，默认针对当前选中分支。

推荐结构：

1. 顶部：当前分支标题 + 状态 + 快速动作
2. 中部：消息流
3. 底部：固定输入栏

固定输入栏应包含：

1. 多行 prompt 输入框
2. `继续当前分支` 主按钮
3. `从当前上下文分叉后执行` 次按钮
4. 可选的 `引用最近回答` 快捷按钮

### 5.3 右栏：任务上下文与控制信息

右栏保留现有能力，但降为辅助区：

1. 仓库、分支、base revision、工作目录
2. 治理与身份上下文
3. DAG 任务图
4. 变更统计、commit 信息
5. 编排决策与 hook 记录

原则：这些信息可折叠、可切换 tab，但不应抢占模型回复区域。

## 6. 续跑设计

### 6.1 续跑作为主力动作

续跑必须从“弹窗动作”升级为页面主操作：

1. 默认总是针对 `当前选中分支`
2. 用户不需要先打开弹窗再输入
3. 输入框始终可见
4. 输入后立即在消息流里出现新的 user message 占位

### 6.2 续跑的行为定义

`Continue` 不创建新 session，只是向当前 session 追加一条新 prompt。

适用场景：

1. 让模型继续未完成任务
2. 修正刚才回答的偏差
3. 补充约束条件
4. 追加验证要求

### 6.3 续跑文案建议

主按钮使用：

1. `继续当前分支`
2. `继续执行`

避免只写 `续跑`，因为普通用户对该词理解不稳定。

## 7. Fork 设计

### 7.1 Fork 的产品定义

Fork = 从某个分叉点之前的历史继承上下文，生成一条新分支。

继承：

1. 分叉点之前的消息历史
2. 分叉点之前的工具结果
3. 分叉点之前的上下文注入结果

不继承：

1. 分叉点之后的消息
2. 分叉点之后的工具调用
3. 分叉点之后的代码变更结果

### 7.2 两种 fork 入口

1. `Session 级 fork`
   1. 从当前 session 最新位置分叉
   2. 适合作为 MVP

2. `消息级 fork`
   1. 从某条 user/assistant message 分叉
   2. 适合中后期

### 7.3 Fork 后的交互

用户点击 `从这里分叉` 后：

1. 创建新 branch session
2. 自动切换到新分支
3. 在输入框中预填新指令，或允许用户编辑后提交
4. 左侧分支树新增节点

### 7.4 Fork 的用户价值

1. 试验另一套实现方案
2. 以同一上下文验证不同模型策略
3. 保留“安全方案”同时探索“激进方案”
4. 从关键历史节点回头重走

## 8. 多任务子窗口工作台

### 8.1 目标

用户可以同时盯住多个任务，而不是在列表页和详情页之间来回切换。

### 8.2 设计分层

#### 第一层：应用内任务标签页

顶层增加 `Task Workbench`：

1. 打开任务详情时，不强制替换当前页面，而是在工作台中新增一个 task tab
2. 每个 tab 显示：任务标题、状态、小红点、当前分支名
3. tabs 可固定、关闭、批量关闭其他

#### 第二层：任务分屏

支持将一个 task tab `拆分到右侧`，形成双栏：

1. 左窗任务 A
2. 右窗任务 B
3. 各自有独立 session 选中状态和输入框

适合：

1. 对比两个任务
2. 一边观察主任务，一边处理故障任务

#### 第三层：自由子窗口

后续可做浮动子窗口系统：

1. 最小化
2. 拖拽
3. 四宫格排列

但这不是 MVP。

### 8.3 浏览器多窗口的降级支持

由于当前路由天然支持深链路，MVP 阶段可以先支持：

1. `在新标签页打开任务`
2. `在新窗口打开当前分支`

URL 建议支持：

1. `/tasks/:taskId?session=:sessionId`
2. `/tasks/:taskId?session=:sessionId&branch=:branchId`

这样即便应用内多窗还未完成，用户也可以通过浏览器多标签并行工作。

## 9. 页面布局建议

### 9.1 桌面端布局

推荐比例：

1. 左栏 20% 到 24%
2. 中栏 52% 到 60%
3. 右栏 20% 到 28%

中栏必须是最大的连续区域。

### 9.2 移动端 / 窄屏降级

1. 默认单栏
2. 顶部切换：`分支` / `对话` / `上下文`
3. 底部续跑输入框固定

## 10. 数据模型建议

> 历史方案注记：本节保留的是早期 workbench 设计阶段的建模设想，不代表当前实现。
> 当前 branch lineage 已由 `conversation_sessions.parent_session_id` 与 `project_tree_nodes(node_type=session)` 协同表达，`task_sessions` 旧表也已下线。

在当时的方案阶段，曾判断旧 `tasks` 表只有单个 `sessionId`，不足以表达 branch tree，因此提出过新增 `task_sessions` 表的设想：

| 字段 | 说明 |
|------|------|
| `id` | 记录主键 |
| `task_id` | 所属任务 |
| `runtime_session_id` | OpenCode session ID |
| `parent_runtime_session_id` | 父 session，root 为 null |
| `forked_from_message_id` | 从哪条消息分叉，可空 |
| `branch_name` | 分支名，可选 |
| `source_type` | `root` / `fork` / `sub_session` |
| `is_active` | 是否当前活跃分支 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |
| `archived_at` | 归档时间，可空 |

补充说明：

1. 历史设想里，`continue` 不创建新 session，不必新增 `task_sessions` 记录。
2. 历史设想里，`fork` 才会新增一条 `task_sessions`。
3. 历史设想里，`tasks.sessionId` 可保留，作为当前活跃分支的快捷引用；当前实现已改由 task-domain / branch lineage 主读链承担这部分语义。

## 11. 后端接口建议

### 11.1 保留现有接口

继续保留：

1. `GET /api/tasks/:taskId/sessions`
2. `GET /api/tasks/:taskId/sessions/:sessionId/messages`
3. `POST /api/tasks/:taskId/continue`

### 11.2 新增接口

#### A. Fork 当前 session

`POST /api/tasks/:taskId/sessions/:sessionId/fork`

请求体：

```json
{
  "messageId": "optional-message-id",
  "title": "可选标题",
  "activate": true,
  "prompt": "可选，fork 后立即发送的首条指令"
}
```

响应体：

```json
{
  "ok": true,
  "sessionId": "new-session-id",
  "parentSessionId": "old-session-id",
  "forkedFromMessageId": "msg_xxx",
  "activated": true
}
```

#### B. 获取 session 分支树

`GET /api/tasks/:taskId/session-tree`

返回：

1. 当前任务的 session 节点
2. 父子关系
3. active session
4. 分支状态与摘要

#### C. 激活某个分支

`POST /api/tasks/:taskId/sessions/:sessionId/activate`

作用：

1. 将该分支设为当前主工作分支
2. 同步更新 `tasks.sessionId`

#### D. 多任务工作台布局持久化

`GET /api/workbench/layout`

`PUT /api/workbench/layout`

用于保存：

1. 已打开的 task tabs
2. 分屏布局
3. 每个 pane 当前选中的 taskId / sessionId

## 12. Runtime 接入建议

### 12.1 Continue

继续使用当前模式：

`POST /session/:id/prompt_async`

### 12.2 Fork

优先接入 OpenCode Runtime 原生 fork：

`POST /session/{id}/fork`

并支持可选的分叉 messageId。

### 12.3 Fork 的降级方案

如果 runtime fork 暂未稳定接入，MVP 可采用近似实现：

1. 读取原 session 到分叉点前的 messages
2. 创建新 session
3. 将历史压缩为 bridge context 注入
4. 再发送 fork 后的新 prompt

这不是严格的原生 fork，但足够支撑产品验证。

## 13. 前端落地建议

### 13.1 第一阶段：重做任务详情页

目标：让 `继续当前分支` 成为主操作。

改造点：

1. 把当前 `会话历史` 从表格改为左侧 session 列表 / 树
2. 把中间区域改成消息流，优先显示 assistant 回复正文
3. 把续跑弹窗改为页面底部固定输入框
4. 右侧收纳任务图、上下文、治理、变更
5. URL 支持 `sessionId` 选中态

### 13.2 第二阶段：补 fork

1. 增加 session 级 fork
2. 左侧树显示 parent-child 关系
3. 支持切换 active branch

### 13.3 第三阶段：多任务工作台

1. 顶层 tabs
2. 支持双栏分屏
3. 状态徽标、未读回复提醒

### 13.4 第四阶段：消息级 fork 与对比

1. 从 message 上分叉
2. 分支间结果对比
3. 分支归档

│ 任务标题 / 当前分支 / 状态 / 打开到新标签页 / 分屏                 │
├───────────────┬───────────────────────────────────┬─────────────────┤
│ Session Tree  │ 模型回复主视图                    │ 上下文 / 图 /   │
│               │                                   │ 变更 / 治理     │
│ Main          │ assistant 回复                    │                 │
│ ├─ Branch A   │ user 追问                         │ 任务图          │

## 15. 风险与注意点

1. 如果没有 session lineage 持久化，前端树结构会不稳定。
2. 如果 fork 只靠 title 约定而不落库，后续排障成本会很高。
3. assistant 回复作为主视图后，工具长输出必须折叠，否则阅读体验会再次被噪声淹没。
4. 多任务工作台需要控制实时订阅数量，避免 WebSocket 事件过多。

## 16. 建议结论

> 历史优先级说明：以下排序反映的是该方案形成时的产品/实现建议，不代表当前仓库仍计划引入 `task_sessions` 作为主线结构。

优先级建议：

1. 第一优先：把 `TaskDetail` 改为 `回复主视图 + 固定续跑输入框 + session 列表`
2. 第二优先：当时曾建议引入 `task_sessions` 与 `session-tree`（历史称呼），接入 session 级 fork；当前已由 branch lineage + tree/session 节点模型替代
3. 第三优先：实现应用内 `Task Workbench` tabs + 双栏分屏
4. 第四优先：消息级 fork、分支对比、归档

结论：

OpenerX 不应继续把任务详情页当成“执行结果说明页”，而应把它升级为“长期协作工作台”。在这个工作台里，`模型回复正文` 是主内容，`继续当前分支` 是主动作，`fork` 是关键探索能力，`多任务子窗口` 是面向真实高频用户的生产力层。
