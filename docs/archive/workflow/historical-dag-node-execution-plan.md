# Historical: 统一 Workflow 执行主方案

> 状态：已归档。
>
> 当前唯一维护版本为 [../../dag-node-execution-plan-v2.md](../../dag-node-execution-plan-v2.md)。
>
> 原因：本文件仍保留了“Stage 内 Node Graph”这一中间态设计；当前代码、migration 与数据库已收口为“Workflow Stage + Hook + parallel/sequential execution”主方案，不再保留 DAG 兼容语义。

## 1. 要解决的问题

当前系统同时存在两种推进结构：

1. Workflow 阶段状态机
2. Runtime 生成并同步到控制面的 task graph

这导致四个直接问题：

1. Workflow 在表达 `clarify/design/implement/verify`
2. DAG 也在表达 `Requirements gathering/Architecture and module design/Implementation of core features`
3. 用户看到的是两套都像“主流程”的结构
4. 真正能执行的却只有对话续跑，而不是节点推进

因此，当前问题不只是“DAG 不能执行”，而是“Workflow 与 DAG 语义重复且执行断层”。

## 2. 方案结论

本方案的核心结论如下：

1. Workflow 保留为唯一顶层主状态机
2. Node Graph 不再作为独立产品能力存在
3. DAG 保留为 Workflow 某些阶段内部的执行图能力
4. 顶层治理、审批、阻断、回退统一挂在 Workflow/Stage 上
5. 细粒度依赖、重试、分叉、回写统一挂在 Stage 内部 Node 上

换句话说：

1. 不再是 `Workflow + DAG` 两套平级系统
2. 而是 `Workflow -> Stage -> Node Graph` 一套分层体系

## 3. 顶层统一模型

### 3.1 统一对象模型

建议将执行模型统一为以下五层：

```text
Task
  -> WorkflowRun
       -> WorkflowStageRun
            -> StageExecutionMode
            -> WorkflowStageNode
            -> WorkflowStageEdge
```

### 3.2 对象职责

#### A. Task

任务本身，承载业务目标、原始描述、项目归属、参与人和最终结果。

#### B. WorkflowRun

任务在控制面上的唯一执行容器。

职责：

1. 记录当前模板
2. 记录当前阶段
3. 记录整体状态
4. 作为顶层审计与治理对象
5. 在任务创建或模板实例化时，承接系统预生成的阶段任务骨架

#### C. WorkflowStageRun

阶段实例，是系统主推进单位。

职责：

1. 表示当前处于哪个阶段
2. 管理阶段状态，例如 `pending/running/blocked/waiting-approval/completed`
3. 承载阶段产物、Gate、审批、失败恢复信息
4. 作为“阶段初始任务”的落点，支持任务创建时即预生成

#### D. StageExecutionMode

阶段执行模式。

建议首批支持两种：

1. `sequential`
   - 阶段内部不展开节点图
   - 该阶段直接由单次执行或少量顺序动作完成

2. `graph`
   - 阶段内部展开节点图
   - 允许节点依赖、节点级重试和节点级回写

#### E. WorkflowStageNode / WorkflowStageEdge

仅当阶段为 `graph` 模式时存在。

职责：

1. 表示阶段内部的子任务
2. 表示节点依赖顺序
3. 记录节点级状态、输出、失败原因与执行上下文

## 4. Stage 与 Node 的分层关系

### 4.1 Stage 负责什么

Stage 回答的是：

1. 当前任务处于哪个阶段
2. 当前阶段能否进入下一阶段
3. 当前阶段是否需要审批或阻断
4. 当前阶段应该产出什么内容

### 4.2 Node 负责什么

Node 回答的是：

1. 这个阶段内部有哪些执行单元
2. 哪个节点可以先执行
3. 节点之间的依赖是什么
4. 某次执行到底落到了哪个节点

### 4.3 两者的边界

必须遵守以下边界：

1. Stage 不描述细粒度实现依赖
2. Node 不重复描述完整主流程阶段
3. Stage 是治理与主推进单位
4. Node 是阶段内执行与追踪单位

### 4.4 一个典型例子

以功能开发模板为例：

1. Workflow 阶段顺序为：
   - `intake`
   - `clarify`
   - `design`
   - `plan`
   - `implement`
   - `verify`
   - `release`

2. `clarify` 阶段通常使用 `sequential`
   - 直接输出需求摘要、范围边界、验收标准

3. `implement` 阶段可使用 `graph`
   - Node A：实现接口
   - Node B：调整数据层
   - Node C：补测试

这样以后：

1. Workflow 告诉用户现在在 `implement`
2. Node Graph 告诉用户 `implement` 阶段内部先做哪个节点

## 5. 哪些阶段允许展开节点图

### 5.1 默认不展开节点图的阶段

以下阶段默认使用 `sequential`：

1. `intake`
2. `clarify`
3. `design`
4. `retrospective`
5. `done`
6. `cancelled`

原因：

1. 这些阶段的核心价值是阶段性判断与产物沉淀
2. 通常不需要复杂依赖图
3. 用图反而会让语义变重

### 5.2 默认允许展开节点图的阶段

以下阶段允许按模板或任务复杂度展开为 `graph`：

1. `plan`
2. `implement`
3. `verify`
4. `release`
5. `post-release`

原因：

1. 这些阶段更容易出现多个子步骤和依赖关系
2. 这些阶段更需要节点级重试、失败恢复和进度追踪

### 5.3 首批建议

第一阶段建议只在 `implement` 开启节点图。

原因：

1. 收益最直接
2. 用户最容易理解
3. 最能体现节点依赖和节点级回写价值
4. 避免一开始把所有阶段都图化，导致系统变重

## 6. 用户视角设计

### 6.1 普通用户看到什么

普通用户默认看到的是阶段，不是节点图全貌。

默认视图：

1. 当前阶段
2. 当前阶段状态
3. 当前阶段产物
4. 若该阶段启用了节点图，则显示“阶段内执行节点”摘要

如果阶段为 `graph` 模式，则在工作台中显示：

1. 当前阶段：例如 `implement`
2. 当前节点：例如 `补齐 Web UI 测试`
3. 当前节点状态：`待执行/运行中/失败/已完成`
4. 主动作：`执行当前节点`
5. 辅动作：`继续当前分支`

### 6.2 普通用户如何使用

普通用户的使用方式应尽量简单：

1. 进入任务工作台
2. 先看当前处于哪个 Workflow 阶段
3. 如果当前阶段未展开节点图，则继续等待阶段结果或补充对话
4. 如果当前阶段已展开节点图，则只关注“当前节点”与“下一步动作”
5. 需要推进阶段内执行时，点击 `执行当前节点`
6. 需要补充自然语言说明时，使用 `继续当前分支`

普通用户不需要理解数据库模型，只需要理解：

1. 阶段是大步骤
2. 节点是阶段内部的小步骤

普通用户还可在任务级执行以下受控操作：

1. 对当前任务的 `graph` 阶段手工设计节点图
2. 调整节点标题、依赖关系和完成标准
3. 提交并运行自己设计的阶段节点图

限制规则：

1. 只能在当前任务范围内生效，不直接修改管理员发布的模板
2. 只能编辑被模板标记为允许用户自定义的阶段
3. 不能越过模板定义的 Gate、审批和阶段顺序
4. 一旦开始运行当前节点图，普通用户不能随意改写运行中的节点

### 6.3 管理员看到什么

管理员应拥有完整配置视图，能看到：

1. Workflow 模板
2. 各阶段的执行模式
3. 哪些阶段允许展开节点图
4. 节点图生成方式
5. 自动推进策略
6. Gate 与审批策略

管理员在模板发布页还应看到：

1. 发布后将预生成哪些阶段任务
2. 每个阶段的初始状态
3. 哪些阶段仅生成骨架，哪些阶段允许立即进入可执行状态

### 6.4 管理员如何使用

管理员的主要工作不是“手工点每个节点”，而是定义系统策略。

管理员需要完成以下配置：

1. 创建或维护 Workflow 模板
2. 为每个阶段指定默认执行模式：`sequential` 或 `graph`
3. 指定允许展开节点图的阶段
4. 为 `graph` 阶段配置节点图生成方式：
   - 规则生成
   - 模型生成后校验落库
5. 配置节点级自动推进、审批和失败恢复策略
6. 决定普通用户是否可以看到节点图详情或只看到当前节点摘要

管理员发布模板后，系统应自动完成以下动作：

1. 将模板发布为可实例化版本
2. 按阶段顺序创建初始 `WorkflowStageRun`
3. 为每个阶段生成初始任务骨架
4. 将首个可进入阶段标记为 `pending` 或 `running`
5. 将后续阶段标记为 `pending`，等待前置阶段完成后激活

这里的“初始任务”不是立即全部执行，而是立即生成可见、可追踪、可治理的阶段实例。

## 7. 统一后的产品规则

### 7.0 三层权限模型

系统按以下三层权限治理 Workflow 与阶段节点图：

1. 普通用户
   - 可查看完整阶段路径
   - 可继续当前分支
   - 可执行当前节点
   - 可在允许范围内为当前任务设计阶段节点图并运行

2. 项目管理员
   - 可维护项目级模板绑定与执行策略
   - 可暂停、中止、阻断、恢复当前阶段
   - 可从已完成节点重新开分支
   - 可决定哪些阶段允许普通用户自定义节点图

3. 系统管理员或审批角色
   - 可发布模板版本
   - 可强制回退阶段
   - 可废弃当前节点图并重建
   - 可覆盖默认续接策略与异常修复策略

### 7.1 两个动作继续保留，但含义收口

`继续当前分支`：

1. 继续当前 session 对话
2. 不直接改变 Node 状态
3. 可作为阶段补充说明入口

`执行当前节点`：

1. 仅在当前 Stage 为 `graph` 时显示
2. 必须绑定明确的 `stageRunId` 与 `nodeId`
3. 必须将执行结果回写到该节点
4. 节点完成后由 Stage 决定是否自动推进

### 7.2 运行中受控干预规则

节点一旦进入 `running`，必须遵守以下规则：

1. 普通用户不能直接改写运行中的节点语义
2. 普通用户只能等待完成、查看进度，或请求停止于安全点
3. 项目管理员可以暂停、中止或将当前 Stage 置为 `blocked`
4. 系统管理员或审批角色可以执行回退、废弃节点图、重新规划

因此，系统只允许从稳定状态继续：

1. `completed`
2. `failed`
3. `blocked`
4. `paused`

若某阶段节点图产生多个结果分支，则：

1. 普通用户只能从这些已落定的合法结果分支继续
2. 项目管理员可以从已完成节点重新开分支
3. 系统管理员可以执行更高权限的回退与重规划

### 7.3 阶段与节点的状态关系

建议约束如下：

1. Stage `running` 不代表所有节点都在 `running`
2. Stage `graph` 模式下，允许只有一个当前节点处于 `running`
3. 当所有必需节点完成后，Stage 才可进入 `completed`
4. 任一关键节点失败时，Stage 可进入 `blocked` 或 `failed`

### 7.4 节点选择规则

系统选择“当前节点”的规则：

1. 当前 Stage 必须为 `graph`
2. 节点状态为 `pending`
3. 所有依赖节点已 `completed`
4. 若有多个候选，按拓扑顺序选第一个
5. 如果已有 `running` 节点，不允许再次发起执行

## 8. 技术方案

### 8.1 顶层接口改造

不再从产品语义上暴露“task graph 独立执行”，而是改为 Workflow 阶段执行接口。

建议新增 BFF 接口：

```text
POST /api/workflow-templates/:templateId/publish
POST /api/tasks/:taskId/workflow/instantiate
POST /api/tasks/:taskId/workflow/stages/:stageRunId/node-graph
POST /api/tasks/:taskId/workflow/stages/:stageRunId/execute-current-node
POST /api/tasks/:taskId/workflow/stages/:stageRunId/nodes/:nodeId/execute
POST /api/tasks/:taskId/workflow/continue
```

其中：

1. `publish` 负责将管理员配置的模板发布为正式版本
2. `instantiate` 负责在任务创建或绑定模板时，立即生成各阶段初始任务
3. `node-graph` 负责创建或更新当前任务在指定阶段下的节点图
4. 阶段执行接口仅负责推进已生成的阶段实例

### 8.2 请求与响应

请求体：

```json
{
  "sessionId": "ses_xxx",
  "mode": "manual",
  "instructions": "可选，用户补充说明"
}
```

响应体：

```json
{
  "ok": true,
  "taskId": "task_xxx",
  "stageRunId": "stage_xxx",
  "nodeId": "node_xxx",
  "sessionId": "ses_xxx",
  "agentRunId": "run_xxx",
  "status": "running"
}
```

### 8.3 Prompt 生成规则

节点执行仍由系统生成结构化 Prompt，但上下文从“独立 DAG 节点”改为“当前阶段中的节点”。

示例：

```text
你正在执行 Workflow 的 implement 阶段中的当前节点。

阶段目标：完成当前功能开发。
节点标题：补齐 Web UI 测试
原始任务描述：为工作台补齐统一 Workflow 节点执行能力。
前置依赖结果：接口改造已完成。
完成标准：新增测试并通过相关校验。

请只完成当前节点，不要跨到其他节点。
完成后输出结构化摘要，供系统回写当前节点结果。
```

### 8.4 运行态回写

执行上下文改为：

```text
taskId + workflowRunId + stageRunId + nodeId + sessionId + agentRunId
```

回写规则：

1. 节点开始执行时，Node `pending -> running`
2. 节点完成时，Node `running -> completed`
3. 节点失败时，Node `running -> failed`
4. 节点摘要、错误、耗时、token 回写到 Node 记录
5. 所有必需节点完成后，Stage 才从 `running -> completed`

### 8.5 阶段初始任务生成规则

管理员发布模板后，系统应支持“预生成阶段任务骨架”。

规则如下：

1. 模板一旦发布，即固化该版本的阶段顺序、执行模式和 Gate 配置
2. 任务绑定模板时，系统立即创建该模板对应的全部 `WorkflowStageRun`
3. 首阶段可按策略直接进入 `pending` 或 `running`
4. 后续阶段初始为 `pending`，但在 UI 中可见
5. 若某阶段为 `graph` 模式，则只生成阶段骨架，不必立即生成内部节点图
6. 阶段内部节点图可在阶段激活时生成，也可按模板配置提前生成

这样做的意义是：

1. 普通用户从任务创建开始就能看到完整阶段路径
2. 管理员能审计模板实例化结果
3. 系统不需要等到运行时再临时推断有哪些阶段

### 8.6 前端工作台改造

TaskDetail 应按两层展示：

1. Workflow 层
   - 当前阶段
   - 阶段状态
   - 阶段产物
   - 阶段审批/阻断信息

2. Stage 内部 Node 层
   - 仅在 `graph` 模式阶段显示
   - 当前节点
   - 节点状态
   - 节点依赖
   - 节点结果面板

## 9. 生成方式

统一后，Workflow 与节点图都允许自动生成或手工配置，但归属于同一套模板体系。

### 9.1 Workflow 模板生成方式

1. 管理员手工创建模板
2. 模型根据任务类型推荐模板，再由管理员确认
3. 管理员发布模板后，模板版本进入可实例化状态

### 9.2 Stage Node Graph 生成方式

1. 规则生成
   - 管理员为某些阶段预定义节点模板
2. 模型生成
   - 模型输出结构化节点，再由 BFF 校验后落库
3. 用户手工设计
   - 普通用户在任务级为允许自定义的阶段手工编辑节点图
   - 保存后生成当前任务私有的 Stage Node Graph

### 9.2.1 用户手工设计的边界

允许普通用户手工设计节点图，但必须满足以下约束：

1. 只作用于当前任务实例，不回写模板
2. 只能在模板授权的阶段进行
3. 不能删除阶段本身，也不能改变阶段顺序
4. 不能绕过模板中的 Gate、审批和必填产物要求
5. 节点图一旦开始执行，修改必须走暂停或重规划流程

### 9.3 原则

关键原则不是“谁来生成”，而是“统一挂在 Workflow 模板之下”。

也就是说：

1. 模型可以帮忙生成
2. 管理员也可以手工维护
3. 但最终都不能形成第二套平行状态机
4. 模板一旦发布，系统应能稳定实例化出一组初始阶段任务，而不是依赖运行时临时生成

## 10. 从现有 DAG 迁移到统一 Workflow 体系

### 10.1 迁移目标

迁移的目标不是简单把 runtime DAG 挪到 BFF，而是：

1. 取消 DAG 作为独立顶层语义
2. 将现有 task graph 归并为 Stage 内部 Node Graph
3. 将执行、审批、治理全部收口到 Workflow 体系

### 10.2 迁移步骤

#### Phase 1：冻结独立 DAG 语义

交付：

1. 文档与产品文案不再把 DAG 作为平级主流程
2. UI 中逐步改名为“阶段内节点”或“阶段执行图”
3. `继续当前分支` 与“执行当前节点”彻底分离

#### Phase 2：停止 runtime 继续生成独立 DAG

交付：

1. 从 `opencode.json` 中移除 `task-graph-plugin.ts`
2. 从 BFF Prompt 注入逻辑中删除 `task_graph_*` 工具提示
3. runtime 不再承担 DAG 状态机职责

#### Phase 3：BFF 接管统一 Workflow Execution

交付：

1. BFF 按 Workflow 模板生成 StageRun
2. 对允许 `graph` 的 Stage 生成 Node Graph
3. Node Graph 落库到控制面，关联到 `stageRunId`

#### Phase 4：兼容历史任务

交付：

1. 旧的 task graph 读取后映射为历史 Stage 的节点图
2. 标记为 `executionSource = runtime-legacy`
3. 新任务只允许使用统一 Workflow Execution 路线

### 10.3 数据层建议

建议保留现有节点表，但语义重命名并补充关联字段：

1. `workflowRunId`
2. `stageRunId`
3. `executionSource`
4. `templateStageKey`
5. `summary`

这样可以减少一次性大迁移成本，同时完成语义收口。

## 11. 普通用户与管理员使用说明

### 11.1 普通用户如何使用

普通用户只需要理解两层：

1. 任务现在在哪个阶段
2. 当前阶段内部是否有可执行节点

普通用户标准流程：

1. 打开任务工作台
2. 查看当前 Workflow 阶段
3. 如果系统提示“当前阶段包含执行节点”，则查看当前节点
4. 点击 `执行当前节点` 推进阶段内执行
5. 若需要补充自然语言说明，则点击 `继续当前分支`
6. 查看阶段结果和节点结果

如果当前阶段允许用户自定义节点图，则普通用户还可以：

1. 打开“设计阶段节点图”入口
2. 新增、删除或调整当前阶段内节点
3. 配置节点依赖和完成标准
4. 保存为当前任务专属节点图
5. 点击 `执行当前节点` 开始运行自己设计的节点图

普通用户在任务刚创建时就应看到：

1. 当前 Workflow 已生成的完整阶段列表
2. 当前激活阶段
3. 后续待进入阶段
4. 某些阶段是否会在激活后展开节点图

普通用户能看到的结果：

1. 当前阶段状态变化
2. 当前节点状态变化
3. 执行输出摘要
4. 是否进入下一节点或下一阶段

### 11.2 管理员如何使用

管理员主要做三类工作：

1. 配模板
2. 配策略
3. 配可见性与自动化

管理员配置流程：

1. 创建或维护 Workflow 模板
2. 为每个阶段指定默认执行模式
3. 指定哪些阶段允许展开节点图
4. 配置节点图生成方式：规则或模型
5. 配置节点自动推进、审批、失败恢复和人工确认策略
6. 决定普通用户能看到摘要还是完整节点图
7. 决定普通用户是否具备“设计并运行阶段节点图”的权限

管理员发布模板后的系统行为应是：

1. 任务一旦选择该模板，就立即生成阶段任务骨架
2. 每个阶段都有唯一 `stageRunId`
3. 每个阶段都可被审计、阻断、审批或回退
4. 后续如修改模板，应通过新版本发布影响新任务，而不是回写旧任务

管理员还需要决定：

1. 哪些阶段允许任务级节点图自定义
2. 普通用户自定义后是否需要审批才能运行
3. 普通用户是否可从现有完成结果重新开分支

管理员关注的结果：

1. 模型是否按阶段输出正确产物
2. 哪些阶段最常阻断或失败
3. 哪些节点最容易失败或重试
4. 模板是否需要持续优化

## 12. 验收标准

产品侧验收：

1. 用户只能感知到一套主流程，即 Workflow
2. 用户知道节点图只是当前阶段内部展开，而不是第二套主流程
3. 普通用户能区分“继续当前分支”和“执行当前节点”
4. 管理员能清楚配置哪些阶段启用节点图
5. 任务创建后，用户能立即看到由模板实例化出的阶段任务列表
6. 若模板允许，普通用户可在任务级设计并运行阶段节点图

技术侧验收：

1. Workflow 成为唯一顶层执行真相源
2. Node Graph 只存在于 `graph` 模式 Stage 中
3. 节点执行具备明确 `stageRunId/nodeId/sessionId/agentRunId` 关联
4. 历史 runtime DAG 可兼容读取，但新任务不再依赖 runtime graph
5. Workflow 模板发布后，可稳定实例化全部初始 `WorkflowStageRun`
6. 用户自定义节点图只作用于任务实例，不污染模板版本

## 13. 最终建议

最终建议不是“继续做独立 DAG”，而是：

1. 用 Workflow 统一主流程
2. 用 Stage 表达阶段治理
3. 用 Node Graph 表达阶段内执行依赖

这样可以同时保留：

1. Workflow 的阶段约束能力
2. Node Graph 的细粒度执行能力
3. BFF 统一治理、审计、审批和执行控制能力

最终判断：

1. Runtime 适合负责 session 执行
2. BFF 适合负责统一 Workflow Execution 体系
3. Node Graph 应作为 Workflow 的内嵌能力，而不是第二套平级产品模型
