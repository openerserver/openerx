# OpenerX 版本页对比表与 CTA 文案初稿

> 适用范围：官网版本页、定价页、销售资料中的版本对比模块
>
> 目标：提供一版可直接用于产品页或销售资料的版本页结构、对比表和 CTA 文案初稿，帮助后续清晰呈现 Foundation、Team、Enterprise 的差异

## 1. 页面目标

版本页要解决的不是“列出功能清单”，而是让客户快速判断：

1. 自己处于哪个阶段
2. 需要哪一层治理深度
3. 下一步应该试用、演示还是联系销售

版本页必须明确表达：

**版本差异不是功能多少，而是治理深度不同。**

## 2. 页面标题与引导文案

### 页面标题

从评估入口到组织级治理，选择适合你的 AI 控制面版本。

### 页面副标题

OpenerX 按治理深度而不是按功能堆叠划分版本。你可以从基础控制面验证开始，逐步升级到团队流程治理，再进入组织级审计、私有化和企业连接场景。

## 4. 版本对比表初稿

| 对比维度 | Foundation | Team | Enterprise |
|------|------|------|------|
| 产品定位 | 基础控制面入口 | 团队治理主力版 | 企业治理与组织经营版 |
| 适用阶段 | PoC / 评估 | 真实团队运行 | 组织级治理与私有化 |
| 项目与仓库规模 | 小规模评估 | 多项目、多仓库 | 组织级规模 |
| 任务与仓库绑定 | 基础支持 | 完整支持 | 完整支持 |
| 工作流模板 | 基础查看与绑定 | 完整团队流程支持 | 组织级模板治理 |
| 角色协作 | 基础视图 | 团队级角色协作 | 高级角色聚合与经营 |
| 审批能力 | 基础审批视图 | 基础审批与阻断 | 高级审批编排与多级审批 |
| 预算与治理 | 基础可见性 | 阈值、告警、限流 | 高级预算治理与组织级归因 |
| 原始审计流 | 基础查看 | 查看与导出 | 完整导出、解封、校验 |
| 证据导出 | 基础导出 | 标准导出 | 企业级审计包 |
| 老板 Agent 能力 | 不默认强调 | advisory / exception-only | 更高等级经营与自动托管 |
| 私有部署 | 不提供 | 可按需评估 | 标准企业能力 |
| 企业连接器 | 不提供 | 不默认提供 | 标准企业能力 |
| 支持模式 | 评估支持 | 标准商业支持 | 企业 SLA 与专属支持 |

## 5. 推荐展示方式

建议版本页展示顺序：

1. 三张版本卡片
2. 对比表
3. “你适合哪一版”分流区
4. CTA 区

不要只放一张横向对比表，否则客户会把页面读成普通 SaaS 功能对照页。

## 6. “你适合哪一版”分流文案

### 如果你正在验证控制面是否成立

推荐：Foundation

说明：

先验证任务、仓库、角色和原始审计流能否在你的环境里跑通，再决定是否进入团队级治理。

CTA：申请评估版

### 如果你已经准备把 AI 纳入团队研发流程

推荐：Team

说明：

当你不再满足于零散试用，而是需要让角色、流程、审批和治理真正生效时，Team 是最合适的主力版本。

CTA：预约演示

### 如果你面临组织级审计、私有化或合规要求

推荐：Enterprise

说明：

当问题不再只是功能可用，而是组织级治理、审计、私有部署和内部系统连接时，Enterprise 才是正确入口。

CTA：联系销售

## 8. 不建议出现在版本页的表达

不建议强调：

1. 聊天次数
2. 消息数
3. 模型品牌数量
4. “更便宜的企业 AI 工具”
5. “功能更多所以更贵”

这些表达会把版本页拉回低价工具比较维度。

## 9. 版本页收口文案

建议页尾使用：

OpenerX 的版本差异，不在于多几个按钮，而在于你希望 AI 在你的组织中承担多深的流程责任、接受多强的治理约束，以及提供多完整的审计证据。

一句话总结：

**如果你只需要一个 AI 工具，版本差异并不重要；如果你需要一个 AI 控制面，版本边界就非常重要。**
